# MEASUREMENT: issue #8 seeding and issue #21 soak, 2026-10-09

Status: final. #8 and #21 both measured on 2026-10-09; evidence under `docs/verification/evidence/measure-8-21/`.
Everything below labelled MEASUREMENT states its sample size.
Nothing here closes an issue; it supplies evidence for the #8 seeding row and for decision D3 in `docs/reviews/open-issues-triage-20261009.md`.

## Headline

1. MEASUREMENT (n=5 per size): `cowfs snapshot create --from base` is flat in tree size.
   Median 11 ms to 12 ms from 1,012 to 1,010,101 inodes, where the median includes about 2 ms of `cowfs` CLI process start.
   Native `cp -a` of the same tree grows from 44 ms to 33.8 s over the same range.
2. MEASUREMENT (n=5): the "first `cargo build --frozen` stays Fresh, 0 crates compiled" criterion is NOT MET when the warm base is made with `cowfs import`.
   All 5 of 5 snapshots recompiled 19 crates (9.4 s median, vs 10.0 s for a native clean build).
   Cause, confirmed on the one fixture: `cowfs import` does not preserve mtimes (0 of 462 files equal the source) and does not preserve hardlinks (0 of 18).
3. MEASUREMENT (n=5 per arm): the criterion IS met when the warm base is built inside the mount, or copied in with `cp -a`.
   Snapshot create 7 ms median, first build 0.069 s median, 0 crates compiled and 34 Fresh in 10 of 10 builds, 18 hardlinks preserved.
4. MEASUREMENT (n=1 run, 36 minutes, 20 cycles): the #21 soak did NOT reproduce any corruption.
   22 of 22 `git fsck --full` and 22 of 22 `git verify-pack` exit 0 on the Core FUSE mount, 21 of 21 byte-identity sweeps of 25,261 worktree files matched the source, 0 zeroed 4 KiB pages in any idx or pack, and a store reopen through a fresh daemon was clean.
   This is a non-reproduction in one window, not proof the historical `.idx` corruption is gone, and the real 805 MiB repo with full history was not available (see the #21 section).
5. Defects found while measuring, filed as issue #290: `cowfs import` drops hardlinks and mtimes; `cowfs import` of 1,000,000 files and `cowfs fsck` of a 154 GB store both hit the CLI default 30 s no-reply timeout (exit 4) while the server keeps working.

  Its only OPEN row is this seeding measurement, "never done".

This report therefore measures:

3. Seeding a warm Rust base: snapshot create, then first `cargo build --frozen -v`, with Fresh and hardlink checks, n=5.
4. Native do-nothing baselines, interleaved within each replicate: `cp -a --reflink=auto`, `cp -a --reflink=never`, `rsync -aH`, and for the Rust fixture `git worktree add`.

### #21 (issue body bullets 2 and 3, plus the PR #104 comment)

Copied from the issue:

- "One `.idx` on the mount had 101 zeroed runs from offset 180,224 (fsck exit 14). The `.pack` was valid and bytes matched the backing store. ... Needs a long soak (repeated `gc`, `repack -adf`, `fsck --full` on the 805 MiB OmniRoute repo) on the fixed server before this can be closed."

This run is the closest Linux equivalent, the Core backend served over FUSE, and is labelled as such.

## #8 results

### 1. Snapshot create versus tree size

MEASUREMENT, n=5 replicates per size, each replicate is `cowfs snapshot create sK --from base` timed from the CLI (wall clock including the CLI process).
Trees are N unique 2 KiB files, 100 files per directory, every tenth entry a hardlink to the previous file.
The no-op round trip `cowfs status` costs a median 2.1 ms in the same environment, so about 2 ms of each figure below is process start.

| Files requested | Inodes | Apparent MiB | Snapshot create median (min to max) | First replicate | Snapshot rm median |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 1,012 | 2 | 0.011 s (0.008 to 0.091) | 0.091 s | 0.102 s |
| 10,000 | 10,102 | 18 | 0.011 s (0.010 to 0.058) | 0.058 s | 0.051 s |
| 100,000 | 101,011 | 176 | 0.012 s (0.009 to 0.526) | 0.526 s | 0.082 s |
| 1,000,000 | 1,010,101 | 1,758 | 0.012 s (0.011 to 0.067) | 0.067 s | 0.109 s |

Reading: the median does not move across three orders of magnitude, so the create is O(1) in tree size at this resolution.
The first replicate and one 0.040 s replicate are slower in several rows (cold caches, other agents' load); with n=5 the max is a single outlier and no tail statistic is claimed.
Per-replicate load1 at 1,000,000: 13.3, 10.9, 12.1, 10.2, 10.9.

Isolation and correctness checks per size: a write into the snapshot (first replicate) left the base byte-identical and was visible in the snapshot (4 of 4 sizes), the snapshot walk saw exactly the base inode count (4 of 4), and `cowfs fsck` returned 0 after each run (4 of 4).

### 2. Bytes added to metadata

The meta file is `meta.redb`.
Its `st_size` did not change on any snapshot create at any size (0 bytes, 20 creates), because redb pre-extends the file.
Allocated blocks changed by 0 to 24,576 bytes on the first creates of the small sizes and by 0 bytes at 100,000 and 1,000,000.
A bulk run of 200 creates per size moved neither `st_size` nor allocated blocks (0 bytes), at 7.5 ms to 7.9 ms per create.
So the per-snapshot metadata cost is below the resolution of file-size observation, at most a few KiB.
This is a resolution limit, not a measurement of the exact byte count, and it is the weakest number in this report.
For scale, the metadata after importing the 1,000,000-file base was 539 MB (`st_size`) and 393 MB allocated, so a snapshot adds a negligible fraction of that.

### 3. First walk of a new snapshot (seeding the directory view)

MEASUREMENT, n=5 per size, `find <snapshot> | wc -l` immediately after create, against the same walk of a native copy.

| Inodes | cowfs first walk median | native walk of source median | ratio |
| --- | --- | --- | --- |
| 1,012 | 0.005 s | 0.004 s | 1.2x |
| 10,102 | 0.023 s | 0.007 s | 3.3x |
| 101,011 | 0.189 s | 0.042 s | 4.5x |
| 1,010,101 | 2.82 s | 0.419 s | 6.7x |

The mount walk is linear in inodes and slower than native btrfs by a growing factor.
This is lookup cost through FUSE, paid lazily by whoever walks the tree, not snapshot cost.

### 4. Do-nothing baselines, same tree, same replicate

MEASUREMENT, n=5 per cell, median (min to max) in seconds.
`cp --reflink=auto` is a real reflink on this btrfs.

| Inodes | `cp -a --reflink=auto` | `cp -a --reflink=never` | `rsync -aH` | cowfs snapshot create |
| --- | --- | --- | --- | --- |
| 1,012 | 0.044 (0.040 to 0.044) | 0.045 (0.032 to 0.054) | 0.111 (0.107 to 0.112) | 0.011 |
| 10,102 | 0.348 (0.276 to 0.486) | 0.425 (0.403 to 0.586) | 0.599 (0.524 to 0.802) | 0.011 |
| 101,011 | 3.27 (3.01 to 3.82) | 4.66 (4.29 to 4.85) | 6.32 (5.53 to 16.9) | 0.012 |
| 1,010,101 | 33.8 (33.3 to 53.0) | 40.8 (40.4 to 41.9) | 57.7 (57.3 to 66.8) | 0.012 |

At 1,012 inodes a native reflink copy (44 ms) is slower than a snapshot create by about 4x, and the gap widens to about 2,800x at 1,010,101 inodes.
"Near the clone, not near the copy numbers" is met on cost, since a reflink copy is linear in file count on btrfs and the snapshot is not.
Note the cp cost on btrfs is per-file metadata work; there is no whole-tree clone primitive here as there is with APFS `cp -c`.

### 5. Seeding a warm Rust base: first `cargo build --frozen`

Fixture: a binary crate with clap, serde, serde_json, regex, anyhow and chrono, debug build, 462 files, 221 MiB apparent, 18 hardlinked files, 34 units in the build graph.
Native clean build baseline: 9.97 s, 9.97 s, 10.02 s (n=3; compiles 34).
Native in-place rebuild with nothing changed: 0.045 s, 0 compiled, 34 Fresh.
The issue's 322 hardlinks and 5.3 s clean build were for a different crate on a Mac; the figures here are this fixture's.

#### 5a. Base created with `cowfs import` (the existing seeding path)

MEASUREMENT, n=5 replicates, arms interleaved in one replicate, cowfs first.
Build is `cargo build --frozen -v -j 4` at the new path.
Load1 11.1 to 12.8.

| Arm | Copy or snapshot median (min to max) | First build median (min to max) | Crates compiled | Fresh |
| --- | --- | --- | --- | --- |
| cowfs snapshot of imported base | 0.018 s (0.012 to 0.028) | 9.40 s (9.24 to 9.60) | 19 of 34, in 5 of 5 | 15 |
| `cp -a --reflink=auto` | 0.036 s (0.027 to 0.037) | 0.056 s (0.046 to 0.063) | 0 in 5 of 5 | 34 |
| `cp -a --reflink=never` | 0.146 s (0.133 to 0.148) | 0.066 s (0.059 to 0.088) | 0 in 5 of 5 | 34 |
| `rsync -aH` | 0.360 s (0.357 to 0.373) | 0.067 s (0.061 to 0.080) | 0 in 5 of 5 | 34 |
| `git worktree add` (tracked files only, no `target/`) | 0.006 s (0.005 to 0.008) | 9.90 s (9.60 to 10.12) | 34 in 5 of 5 | 0 |

The `git worktree add` row is not an equivalent artifact (no warm `target/`); it shows what a seedless tree costs.

Result: with an imported base, snapshot plus first build is 9.4 s, which is NOT better than the native clean build (10.0 s) and about 100x worse than a native reflink copy plus build (0.09 s).
The criterion "Fresh first build (0 crates compiled)" is NOT MET on this path.
Hardlink count: native 18, `cp -a` 18, `rsync -aH` 18, cowfs snapshot of the imported base 0 (n=5).

Cause (one fixture, diagnostic run with `cargo build -v`, labelled a confirmed mechanism for this fixture, not a general proof):
cargo printed `Dirty <crate>: the dependency <leaf> was rebuilt (...)`, comparing output mtimes.
Comparing every regular file of the source against the imported base: modes equal for 462 of 462, mtimes equal for 0 of 462.
The imported mtimes are the import time, in ingest order, so cargo's fingerprint comparison between a dependency and its dependents fails.
The hardlink loss is measured separately: 18 hardlinked files in the source, 0 in the imported base (also 0 of 200, 2,000, 20,000 in the synthetic trees at the three smaller sizes; not checked at 1,000,000).

#### 5b. Base made inside the mount (build in place, or `cp -a` into the mount)

MEASUREMENT, n=5 replicates for each of two bases, built to be the realistic flow where the base is produced on the mount.
Base A: `cp -a` of the native warm tree into an empty snapshot (2.19 s for the copy).
Base B: source copied in, clean `cargo build` run inside the mount (11.3 s, 34 compiled).
Load1 12.4 to 12.6.

| Base | Snapshot create median (min to max) | First `cargo build --frozen` median (min to max) | Compiled | Fresh | Hardlinked files |
| --- | --- | --- | --- | --- | --- |
| A (`cp -a` into mount) | 0.007 s (0.006 to 0.032) | 0.069 s (0.064 to 0.074) | 0 in 5 of 5 | 34 | 18 of 18 |
| B (built in place) | 0.007 s (0.006 to 0.115) | 0.068 s (0.059 to 0.076) | 0 in 5 of 5 | 34 | 18 of 18 |

Snapshot plus first build is about 0.076 s against a native clean build of 10.0 s.
Native reflink copy plus build is about 0.09 s on this box, so cowfs seeding is on par with the native reflink on this fixture and far under the native clean build.
`cowfs fsck` returned 0 after both runs.
This meets the issue's Fresh and hardlink criteria, for bases not created through `import`.

### 6. Verdict on #8

- O(1) snapshot claim: MEASURED at flat 11 to 12 ms median from about 1 thousand to 1 million inodes, n=5 per size.
- Seeding acceptance criterion: MET for bases built or copied on the mount, NOT MET for bases created by `cowfs import`.
- Metadata byte count per snapshot: below the resolution of this method.

## #21 results

### What ran

MEASUREMENT, one soak run, 20 cycles, 12:14:00 to 12:50:12 on 2026-10-09 (36 minutes of wall clock), label: Linux FUSE equivalent of the macOS NFS soak, not the original configuration.

Corpus: `diegosouzapw/OmniRoute` cloned with `--depth 1` at `977d0065d9`, 25,290 files, 883,971,260 bytes (843 MiB) imported with `cowfs import`, `verified: true`.
The issue's "805 MiB OmniRoute repo" is not recoverable: the full-history clone is 2.1 GiB on disk (1.36 GiB pack), the 805 MiB repo from the spike no longer exists on this box, and a depth-1 clone is the closest size.
The consequence is a shallow history with one pack of about 130 MB, so repack and gc work on a smaller object graph than the original.

Setup: fresh store, Core backend over FUSE, `git` working directly inside `mnt/soak` (both worktree and `.git` on the mount).
Each cycle did, in order:

1. `git checkout -b tN`, append a marker to 300 random tracked files, write a 3 MiB random new file, `git add -A`, `git commit`, `git status`, `git checkout` back to the original branch.
2. One of `git gc`, `git repack -adf`, or `git gc --aggressive --prune=now`, rotating (7, 7 and 6 runs).
3. `git fsck --full`, `git verify-pack` on every idx, and a scan of every idx and pack for all-zero 4 KiB pages (the original symptom was zeroed runs from offset 180,224).
4. Delete the topic branch, then sha256 every tracked-tree file (25,261 files) against the source clone.
5. Every third cycle, `cowfs fsck`.

Concurrent write pressure for the whole run: a thread rewrote random files of 100 B to 1 MiB with modes 0444, 0400 and 0644 in an untracked directory on the same mount (610,854 write, chmod and read-back operations, 0 read-back mismatches, 0 errors).
This exercises the read-only-mode write race from bullet 1 and parallel WRITEs.
Host load1 during the soak was 3.2 to 19.6 (most samples 5 to 14).

Harness controls before the soak:
a clean native repo passed all checks, and the same repo with 8 KiB of its idx zeroed at offset 180,224 was detected (`git fsck` exit 11, `git verify-pack` exit 1).
So the checks would have flagged the original shape.
`git show-index` was deliberately not used as a gate; `scripts/verify-git-index-integrity.py` already records that it returns 0 on a zeroed idx.

### Results

| Check | Runs | Failures |
| --- | --- | --- |
| `git fsck --full` on the mount | 22 (before, 20 cycles, after reopen) | 0 |
| `git verify-pack` on the mount idx | 22 | 0 |
| zero-page scan, idx and pack | 22 idx, 22 pack | 0 zero pages |
| byte identity, 25,261 worktree files vs source | 21 (20 cycles and after reopen) | 0 mismatching files |
| `git gc`, `repack -adf`, `gc --aggressive` | 7, 7, 6 | 0 non-zero exits |
| `git add`, `git commit`, `git checkout` | 20 each | 0 non-zero exits |
| concurrent churn operations | 610,854 | 0 bad |
| `cowfs fsck`, default 30 s CLI timeout | 7 attempts (cycles 3, 6, 9, 12, 15, 18 and final) | 1 passed (cycle 3), 6 timed out with exit 4 |
| `cowfs fsck`, 3000 s timeout, after the soak | 1 | 0 problems, 2,395,167 blocks, 154,418,273,801 bytes, 88 s |

The timeouts are the CLI giving up after 30 s without a reply while the store grew; the follow-up run with a long timeout checked every block and found no problems.
That is a harness and usability limit, not an integrity failure, but it means the in-soak `cowfs fsck` evidence is the single pass at cycle 3 plus the final long-timeout run.
The store reopened through a fresh daemon after the soak and `git fsck --full` plus the byte-identity sweep passed again.

### Observations that are not integrity failures

- First attempt, discarded: `git add -A` died with signal 7 (SIGBUS) in cycle 1 because the harness's churn thread was truncating files in a directory that `git add -A` was hashing.
  This is the harness's own race, not a cowfs result; the churn directory was excluded via `.git/info/exclude` and the run was restarted.
  It was not reproduced natively; the attribution is a likely cause, not a confirmed one.
  The log is kept as `soak-attempt1-sigbus.jsonl`.
- The store grew to 154 GB for an 843 MiB repo because the churn thread wrote about 150 GB of incompressible unique data over 36 minutes and `cowfs gc` was not run.
  This is expected under no GC and says nothing about leak.
- The daemon printed `closing the backend: closing the core: stale inode` once on the mid-soak shutdown for the reopen, and once when a 1,000,000-file measurement run was interrupted.
  The soak continued and verified clean after the reopen; the message was not investigated.

### Verdict on #21

- Bullet 2 (unexplained corrupt idx): NOT REPRODUCED in a 36 minute, 20 cycle Linux/FUSE soak at about 843 MiB with concurrent writes.
  This matches the earlier 42-operation macOS result in `docs/verification/ready-21.md`, at a larger size and longer duration, on a different mount transport.
- Bullet 3 (write-race fix on a large repo): 610,854 concurrent mode-flipping writes and 20 git write cycles completed with 0 errors on the Core, which stores modes as metadata.
  Not exercised: the macOS NFS client and a repo with the original full history.
- The decision D3 is still a human call; this report offers a longer non-reproduction, nothing more.

## Limits and what is not claimed

- Single host, shared box, load1 9 to 17 throughout; absolute times are inflated.
  The cowfs and native arms of each replicate ran back to back, so ratios are more trustworthy than absolutes.
- n=5 per cell; min and max are shown, standard deviations from n=5 are rough.
- Tree contents are synthetic 2 KiB unique files for the scaling runs, one Rust fixture for seeding.
  The 322-hardlink Mac crate and 130 MiB base were not reproduced; the fixture here is 221 MiB with 18 hardlinks.
- The cause for the non-Fresh imported build is confirmed on one fixture by an mtime comparison and cargo's own `Dirty` reason lines.
  It was not checked whether any other cause also contributes.
- The macOS NFS client path is not covered by anything on this box.
- The scaling runs at 1,000, 10,000 and 100,000 files used an earlier revision of `m8.py.txt` than the committed one; the committed version adds `--timeout 3600` on every control call, a mismatch record in place of an assert, and the hardlink check only on mismatch, so the hardlink count at 1,000,000 files was not measured.
- The #21 soak is one run; no rate or confidence interval for a rare corruption can be derived from it.
- Scratch on the box (148 GB, sources, stores, target) was deleted after the run; a `cargo fetch` added to the shared `~/.cargo` registry cache on the box.
- The harness sources are stored as `.py.txt` under `docs/verification/evidence/measure-8-21/` so repository Python lint and test discovery do not pick them up; rename to `.py` to run.
- No file in the repository other than this report and that evidence directory was changed.
