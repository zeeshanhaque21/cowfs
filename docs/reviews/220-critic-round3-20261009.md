## 1. Hash choice, width, length

The hash is an inline FNV-1a 64 over the target bytes (`swap.rs:76`), not `std::collections::hash_map::DefaultHasher`.
It is deterministic across processes, runs and Rust versions.
Format is `prefix ~ 16 lowercase hex ".cowfs-swap" "0"`, so the suffix is a fixed 29 bytes.
Prefix is `min(len, 200)` bytes, decremented to a char boundary (`is_char_boundary(len)` is true, so the loop terminates and never splits UTF-8).
Maximum staging name is 200 + 29 = 229 bytes, under NAME_MAX 255 and under BASE_NAME_MAX 240, for every valid target up to 255 bytes.
Because the suffix length is fixed, two staging names are equal only if prefix and hash are both equal; a `~` inside a target cannot create an ambiguity.
Collision probability for two distinct targets with the same 200-byte prefix is about 2^-64 for non-adversarial names.
A collision is not detected (see note N1), but it no longer matters for recovery because recovery never recomputes the name (section 2).

## 2. Recorded staging name, old intents

`write_intent` records `"{staged}\n{target}\n"`, and `recover_intent` passes the recorded `staged` to `finish_swap`; nothing compares it with `staging_name(target)`.
Intents from main and from 9f8e27e record the old name (`target.chars().take(200)` + `.cowfs-swap0`), which still satisfies `is_staging`, so they recover unchanged after upgrade.
The sweep builds its keep-set from the recorded names of every readable intent, so an old-named staging snapshot an intent still names is kept.
The only recomputations are the torn-intent branch and the leftover cleanup at the start of swap and ingest; neither runs when a readable intent exists for that target, because `recover_target` finishes it first.
Out of scope and pre-existing: two main-era pending intents for long targets sharing a 200-char prefix already share one staging snapshot on disk; the second recovers as NotFound with `last_error`; this head cannot repair that.

## 3. Trailing-newline rule (highest-risk point)

Every version of the writer in history writes `format!("{staged}\n{target}\n")` (checked across every commit that touched `swap.rs` on main; there is only that one format, since f50446e).
Main and this head both write a temp, fsync it, rename it over `swap-<target>`, then fsync the directory, and only then remove the victim.
So a legitimate intent file named `swap-<target>` always ends in `\n`; the stricter `read_intent` cannot reject a valid intent from main, from 9f8e27e or from this head.
Names cannot contain control characters (`cowfs-snapname`), so a `\n` or `\r` inside a name cannot fake a record boundary.

## 4. Orphan sweep after a rejected intent

A rejected intent reaches the sweep only if the file is torn, which with temp plus rename means either a main-era temp `swap-<X>.tmp` cut before its rename, or media corruption.
Main-era torn temp: its swap had not passed the point of no return (the rename precedes victim removal), so sweeping its staging snapshot loses nothing committed; the torn branch deletes `staging_name("<X>.tmp")`, which only a `swap-<X>.tmp` intent could name, and that is this same file.
Main-era complete temp: read OK, name equals `swap-<recorded target>.tmp`, dropped without rolling forward, which is correct for the same reason.
A real intent for a target named `x.tmp` (file `swap-x.tmp`, recorded target `x.tmp`) does not equal `swap-x.tmp.tmp`, so it rolls forward; this also heals the round-1 bug for intents main wrote.
Corrupted committed intent: the new tree is deleted (N2); main did the same, so not a regression.

## 5. Earlier counterexamples against 56f1c91

Round 1, target `base.tmp`: `intents()` takes every `swap-*` file, the temp is `tmp-swap-<target>`, and open removes stray `tmp-swap-*` before scanning.
`a_target_named_like_a_temp_file_is_rolled_forward` and `two_pending_swaps_whose_names_differ_by_a_suffix_both_recover` cover it.
Round 2, `'a'*200+'1'` and `'a'*200+'2'`: same 200-byte prefix, different FNV hashes, so distinct staging names; a plain ingest of B removes only `staging_name(B)` and leaves A's staging.
Both pending then reopen: each intent names its own staging snapshot, so A gets A and B gets B; the two new tests assert exactly this.

## 6. PR body honesty

Claims match the code: FNV-1a 64 of the full target, prefix at most 200 bytes on a char boundary, no `staged == staging_name(target)` check, trailing-newline rule, failing-first tests named.
One inaccuracy (N3): "Names of 201 to 250 bytes do get an intent file" is true for the intent file name, but the temp `tmp-swap-<name>` needs 9 + len <= 255, so names of 247 to 255 bytes fail `write_intent` with ENAMETOOLONG and roll back cleanly.
Main's temp `swap-<name>.tmp` had the same 9 extra bytes, so this is pre-existing and not a regression.

## Notes

N1. Leftover cleanup in `swap_snapshot` (`swap.rs:261`) and `ingest_with` (`import.rs:156`) unregisters `staging_name(target)` without checking that no other intent names it.
With a crafted FNV-1a 64 collision (two names with equal 200-byte prefix and equal hash, feasible by birthday search for a local user) plus an in-process pending intent for the other name, the round-2 loss reappears.
Not reachable by accident (about 2^-64), and only by the store owner against their own store; cheap hardening is to skip the unregister when any readable intent records that staging name, the same set `sweep_orphans` builds.
N2. Torn-intent policy destroys the staging tree even when the victim was already removed.
The file name `swap-<target>` already carries the target, so a torn intent whose `staging_name(target)` snapshot exists could be rolled forward or kept and reported instead of deleted.
Pre-existing behaviour on main; only reachable through media corruption once temp plus rename is used.
`a_torn_intent_is_not_read_as_a_shorter_name` encodes the current choice (it asserts no stray `ab` and no leftovers, and `abc` ends up with neither old nor new content).
N3. Replacing import of a 247 to 255 byte name always fails at the intent temp file (pre-existing; bases are capped at 240 so promote is unaffected).
Fix the PR body sentence, and either cap replacing-import targets or file an issue.
