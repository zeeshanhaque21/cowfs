## 1. Does the injection hide a real cowfs defect

Guard as written: bench/pjdfstest.py PATH_MAX_SUPPLY is `[ "${path_max}" -gt 0 ] 2>/dev/null || path_max=<native>`.
It fires for -1, empty, 0 and any non-numeric output, not only EINVAL.
It is not restricted to "NAME_MAX answers while PATH_MAX does not".
The unit test test_injected_line_only_changes_an_arm_that_cannot_answer confirms the breadth (-1, empty, 0 all replaced).

What stays safe:
- NAME_MAX is read separately in misc.sh (lines 138 and 147) and is not touched, so a NAME_MAX failure still produces empty names and visible failures.
- A positive but wrong cowfs PATH_MAX is not replaced, so the case builds a differently sized path and is compared against native as before.
- Any new ordinal-worse position still lands in accepted_reasons as an uncovered DIVERGENCE (pjdfstest.py:1112) because the #108 rule and entries are gone.
- The fallback only touches PATH_MAX, which the NFSv3 PATHCONF reply cannot carry (docs/verification/evidence/nfs108-pathconf.md), so the defect class it hides is "client could not answer PATH_MAX".
- On Linux the pinned tests/conf supports only Darwin and FreeBSD in get_mountpoint, and glibc answers PATH_MAX as a constant, so the Linux FUSE scenario is not a live g3 path today.

The gap (note, not block): suite_input records both arms' PC_PATH_MAX and PC_NAME_MAX answers in identity.json (pjdfstest.py:1650), but grep shows no reader of "suite_input" in verdict().
A cowfs arm that answers 0 or -1 for PATH_MAX for any reason now gets native's value and the 13 cases pass, with only a receipt line and the still-printed stderr `pathconf returned -1` as trace.
Concrete case: the cowfs client answers (None, ENOTSUP) for PATH_MAX after some future regression; the 13 cases compare equal and the verdict is unchanged.

Recommendation, no scope expansion: add one verdict check that the cowfs PC_PATH_MAX answer is either equal to native's, or errno EINVAL with a positive NAME_MAX equal to native's.
Any other shape should yield UNMEASURABLE (or INVALID) naming the receipt.
That narrows the fallback to the exact known condition without touching the shell injection.

## 2. Overlay mechanics

Verified by running real code, not just reading.
I built the pinned tool, built an overlay with build_suite_overlay, and ran chmod/03, open/03, rename/02, mkdir/03 and link/03 through a wrapper binary that answers -1 for `pathconf . _PC_PATH_MAX` (the macOS client behaviour).
- Overlay: 5/0, 4/0, 6/0, 3/0, 13/0 ok/not ok, all pass.
- Same pinned tree plus the same wrapper, no overlay: 0/5, 0/4, 1/5, 0/3, 0/13, with `cut: [-bcf] list` errors. That reproduces #218 and shows the injection is what fixes it.
- `git status --porcelain` on the pinned checkout is empty after the run. verify_tool_source (pjdfstest.py:400) only hashes pjdfstest.c and the case files and checks git cleanliness, so it still holds.
- Group directories are real directories of symlinks, so `dirname $0` resolves to the overlay and misc.sh sourced from `$dir/../misc.sh` is the overlay's. This is exercised for all five cases above, not only the 13 named, and misc.sh's `maindir` walk finds the `pjdfstest` symlink at the overlay root.
- The overlay is rebuilt per run at run_dir/suite. build_suite_overlay does `tests.mkdir(parents=True)` with no exist_ok, so a stale overlay inside one run_dir fails loudly instead of being reused. run_dir is per run, so nothing survives across runs.
- The patch refuses to proceed unless PATH_MAX_READ occurs exactly once in misc.sh (tested), so an upstream change cannot silently skip the injection.
- Minor: only one level of group directory is symlinked per file. The pinned layout has none deeper, and a deeper entry would be a directory symlink that still works because only `../misc.sh` matters.

## 5. Verdict claim

open/17.t #2 is an established regression (#204), scored by the established-regression rule at pjdfstest.py:1256 and never waived by the list (docstring at 1097, module header lines 22 to 25).
So g3 cannot go green until #204 is fixed or deliberately classified.
The list entry for #204 only keeps the ordinal position on record.

Recommendation, not a change request: leave g3 FAIL while #204 is open.
If Zee wants a green g3 with #204 as a known limit, add a separate accepted-established-regression class that needs an explicit named sign-off record (issue number, date, who accepted) in the JSON, reported as its own COVERAGE line and never reducing the exit code silently.
It should fail when the signature no longer matches, like the existing list.
Do not reuse the ordinal-position list for this.
