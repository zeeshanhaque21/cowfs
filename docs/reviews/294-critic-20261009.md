## Findings
1. MEDIUM, correctness. The caveat in the body understates the hazard.
   CowNfs::run uses spawn_blocking, so a cancelled non-idempotent call (REMOVE, RENAME, CREATE, MKDIR, SETATTR, LINK) keeps running and may still complete after JUKEBOX was sent.
   The reply is then not cached, so the client retry re-executes it.
   Result A: the retry hits the already-applied change and returns NOENT or EXIST to the user although the operation succeeded (rename/remove).
   Result B: if the original is still blocked, the retry runs concurrently with it, two copies of one mutation in flight.
   This is strictly better than hanging forever, but the reply-cache exactly-once guarantee is knowingly broken for these procs after 45 s.
   Fix: document this in the Limits::handler_timeout doc comment and in docs, or keep the cache entry InProgress until the blocking task really ends (needs the join handle surfaced).
2. LOW, test gap. No test for a legitimately slow handler that finishes after the timeout then the retry (the exact hazard in finding 1).
   a_slow_handler_under_the_watchdog_is_untouched only checks fast calls, so it does not test slowness at all (name overclaims).
   Fix: rename, or make the HangVfs delay a fixed time under the timeout.
3. LOW, config. handler_timeout is not wired to any daemon flag or env, and nothing asserts handler_timeout < reply_cache_age (60 s) when a caller overrides Limits.
   Fix: debug_assert or clamp in the listener.
4. LOW, ops. Large legitimate WRITE/COMMIT/fsync or READ over 45 s on a stalled disk now returns JUKEBOX, then the client retries and re-issues the same heavy I/O.
   Acceptable, but note in PR.
5. NIT. NULL (proc 0) in the table maps to 0 words with a JUKEBOX status, harmless but NULL has no status field.
   The hang.rs helper is 118 lines of passthrough boilerplate; fine.
