## Attack results

1. Crash points.
   - Faults 1..5 matrix (k1): after each step and after reopen, exactly 2 snapshots exist (base, src), no hidden leftover, src id unchanged.
     Steps 1..3: base keeps old id 1 and old content.
     Steps 4 and 5: base id 3 (one fork spent: ids 1,2 then 3), new content, the id the staged fork got.
   - Hand-built images (meta layer, then plant the intent file, reopen):
     victim gone + staged present + intent (k5): base is the staged id, new content, 2 snapshots.
     both base and staged present + intent (k6): old base kept, staged dropped, intent removed.
   - Stale intent after the rename, three variants:
     target recreated by the user in the gap with other content (k2): the user snapshot is kept, intent dropped.
     a hidden snapshot with the same staging name re-created (k3): it is dropped, target kept, intent dropped.
     target removed by the user (k4): nothing resurrected, no panic, intent dropped, a later promote works.
   - Real kill -9 loop (k9): a child process runs remove src / create src / write / promote_base in a loop and the parent SIGKILLs it at random moments (150 to 400 ms).
     500 total rounds (400 + 100) plus the first 150-round run: base always present, exactly one base, no hidden snapshot, no intent file left, `check()` clean.
     Acked generation counts per round ranged about 4 to 19, so kills landed across many promotes.
2. Rename semantics (k7).
   - Root lookup by name after a swap gives a fresh root ino and the new content.
   - A promote with a file open in the old target returns Busy and leaves the old base intact (victim removal refused, rollback).
   - A second promote after release lands the new tree; a write through the root path after the swap lands in the new base, not in src, and survives reopen.
   - The staged snapshot's id is new, never the old target's id, so any id-keyed cache that saw the old target sees a different id.
3. move_name vs old rename logic.
   `git diff` shows the body moved verbatim: meta rename, snapshot_by_id, by_name remove/insert, root_time, entry.
   Validation (validate_snapshot_name, old == new, check_new_name_except) stays in `rename_snapshot` before the call, so its behaviour is unchanged for callers (daemon backend.rs rename, ctl).
   Checked live (k8): rename to a 255-byte name ok, back ok; rename onto an existing name gives Exists; rename to self and to a reserved name are refused; promote to a 241-byte name ok.
4. PR 268 torn-intent roll-forward: it calls `finish_swap(&staged, &name)`, so it now renames too.
   Same semantics (target absent: staged becomes target; target present: staged dropped).
   The existing `a_torn_intent_*` and hash-collision tests pass unchanged.
5. Promote keeps the source: src id unchanged after two promotes, promote of a promoted snapshot (base -> b2 -> base) works, promote onto itself and from a missing source are refused with the old base intact, second promote spends exactly one more id.
6. Lock-audit table: `--check` passes; the diff only swaps the `rename_snapshot` row for `move_name` and drops the `finish_swap` row (it no longer takes a snapshot lock itself).
7. PR body honesty: the claims match what I measured (one fork per promote, no test deleted, counts 16->18 and 5->5, still two commits for remove-old plus rename-new with the intent covering the gap, D13 deferred, not closing #42).
