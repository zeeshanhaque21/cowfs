# Gate g4 status, 2026-10-09: mounted fsx, cowfs vs native, with fallocate coverage

Issue: 103 (fallocate), gate harness PR 102.
Host: the cachyos box, kernel 7.2.8-2-cachyos, native arm on btrfs, under `/mnt/docs/Projects/cowfs-g4`.
Tree: a clean checkout of `origin/main` at `9c32468143ddad93b1c95be71e9b6e3b13d0f949`, shipped by `git bundle`.
No root and no sudo were used.
FUSE mounted unprivileged (`/dev/fuse` is mode 666).

## Verdict

Every compared case passed: 18 of 18 seed pairs, 36 case executions, stream and data byte-identical on both arms.
This includes the fallocate family (allocate, keep-size, punch, zero-range, write-zeroes) that was UNMEASURABLE before.
Nothing diverged, so there is no unexplained divergence and no cowfs defect found by this run.
Two caveats limit the claim and are listed at the end (native arm is btrfs not ext4, and a local config variant was used).

## What the gate measures and the bar

The gate runs one pinned fsx binary on two arms with the same seed and operation count.
The native arm is a directory on a native filesystem.
The cowfs arm is a directory on a real FUSE mount of cowfs served by a private daemon on the Core backend.
The bar is "no worse than native": both arms exit 0, execute the declared operation count, record the same operation stream, and end with byte-identical data.
A fresh process must read the same sha256 after fsx exits.
After the daemon restarts on the same store, every cowfs data file must still hash the same.
The runner attests arm identity from the kernel (st_dev differs, fstype is `fuse.cowfs`, daemon pid and backend recorded).
An empty or missing result never passes.

## What was proven before

PR 102 landed the harness and its mutation and exit-taxonomy controls.
The independent reviews are `docs/reviews/mounted-fsx-g4-final.md` and `docs/reviews/mounted-fsx-g4-repair-final.md`.
They reproduced the matched subset on a private mount and closed the false-PASS findings (arm identity, restart generation, case directory reuse, binary pin).
The matched modes then disabled the whole fallocate family on both arms, so that only read, write, mmap and truncate were compared.

## What blocked it

The FUSE adapter answered ENOTSUP to every fallocate mode, 75 of 75 matrix rows, where ext4 answered ok.
fsx therefore recorded `skip fallocate` on the cowfs arm and `fallocate` on the native arm.
The `full` mode could not pass, and hole coverage (punch, zero-range, keep-size) was never measured on the mount.

## What is covered now

Core fallocate (PR 198), the FUSE mapping (PR 203) and EFBIG (PR 195) are merged.
The Core backend through `cowfs-fuse` is what ran.
PathVfs fallocate (issue 103 slice D) is not merged and was not exercised.

## Expected difference, not a regression

cowfs punches on ZERO_RANGE where a preallocating filesystem keeps its blocks (`docs/fallocate-103.md`).
A direct check on a 64 KiB written file, zero-range of 32 KiB at 8 KiB: native btrfs `st_blocks` 128 to 128, cowfs 128 to 64.
fsx does not compare block counts, so the gate cannot see this, and the doc already marks it expected.

## Caveats

1. The native arm is btrfs, not ext4, because that is the only filesystem available unprivileged on the box.
   btrfs has no collapse-range or insert-range, so fsx disabled them on both arms and `full` became comparable.
   On an ext4 native arm, collapse and insert would exist natively and ENOTSUP on cowfs, and `full` would again be UNMEASURABLE for that reason.
   Creating an ext4 loop mount needs root, which this run did not use.
2. The fsx binary built here has a different digest from the manifest (`dc93eda7...`), as the manifest's `rebuild_note` predicts for another toolchain.
   The run used a config copy `fsx-gate-g4.json` on the box that differs from the committed `fsx-gate.json` in three ways: `expected_binary_sha256` set to this build, the `caps` byte budget raised from 3932160 to 4718592 per arm (and 9437184 for both), and one added mode `falloc` (flags `-f -C -I -u`, seeds 1,2,3, 10000 ops, required ops include punch_hole and zero_range).
   The committed config and harness were not edited.

## Follow-ups (text only, no issues filed)

- Add a committed fallocate mode (`-f -C -I -u`) with a declared tolerance for collapse, insert and unshare, so hole coverage is a standing part of the matrix.
- Make the binary pin accept a per-host digest recorded from a verified source build, instead of requiring a config copy.
- Record `st_blocks` after each fallocate in `fallocate-matrix.py`, so the ZERO_RANGE block difference is visible rather than only documented.
- Re-run with an ext4 native arm when a root-run loop mount is approved, to measure the collapse and insert gap honestly.
- Re-run after PathVfs fallocate (slice D) merges to cover that backend.
