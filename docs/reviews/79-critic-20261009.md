## 2. Production change (crates/cowfs-ctl/src/server.rs)

Diff read in full against merge base bc3ea7d (+172 -9).
Mechanism: `begin_shutdown` fixes two instants once, `abandon = now + shutdown_deadline` and `grace_end = abandon + drain_deadline`.
At the first accept-loop pass after `abandon`, one worker per straggler connection runs `abandon_inflight()` then `kill()`.
The accept thread waits for the workers by `recv_timeout` until `grace_end`, then calls `kill()` on every straggler, then waits (spin with `yield_now`, bounded by `grace_end`) for the workers and for `conns` to empty.
Findings:
- Bounded wait: every wait is capped by the single absolute `grace_end`.
  Measured on the head: beyond-grace test `wait_ms=450` for a 200 ms deadline and 250 ms grace.
  So the total is deadline + grace, as documented in the PR, and no wait restarts the budget.
- Client that never resumes: its worker parks on `write_lock` behind the progress write.
  At `grace_end` `kill()` does `shutdown(Write)`, which aborts the blocked `write_all`, and `wait()` returns at about 450 ms.
  Base took 4697 ms in the same scenario (section 3).
- No frame loss for a client that resumes inside the grace: the blocked progress write completes, the worker takes the lock, writes the terminal, then kills.
  `kill()` is `shutdown(Write)` after the write, so the frame precedes the EOF.
  Mutation checks in section 4 show the delivery tests fail when this is broken.
- No double delivery of the terminal frame: `Conn::finish` removes the id from `inflight` under the map lock and returns if it was already gone.
  The worker and the handler therefore cannot both write a terminal.
- Half-close: truncation of a frame still being written at `grace_end` is the intended "abandoned" semantics and is documented in the code and the test comments.
  The tests count only complete lines, so a truncated frame is not counted as delivered.
- Memory: the handler's progress callback is synchronous, so at most one encoded frame per connection is pending server-side.
  Workers are bounded by `max_connections`.
  The 1 MiB-per-line backlog is kernel buffer plus one frame, not an unbounded queue.
- Spawn failure of a worker falls back to `best_effort_abandon` with a write timeout equal to the remaining grace, so the accept thread cannot be parked for `write_timeout`.
Base behavior for contrast: the accept thread itself called `abandon_inflight()`, which blocks on the write lock held by a blocked progress write, for up to `write_timeout` (30 s default).
This was the actual bug of issue 77, and the PR fixes it.

## 4. a4 change and mutation checks

Final a4 shape: `(250 ms, required)` and `(400 ms, optional)`.
Each attempt measures `resumed` from just before `shutdown()`, so it is never later than the server's own start.
So `resumed < 450 ms` is a conservative proof that the resume was inside the server's window.
An attempt that resumed at or after 450 ms is discarded, up to 5 attempts.
The 250 ms case fails the test if all 5 attempts are late, and hard-fails on any on-time attempt that does not get `Ending::Response`.
The 400 ms case is asserted only when an on-time attempt exists.
Mutation 1 (scratch clone of head, `release_start = Instant::now()` so the kill runs at once and the frame is dropped for a client that resumes after the deadline):
- 250 ms case FAILS: `ending=NoFrame resumed_at=251ms`, panic at admission.rs:419.
- So the always-asserted 250 ms case does catch "resumed-after-deadline clients get no frame".
Mutation 2 (the earlier half-split, `release_start = grace_end - drain/2`, cut at 325 ms):
- a4 250 ms case PASSES (resume is before the cut), so 250 ms alone cannot catch a half-split.
- a4 400 ms case FAILS locally (`resumed_at=403ms ending=NoFrame`), but on the macOS runner that case resumes at 453..547 ms, is discarded, and asserts nothing.
- progress_shutdown `a_client_resuming_late_inside_the_full_grace_gets_a_whole_frame` FAILS on the half-split (`window700/resume480 ... whole_terminal=false`).
  That test runs in the hosted check jobs and is the hosted guard for the half-split class.
Plain statement: the final a4 change is an invariant for the property "a client that resumes after the deadline but well inside the grace gets one whole frame", with 200 ms of slack, and the test can fail (mutation 1).
It is not just a larger margin, because the late attempts are discarded by a measurement instead of by a bigger sleep, and the asserted point is separate from the edge probe.
The edge (400 ms) is only a local probe and is not a hosted gate.
The half-split class is guarded in CI by progress_shutdown, not by a4.

## 7. Notes

Blocking: none.
Non-blocking, in priority order:
1. `drain_and_close` change is wider than the PR states.
   It now skips the read-away loop when `dead` is set, but the only caller (server.rs:609-610) calls `conn.kill()` immediately before `drain_and_close`, so `dead` is always true there.
   The drain is therefore disabled on every connection teardown, not only after a shutdown kill.
   docs/v1-control-api.md says every close after an error reply "read[s] away what the peer already sent, then close[s]", and `reject_oversized` says its drain exists so a close does not reset the connection and destroy the error frame.
   I could not make it lose a frame: on this macOS a frame written before the close survived a close with 5000 unread bytes (python AF_UNIX probe), and the hosted Linux jobs are green.
   It is still an untested, undeclared behavior change; scope the skip to `shared.abandoned()` or add a test.
2. Possible ordering race: after the worker writes the terminal and before its `kill()`, the handler can still emit a progress frame for the same id, because `finish` removes the id before `dead` is set.
   The tests assert no second terminal but not "no progress after the terminal".
3. a4's 400 ms probe is invisible on hosted runs (no `--nocapture`), so it is unknown whether it ever asserts in CI; consider logging asserted or skipped unconditionally.
4. Update the PR body (items in section 6), the wait() doc comment and docs/v1-control-api.md for the deadline-plus-grace bound, and sync or rebase with main before merge.
5. The 5-attempt discard loop in a4 can mask a persistently starved runner only as a failure of the required 250 ms case, which is the intended behavior; no change needed.
