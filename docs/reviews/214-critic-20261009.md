## 1. chmod fix

Fix is at crates/cowfs-vfs-path/src/sys.rs:239-250: `libc::fchmodat(..., AT_SYMLINK_NOFOLLOW)`.
Linux with a planted symlink: glibc (emulation, or fchmodat2 on newer kernels) and musl return ENOTSUP/EOPNOTSUPP for a symlink, or act on the link inode.
Either way the target is never chmod'ed.
The error goes through `map_err(io_err)` at lib.rs:305 (mknod) and lib.rs:215 (setattr), so the caller gets a clean error.
The test (tests.rs:866-880) discards the result with `let _ =` and asserts only that the target mode stays 0o644.
That is the right invariant, and it holds for both the error outcome and the change-the-link outcome.
CI evidence: `cowfs-vfs-path tests::fchmodat_by_name_never_follows_a_symlink` PASS in job "test (ubuntu-latest, 2, 2)" (log line 1221).
`setattr_mode_on_a_special_node_never_lands_on_a_swapped_in_symlink_target` PASS in "test (ubuntu-latest, 1, 2)" (log line 1248).
macOS job is green too.
linux-fuse is green (25/25 and 150-run conformance), so the 16 FUSE mknod checks still pass with the flag change.
The glibc emulation opens the name with O_PATH|O_NOFOLLOW, then chmods via /proc/self/fd.
For a fifo or socket that works, which is why mknod still passes.
It needs /proc mounted, but `chmod_fd` (sys.rs:255) already has that dependency.
macOS: the link itself is chmod'ed.
That is acceptable because macOS PathVfs has no mknod and no special-node open (O_PATH is unavailable), so the macOS path is effectively only reachable from the test.
Note: the Linux test only proves "target untouched".
It does not assert which errno came back.
That is fine, but it means ENOTSUP behaviour is observed rather than pinned.

## 3. devices_need_privilege and is_root

Code: crates/cowfs-vfs-test/src/conformance/special.rs:21-24 and 43-45.
Plus runner.rs:209-213 (option, default false) and the two consumers (tests/common/mod.rs:57 and cowfs-fuse/tests/conformance.rs:72).
MemVfs and Core leave it false, so a PermissionDenied for a device there now fails via `Err(e) => Err(e.into())`.
The CI memvfs and core conformance runs are green, so neither answers PermissionDenied today.
Notes on `is_root`:
- Owner of /proc/self is the process euid only when the process is dumpable. A non-dumpable process (setuid binary, PR_SET_DUMPABLE 0) shows root:root, so is_root would be true for a non-root run. Effect: a legitimate PermissionDenied then fails the test (fails loud, not a false green).
- User namespace with uid 0 mapped but no CAP_MKNOD (for example `unshare -r`): /proc/self is owned by 0 in the namespace, so is_root is true, the device mknod gets EPERM, and the check fails although this is the expected unprivileged outcome. The linux-namespaces job (ci.yml:116-123) uses `unshare --user --map-root-user` but did not trip this, so it evidently does not run a PathVfs or FUSE suite that way. A latent false red, not a false green.
- Real root in a container without CAP_MKNOD: same failure mode. Probing for CAP_MKNOD, or simply keying only on the EPERM answer, would be more accurate than a uid heuristic.
- /proc unmounted or macOS: metadata fails, is_root is false, fallback to fifo and socket is allowed. Safe for both, since PathVfs skips on macOS anyway.
No false green found: every misclassification path ends in a failure, not a skipped device check.
Severity: low.

## 4. ctime >= mtime (special.rs:71-75)

Non-flaky.
Fresh node: mknodat sets atime, mtime and ctime from one kernel timestamp.
fchmodat only moves ctime forward.
Both stamps come from the same clock source in MemVfs, Core and the kernel, and mtime is not touched after creation.
The only way to violate it is a backward wall-clock step between the two calls, which is the same exposure as the existing `atime == mtime` check.
The comparison is `>=`, so equal coarse timestamps are fine.
CI passed on all three platforms.

## 5. Residual race

Disclosed accurately in the PR body: a swap to another non-symlink special node between mknodat and chmod still lands on that node.
It is not worse than before: previously a swap to a symlink also followed to any target, and now only swaps to special nodes remain.
The glibc emulation does not close it either, because it opens by name before chmod via the fd.
The honest follow-up (fd-based chmod plus a dev/ino check) is listed in the PR body.
Inside PathVfs's own use the window needs a concurrent writer to the backing directory, which PathVfs treats as untrusted, so it should stay tracked in #211.
