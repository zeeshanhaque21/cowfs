# PR 240 critic (refs #101): pinned unprivileged xfstests helper build

Head reviewed: 61e74947ce70ea76255c6eaeeacb0a1fc7966918 (branch feat/g5-tools-101), parent fb64023.
Reviewed from a plain scratch clone with refs/pull/240/head fetched; no treehouse lease, nothing edited, merged or pushed.
Diff vs parent: bench/xfstests_build.sh, bench/test_xfstests_build.py, 2 lines in bench/g5_root.sh, docs/reviews/g5-tools-101-20261009.md and 4 evidence files.

## Verdict

BLOCK, with a one-line fix.

The pre-build "dirty tree" refusal uses `git status --porcelain`, which does not report ignored files.
In the pinned xfstests tree every build output and every configure product is gitignored.
`git check-ignore -v` at 3e1ee800 shows `/ltp/fsstress` (.gitignore:51), `/ltp/fsx` (:52), `/include/config.h` (:38), `/include/builddefs` (:37), `/tests/*/group.list` (:15) and `/configure` (:20).
So a present XFS_DIR at the right commit, carrying stale or hand-made outputs, passes every refusal.
A make that does nothing then passes the post-build checks too, because lines 45 to 50 only test that the files exist and are executable, not that this run produced them.
The identity file then records digests of binaries this run did not build, under a recipe that claims the suite's own make with unmodified flags.

This is the documented path, not a contrived one.
The script header (lines 7 and 8) supports a present XFS_DIR.
The review doc says to run the recipe at `$G5_W/ref/xfstests`, and says that tree already holds an Oct 8 build.
A leftover hand-written `include/config.h`, the approach issue 101 declined, would be invisible to the dirty check in the same way.

### Counterexample (run)

Setup: a fresh depth-1 fetch of 3e1ee800 (rev-parse HEAD and HEAD^{tree} match both pins), copied to a scratch dir.
Planted: `ltp/fsx`, `ltp/fsstress` (executable fakes), `tests/generic/group.list`, `include/builddefs`, `include/config.h`.
`git status --porcelain` printed nothing.
`git status --porcelain --ignored` printed all five planted files as `!!`.
Ran lines 1 to 52 of the script (every refusal, the make and every post-build check) with `make` on PATH resolved to `/usr/bin/true`, standing in for a make that finds its targets up to date.
Result: rc=0.
A run of the full script with the same setup got past line 52 and was executing the planted `ltp/fsx` for the smoke.
I could not finish the smoke step on this Mac: macOS provenance or Gatekeeper hangs the first direct exec of a freshly written script in the scratch dir, and the same fake runs fine via `bash ltp/fsx`.
Faking the smoke output is trivial anyway (fsx needs one grep line, fsstress needs one `0/N: ` line), and in the realistic case the stale binaries are real helpers that pass the smoke honestly.

### Fix

Before the build, refuse unless `git -C "$XFS" status --porcelain --ignored` is empty (or `git clean -ndx` prints nothing).
Put this check before the commit check, so a unit test can cover it offline: seed a repo with a .gitignore and a planted ignored file, and expect a refusal before make.
Trade-off to state in the header: a second run in the same directory is refused until `git clean -fdx`, which is the point.

## Check 1: pin enforcement

The commit pin is read from the allowlist's `tree_sha` line (sed on `^tree_sha [0-9a-f]{40}$`), and an empty result is refused.
Two `tree_sha` lines would join into a value with a newline in it, which then fails the comparison, so that case also refuses.
After the fetch, `rev-parse HEAD` must equal the commit and `rev-parse HEAD^{tree}` must equal 3683cb11c7dde850a567042e89b4e35e5d082b8e, so the checks run against real objects, not names.
I confirmed both ids on a real fetch from kernel.org.
The fetch goes to `origin`, which is `XFSTESTS_UPSTREAM` or else the kernel.org https URL.
The override has no allowlist, but that is safe: git verifies object hashes in index-pack, and the post-fetch rev-parse binds the content to the commit id.
There is no mirror fallback, and make runs only after all three checks.
The tree check is redundant by construction, because the commit id already covers the tree.
SHA-1 (git uses hardened SHA-1DC) is fine for pinning a third-party commit, since that needs a second preimage, not a collision.

Refusal tests: `python3 -I bench/test_xfstests_build.py -v` gives 5 tests OK.
Mutation results:
- Replacing the commit check (line 29) with `:` makes test_present_tree_at_another_commit_is_refused_before_make FAIL, so the commit refusal is exercised.
- Replacing the tree check (line 31) with `:` leaves all 5 passing. This is acceptable because the check is redundant.
- Replacing the pre-build dirty check (line 33) with `:` leaves all 5 passing. No test covers the dirty refusal at all, and that is the gap the counterexample exploits.

A failed fetch leaves an initialized `XFS_DIR/.git` with no HEAD.
A rerun then dies at `rev-parse HEAD` with git's own fatal message.
That is still a refusal, but an unfriendly one, and the operator has to delete the directory by hand.

## Check 2: shell safety

The script uses `set -eu`, not pipefail.
That is acceptable here: with pipefail, the `grep -o` on line 60 would abort with status 1 before the friendly "logged no ops" refusal.
Every expansion of `$XFS` is quoted, and `mktemp -d "$XFS.smoke.XXXXXX"` and `rm -rf -- "$sm"` handle spaces.
There is no sudo.
The only network access is the pinned fetch.
There is no trap, so on a failed smoke the `$XFS.smoke.*` dir is left behind.
Writes land next to XFS_DIR, not inside it: `$XFS.build.log`, `$XFS.smoke.XXXXXX/`, `$XFS.smoke-fsx.txt`, `$XFS.smoke-fsstress.txt` and `$XFS.identity.txt`.
The header documents only the identity file.
shellcheck reports only SC1083 on the unquoted `HEAD^{tree}`.
That is harmless in bash, since there is no comma or `..`, but quoting it costs nothing.

## Check 3: make -k honesty and the smoke bar

`make_rc` and `make_failed_targets` are recorded.
The evidence identity shows `make_rc=2` and `make_failed_targets=default locktest src`, and build-errors.txt shows compile errors only in locktest.c (`struct delegation` has no member `d_type`).
So "only src/locktest fails" is consistent with the evidence, and `default` and `src` are recursion parents.
The script never refuses on `make_rc`, by design.
On a fresh tree a failed helper cannot be reported as success, because the binary is absent and the `-s` check fires.
On a present tree with stale binaries (the blocking finding), a failed `ltp` rebuild would be reported as success, with only `make_failed_targets` hinting at it.
The smokes run under `set -e`, so a non-zero rc from fsx or fsstress aborts the script.
The fsstress bar is "more than 0 distinct `0/N: ` lines".
The evidence logged 45 of 50.
The missing ops are 20, 27, 36, 37 and 38.
Only 27 is explained by the doc's "btrfs-only ops print otherwise" (`0:27: subvol_delete - no subvolume`), and the other 4 print nothing.
A floor of more than 0 rejects a true no-op but accepts a 1-op run, so a floor of half of `-n` would cost nothing.
This is a note, not a blocker.

## Check 4: the g5_root.sh additions

Both lines are additive and sit inside the existing meta block.
g5_root.sh runs with `set -u` only (line 10), so a missing helper yields `fsstress_sha256=` with an empty value plus a sha256sum error on stderr, and the run continues.
This is the same pattern as the existing `check_sha256` and `cowfs_bin_sha256` lines.
`g5_diff.py` `parse_identity` reads plain `key=value`, and `build_receipt` requires only `tree_head`, `check_sha256` and `cowfs_profile`, so verdicts are unchanged.
The key names match the identity file exactly, and test_g5_meta_records_the_helper_digests_under_the_same_keys asserts the identical `echo` literal in both files.
The same ignored-file blind spot exists in g5_root.sh's `tree_porcelain` and in g5_diff's clean-tree check.
That is pre-existing, out of scope here, and worth one line in the follow-up.

## Check 5: path dependence of the digests

This is stated clearly in the script header (lines 10 and 11) and in the review doc section "Digests, and why they are per host and per path".
The doc says outright that the PR-run digests (37b4976f..., a3c50f07...) are not what a harness run sees, and names the Oct 8 harness-tree digests (9bfa06b0..., d1ab6fa4...).
Nobody should pin the wrong digest from this text.
The doc's `grep -cFx` proof only shows that meta matches identity; it does not show the recipe built the helpers.
The blocking finding closes that gap.
