## (2) Validity logic: shared and sound

I read the whole driver. Diff against main removes only the macOS-specific literals and replaces them with `is_cowfs_mount`, `cowfs_kind`, `linux` parameters. Nothing weakens a shared refusal.

- Profile check: `build_release` and `profile_problems` run on both platforms before the daemon is built into `Daemon`. No Linux branch skips them.
- Digest: `arm_problems(... digest_problems(self.bin, self.sha))` is on the shared path, called in `pre` and `post` for every cowfs arm.
- Minimums and `param_problems`: run before `run()` on both platforms. `--sample` relaxation is unchanged.
- Arm identity: `is_cowfs_mount` is exact (`fuse.cowfs` and source `cowfs`). `mount_entry` takes the longest mount point containing the resolved path. The macOS branch is stricter than before, not looser (`startswith("localhost:/cowfs-")` and `nfs`).
  - Another FUSE mount cannot satisfy it unless its fsname is literally `cowfs` and it contains the private mountpoint.
  - A native dir fails (kind is `btrfs`). A stale mount at the exact path is impossible: `out.mkdir` and `mnt.mkdir` are exclusive and a repeated run id is refused.
  - st_dev must also differ from the native root, and the daemon must be alive.
  - Residual: a stale cowfs FUSE mount at a parent directory of the new mountpoint would match by longest prefix. Far-fetched, since the new directories would live inside that FS.
- `/proc` foreign CPU:
  - Identity: `delta_rows` keys on pid and starttime (field 22; indexing in `parse_pid_stat` checked against proc(5): utime/stime are `rest[11]`/`rest[12]`, starttime `rest[19]`). A reused pid counts all its ticks. comm may change. Correct.
  - Units: `100 * delta_ticks / SC_CLK_TCK / dt` with measured dt. Percent of one core, not divided by CPU count, which matches ps pcpu on macOS (also per core, can exceed 100). The "points" are comparable in unit, not in meaning (1 s delta against decaying average), and the doc says so.
  - Threads: the process-level stat already sums all threads. `/proc/[0-9]*` lists thread-group leaders only. Zombies are included with their ticks. Fine.
  - Own-tree exclusion: ppid walk from the driver pid and daemon pid over rows from the same snapshot. Orphans reparented to init (a daemonised child of the build) would count as foreign; conservative.
  - Kernel threads: children of kthreadd are counted as foreign unless their comm matches the induced prefixes.
  - Bad read: per-pid `OSError/ValueError/IndexError` is skipped (vanished pid). A bad `/proc/stat` raises, and `main` turns any exception into INVALID with exit 2, so it does not silently pass.
  - `/proc` on the box is `proc ... (rw,nosuid,nodev,noexec,relatime)`, no `hidepid`, so other users' processes (CI runner, desktop) are visible. Checked over ssh.
  - Baseline is measured with the same sampler (`window(..., [os.getpid()])`), limit = p95 + 50, refused above 100. Same rule as macOS.
- Path guard: `linux_path_problems` is textual (`os.path.abspath`), tested against `..`, a sibling prefix (`-evil`) and an outside path. It does not resolve symlinks, so a symlink inside the base pointing out would pass. This is a footgun guard, not a security boundary, and nothing in the base is a symlink. Non-blocking.
- `stop()`: SIGTERM only after an argv check that the pid runs the built binary; then `fusermount3 -u <exact mountpoint>` only when `cowfs_mounted(self.mnt)` is true; no `-z`, no `-f`, no `pkill`, no shell. A non-mountpoint path makes fusermount3 fail harmlessly. The table is re-read and a remaining mount is a recorded problem. Socket and its `.lock` removed only after. Safe.
- Lock: same atomic-rename stale-lock code as macOS, now at `<base>/cpu.lock`. Not shared with the CI runners (admitted in the doc).

## Harness g2 at 0.11 to 0.36 s: my explanation

- Workload (`bench/gates.py` `g2`): append a comment line to `crates/cowfs-vfs-path/src/cookies.rs` in the pinned clone, then `cargo build --offline --locked -j 4` on a warm dev-profile target dir.
- A comment-only edit changes no API. On the box, `lsample3/native/corpus-target/debug/deps` shows the evidence. After the g2 rep (ts 09.18 to 09.35) the only rewritten artifacts are `cowfs_vfs_path-*.d` (09.307) and `libcowfs_vfs_path-*.rlib` (09.342), plus the unit `.d` stubs. `libcowfs_fuse-*.rlib` is still 06.7 and the crate rmeta files were not rewritten. No downstream crate or binary was rebuilt or relinked.
- So g2 measures: cargo's freshness scan of the workspace plus one incremental rustc run of one library crate. Native 0.11 to 0.13 s; cowfs 0.30 to 0.36 s. The difference is about 0.2 s, mostly stat and read latency through FUSE on a metadata-heavy scan, which is exactly why the ratio is 2.7 to 2.8x.
- The comment in `bench/gates.py` ("nothing in the workspace depends on cowfs-vfs-path ... everything downstream of the vfs trait rebuilds behind it") is false: ctl, daemon, fuse, gc and nfs depend on it, and nothing downstream rebuilds on a comment edit. That comment is not in this PR.
- Implication for the bar: off macOS, `compare.py` gates g2 at ratio 1.5x with no added-seconds budget (the 1.0 s budget is macOS only). On a 0.1 s native workload a 0.2 s FUSE overhead is a 2x to 3x ratio, so the Linux g2 verdict will be FAIL by construction of the workload, not because rebuilds are slow. Either the tracker g1 bar on Linux needs the same added-seconds budget, or g2 needs an edit that actually propagates (a public item change in vfs-path, or an edit to a mid-graph crate). A decision for Zee; the doc should say it, not hide it.
- The note applies equally on macOS, where the budget masks it. It is "text only" for this review: gates.py is not touched here.

## Non-blocking notes

1. `INDUCED_LINUX` is a name prefix match (`kworker`, `ksoftirqd`, `kswapd`, `btrfs-`, `jbd2`, `fuse`). Any user-space process whose comm starts with `fuse` (for example `fusermount3`, `fuse-overlayfs`) or `btrfs-` would be exempt from the foreign gate. The macOS set is exact names. Restrict to kernel threads (ppid 2) and add a test that a user process named `fuse-something` is still gated.
2. `proc_snapshot` returns an empty dict if `/proc` is unreadable, which yields 0 foreign CPU and passes. Assert that the driver's own pid is in the snapshot.
3. Processes that start and exit inside the 1 s window (compiler bursts from another user) vanish from the second snapshot and are not counted. Foreign cargo/rustc/cc1/ld are only checked by `ps` at baseline and between arms, not during an arm. Same weakness class as macOS ps; mention it in the doc.
4. `/proc/stat` idle counts iowait as idle. On btrfs with an I/O-heavy foreign process this makes the idle floor easier to meet. Defensible, since the floor is relative to a baseline with the same definition, but say so.
5. `native_fs` is recorded but not gated. A guard that refuses anything other than btrfs, ext4 or xfs would stop a tmpfs native arm if the path guard is ever overridden.
6. The Blockers checklist still says "UNVALIDATED: cargo build through the release daemon mount" at the top; lsample3 ran one on Linux. Tighten the wording (macOS still unvalidated).
7. `COWFS_G12_BASE` is overridable and the guard only checks the same base it was given. That is fine for tests, but a real run should not override it.
8. The doc could drop the variable name `CACHY_OS_PASS`.
