## 284 attack results

E8 static test `dropping_the_stale_checkpoint_is_followed_by_a_directory_fsync`:
- It reads the op log of a real `acknowledge_corruption` run (`LogOp::Unlink index.cix`, next op must be a non-packs `DirSync`). It does not parse source text. Not a tautology.
- Applied mutant E8 (fsync deleted) on the box: test FAILS, the other six pass.
- Applied wrong order (fsync before the unlink): test FAILS. It requires the fsync to be the immediate next op, so it is strict, not loose.
- Resurrecting the checkpoint is harmless in the way that matters. `open` accepts a checkpoint only if every pack it names exists with length at least the recorded length and the same creation nonce, and not if the watermark fell back (`wm.uncertain()`). A missing or compacted-away pack makes `packs_ok` false and the whole checkpoint is dropped. Pack ids are never reused. `get` re-hashes the data (`BlockId::of(&data) != id`, store.rs:1280), so a stale entry can at worst return an error, never wrong bytes.
- Residual note, pre-existing and not caused by this PR: a resurrected checkpoint also masks bit rot inside the range it covers, exactly like any normal open after a checkpoint. Not a regression.

E7: mutant applied, `discard_makes_earlier_puts_durable` is the only test that fails (power_collect and crash stay green), so the kill is real and singular.

`crash_image` with `k == ops.len()`: for `k < len` the image is byte for byte unchanged (`upto = k+1`). Only `k >= len` changed, from "last op in flight" to "all ops completed". Other callers that can pass `k == len`: `tests/crash.rs` (`.min(h.ops.len())` and `rng.below(len+1)`). That sweep loses the "last op in flight" image only for the draw `k == len`, which was already inconsistent with `acked_at(&ops, k)` that counts everything acked. Full suite passes. Harmless, arguably a fix. Note it in the docs for crash.rs.

Seam script: experiment on the box. Deleting `#[cfg(feature = "fault-injection")]` on `pub mod crashmodel` gives E0432 `unresolved import crate::LogOp` on a feature-off `cargo check -p cowfs-store`. `crashmodel` is mentioned only in lib.rs in src, so no other item is reachable. Note: the gate relies on crashmodel importing `LogOp`, which is a side effect. If someone replaces that import the gate silently disappears. Acceptable, but say so in the comment.

## 285 attack results

(d) Determinism and runtime on the box: full `cargo test -p cowfs-store -p cowfs-meta -p cowfs-core -p cowfs-gc` at 4ae25e8: 100 binaries, 846 passed, 0 failed. power_discard plus power_collect three times: all green, 21-22 s wall each (power_collect about 18 s, power_discard about 3 s). Pass/fail is stable, but the recorded op count varies by one between runs (139 vs 140 ops, 1120 vs 1128 images). Cosmetic, the PR quotes the 140 run.

(a) Metadata model: the recording backend logs write, set_len and sync_data faithfully and stamps each into the store log, so ordering is one timeline. Image = base plus events up to the last completed sync_data. The gap (an unsynced redb write or a torn commit header surviving a cut) is disclosed in the PR body and docs ("Not covered"). It means the test cannot catch a redb commit-ordering fault; that lives in cowfs-meta/tests/crash.rs. Disclosure is honest.

(b) GF1/GF2 are EQUIVALENT mutants, not a model hole. Evidence:
- `Snapshot::live_blocks_with_root` begins with `inner.sync()?` (cowfs-meta/src/db.rs:2141). Every snapshot the collect walks is committed before its blocks are marked, so the explicit `meta.sync()` at the freeze and at the fresh listing are redundant with the walk's own commit.
- Removing both GF1 and GF2 still passes the sweep (run on the box). Adding to the scenario a file whose old content is overwritten in memory only, with the old block's pack actually reclaimed, and removing the test's mid hook (which itself commits via `new_snapshot`), GF1+GF2 still pass.
- Removing GF1, GF2 and the walk sync together (mid hook removed, as above) makes the sweep FAIL: 8 of 992 images, "a block of snapshot late is lost", at k=all done. So the model can see the failure; it just needs all three removed.
- Consequence: the explicit syncs are defence in depth that no test pins. The PR text "each is the other's backup" is incomplete; the real reason is db.rs:2141. Suggest saying so, and that a future change to `live_blocks_with_root` would unprotect the collector without any test failing.

(c) GA1/GA2 and the "advisory" claim:
- GA2 (no dir fsync after rename) is truly safe: the old file is a valid older state and the test covers it.
- GA1 claim is FALSE as written ("survives by design because advisory ... test already explores every state"). `mark.bin` has a magic and structural checks but NO checksum. The test's torn state is a prefix, which fails the length parse and is safe. A same-length file with a corrupted or zeroed span passes the parser and the collector then skips that root's walk and frees live blocks.
- Reproduced on the box by editing the test's `write_state`: flipping 1 to 8 bytes in `mark.bin` makes `gc_state_is_advisory` fail (seeds 4, 10, 11, 15, 18 ...: "a block of snapshot s is lost: NotFound"). Zeroing a 64 byte span inside `mark.bin` fails the same way. Flipping or zeroing `atime.bin` does not fail. 512 byte sector zeroing did not trigger only because the test's mark file is smaller than 1 KiB, a production sized file would have such sectors.
- Why it matters for power loss: with GA1 (no file fsync before rename) a legal outcome on delayed allocation filesystems is a renamed file of the right size with unwritten (zero) pages inside. The fsync is therefore load bearing, and the test cannot show it because `write_state` never builds that image.
- Production impact today: the shipped code does fsync, so power loss is fine. Bit rot or any silent corruption of `mark.bin` can cause the collector to free live blocks. This is a pre-existing robustness gap, not introduced by 285.
- Recommended: (1) soften the docs and PR body claim for GA1 and for "any mix of old/new/torn/missing is safe" to name what was actually explored; (2) add a "same length, zeroed or flipped span" state to `write_state` and keep GA1 as a killed mutant; (3) file an issue: add a CRC to `mark.bin` (a mismatch means empty, which the loader already treats as safe).

(e) PR body honesty: both say Refs, not Fixes. 284 states the daemon sweep `verify-daemon-crash.py --fault-boundary 1-60` was not re-run. 285 states the GF1/GF2 reasoning was not isolated by experiment and lists "not covered". The only overclaim is the GA1 sentence above.
