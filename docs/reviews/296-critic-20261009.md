## Findings

1. Doc inaccuracy (fix before merge). The fault table says fault 4 leaves "base is absent, intent file present".
In swap_snapshot (promote) fault 4 is only logged to last_error and the swap rolls forward and returns Ok.
Base is absent only on the replace_with_staged (import) path, where fault 4 returns Err.
Fault 5 exists only in the promote path.
Say which path each row applies to, or the table misleads the next reader.

2. Incomplete "no longer swallows" (small fix). recover_intent still has `let _ = fs::remove_file(p)` in the torn-intent branch and in the old-release `.tmp` branch. rollback() also ignores remove errors.
The PR title and body imply intent-removal errors are now reported.
Either report them the same way or state in the body that these three sites are intentionally best-effort.

3. Fault 7 test is weaker than it reads. fault(7) fires before remove_file, so the real remove_file error arm and the `Err(_) if !p.exists()` arm are never executed by a test.
The guard `!p.exists()` also hides a real error whose file happens to be gone, which is fine, but untested.
sync_dir result after removal is still ignored (pre-existing).
Acceptable for a seam-based suite. Note it, do not block on it.

4. Parent test is a characterization test. It already passes on main after PR 280 (the change came from 280), so it does not fail without this PR. The PR body does not claim otherwise. Fine.
The fault 6 and 7 tests do fail without the PR (the seam does not exist), and the assertions (intent file kept, dropped after reopen, no staging leftovers, check() clean) are meaningful.

5. Semantics note. With fault 6 the promote call returns Err although the new tree is visible. This is a crash simulation only, since fault is test-only, but the daemon would show an error for a landed swap if a real error ever occurred between rename and drop. Real drop_intent errors correctly return Ok, so there is no production path to this.

6. Concurrency (pre-existing, not introduced). drop_intent deletes swap-<target> by path with no check that the intent is the one this swap wrote. If two swaps on one target could interleave, one could remove the other's intent. I did not confirm whether a per-target lock prevents this. Not a regression of this PR.

7. last_error is a single slot. A later message overwrites the intent-removal report, so the "reported" failure can vanish quickly. Matches existing practice.
