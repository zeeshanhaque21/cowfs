## 3. Correctness and safety

### PR 194 (kill vs in-flight terminal write)

Mechanism confirmed in code on main: `finish` removes the id and does `finishing.fetch_add` before `write_frame`; `abandon_inflight` iterates only ids still in the map; `kill` (line 779) sets dead, cancels, and `shutdown(Write)` without reading `finishing`.
Both teardown callers (abandon worker, line 328; connection thread, line 607) call `abandon_inflight` then `kill`. The fix replaces both with `abandon_inflight_until(grace_end)`.
Boundedness: the only new wait is `while finishing != 0 && now < until`, a 1 ms sleep loop. `until` is `Shared::grace_end()`, read from the same `OnceLock<ShutdownDeadlines>` the accept loop uses. No new constant, no second grace.
`begin_shutdown` sets `deadlines` before it sets `stopping`, so on the connection-thread path (guarded by `stopping()`) `grace_end()` is always `Some`. The `unwrap_or_else(Instant::now)` fallback is dead code and harmless.
No deadlock: the waiter holds no lock. The awaited writer can park on `write_lock` behind a non-reading peer, but the accept loop kills every straggler at grace_end (`shutdown(Write)` aborts the blocked `write_all`), and the waiter exits at the same instant. The worker is also bounded by the accept loop's `done_rx.recv_timeout(left(grace_end))`.
No double delivery: the wait writes nothing. Terminal frames stay single-claim through `inflight.remove`.
Resumed client inside the grace: improved. Before, a queued terminal write was cut at the deadline or at shutdown start. Now it gets until grace_end.
Never-reading client: terminal frame is lost at grace_end, same as before. Half-close: `kill` still half-closes after the wait, so the order is terminal frame, then FIN.
Existing suites in my scratch clone at the 194 head: lib 12, admission 15, flood 1, progress_shutdown 13 (examples built first), regress 19, server 31, wire 20, all ok. The PR 79 tests do not change meaning.
Finding (inference, not measured): a connection whose handler has finished and whose terminal write is stuck behind a non-reading peer used to be killed at once by the connection thread and leave `conns` early. Now it holds until grace_end. With the default 5 s deadline that is up to 5.25 s of `wait()` for that one case, inside the documented budget but later than before. Delivery over latency is the intent of #127, so this is non-blocking. A probe with a non-reading peer and the default options would quantify it.
`best_effort_abandon` (spawn-failure path) keeps the kill-without-finishing shape. The status doc already records why it was left alone (accept thread must not block). Agreed.

### PR 193 (progress after terminal)

`send_progress` takes `write_lock`, then `inflight`, checks the id, then writes. `finish` removes the id under `inflight` first and writes under `write_lock` after, so a progress frame is either fully written before the terminal frame or refused. Verified by reading the code.
Lock order: `write_lock` then `inflight`. The `inflight` guard in the `if` condition is a temporary dropped before the block, so it is not held across the write. `kill` (which takes `inflight` in `cancel_all`) is called after the write-lock block ends. `best_effort_abandon` takes `inflight` then drops it before `write_lock.try_lock`. `finish` never nests them. No inverse order found.
Refusal returns false, `OpContext::progress` cancels the token and returns `cancelled`; the connection stays up. Correct for a shared connection.
A reused request id could let a stale handler's progress pass the check. That is pre-existing, outside this PR.
Narrowness is as the PR says: `cancel_all` plus `OpContext::check` stop most handlers first. The fix is cheap and removes a protocol-level hole (a frame after a terminal frame of its id). Worth merging.
Suites at the 193 head in my clone: all ok, same counts as above.

### PR 196 (drain scope)

On main, `drain_and_close` loops `while !self.dead && now < until`, and its only caller (`admit`, line 610) calls `kill()` immediately before, so the drain never ran. Confirmed by the failing-first test (5 us).
Fix: caller passes `Duration::ZERO` when `shared.abandoned()`, else `drain_deadline`; the `dead` condition is removed.
Does it bring back the unbounded drain PR 79 removed? No.
- After the shutdown deadline the duration is zero, so `until = now` and the loop does not run. The PR 79 property (close does not outlive `wait()`) is kept.
- Before the deadline a drain ends at the first read that returns 0 or an error. The socket has a 50 ms read timeout, so a silent peer ends it after about 50 ms. A peer that keeps sending ends at `drain_deadline` (250 ms by default).
- A drain started before the abandon instant ends by abandon + drain_deadline, which equals the one grace_end. So it cannot exceed the grace.
- `abandoned()` is evaluated once at the call. A drain that starts at deadline minus 1 ms runs at most 250 ms, still within grace_end.
Cost: a shutdown with a chatty peer on a stopped connection can take up to 250 ms longer than on main for that connection. This is what `v1-control-api.md` already promised for every close. Non-blocking.
Suites at the 196 head: all ok.

## 4. Interaction of the three PRs

Production hunks do not overlap: 194 touches `accept_loop` (line 328), `admit` (line 607 region) and `Conn` (`abandon_inflight_until`, `Shared::grace_end`); 193 touches `Conn::send_progress` and `run_request`; 196 touches `admit` line 610 and `drain_and_close`.
Note `admit` is touched by both 194 (`abandon_inflight_until` line) and 196 (`drain` line). Git merged them without a conflict because the lines are adjacent but distinct.
Textual conflicts: every sequential `git merge` conflicts in the test module, because all three PRs append a test at the end of `mod tests`. Order 194, 193, 196 gave two conflicts, both in the final test region. I resolved by keeping both tests (no production line involved).
Merged result in the scratch clone (194, then 193, then 196, conflicts resolved as above): `cargo test -p cowfs-ctl` lib 14 (12 plus 2 new), admission 15, flood 1, progress_shutdown 13, regress 19, server 31, wire 20, all ok. `cargo clippy -p cowfs-ctl --all-targets -- -D warnings` clean, `cargo fmt --check` clean.
Semantic interaction 194 x 196: 194 may hold the connection thread until grace_end, then `abandoned()` is true and 196 passes zero drain. This is the intended order (deliver, then close without a drain once the grace is spent). No interference found.
The merge order only changes who resolves the end-of-file test conflict. Merging 194 first keeps the real #127 fix first. Each of the others needs a trivial rebase.
