## Attack results

### 1. OnceLock caches any unshare failure, forever (note, not a block)

`with_private_umask` does `PRIVATE_UMASK.set(ok)` with `ok = unshare(CLONE_FS) == 0`, with no errno inspection.
Every failure (EPERM from seccomp, but also ENOMEM or EAGAIN) is cached as permanent refusal.
Reproduced with an LD_PRELOAD shim that makes the first unshare return ENOMEM and later ones succeed: `mknod_mode_is_atomic()` stays false and mkdir_race prints SKIP, i.e. the process stays on the chmod-by-name path for its lifetime.
Impact: silent downgrade to the racy path for a daemon that hit one transient error at its first mkdir or mknod.
Fix: cache only EPERM, ENOSYS and EINVAL (seccomp or kernel refusal); on ENOMEM or EAGAIN return `Ok(None)` for that call without caching.
Under permanent EPERM the contract still holds: mode_contract passes 3 of 3 with the shim, mkdir_race skips.

### 2. with_private_umask cost on the mkdir hot path (note)

Measured, release build, tmpfs, 16-core box, one thread doing mkdir plus rmdir through PathVfs with a /proc poller running in both arms.
main: 4.8 to 5.2 us per mkdir+rmdir pair.
PR: 33.6 to 34.0 us per pair.
That is roughly +29 us per mkdir, about 7x on tmpfs; on btrfs or ext4 the relative cost is smaller but the absolute 30 us is the same.
It serialises under the PathVfs mutex, so it adds directly to latency for the daemon backend (crates/cowfs-daemon/src/backend.rs).
Acceptable for correctness first, but not free: a single persistent worker thread (unshared once, fed over a channel) would cut it to a channel round trip.
I would accept this PR and file the worker as a follow-up with the numbers above.
Panic safety is fine: a panic in `f` becomes an io error via join, and the umask is thread-private so nothing leaks.
Process umask never leaked: during 20000 mkdirs a poller thread read Umask from /proc/self/status and every /proc/self/task/*/status in a loop (about 68000 samples per run, 3 runs), the leader always showed 0027 (the umask I set) and the process umask read back as 027 afterwards.

### 3. mode_may_change detection (note: incomplete outside local POSIX filesystems)

It queries the parent on every call: one fgetxattr of `system.posix_acl_default` plus one fstat (dirs only).
No caching, so a parent ACL changed later is seen; cost is two cheap syscalls.
Any error other than ENODATA or ENOTSUP counts as "may change", which fails safe.
Covered: default ACL, setgid parent (dirs), setuid or setgid in the request (dirs), owner-inaccessible modes (`first != mode`).
Sticky survives mkdir on Linux, so no handling needed.
Not covered, and invisible to the check:
- Network filesystems where the client cannot see the ACL (NFS without the ACL side-band, 9p, sshfs): the getxattr returns ENOTSUP, detection says "no change", but the server may filter or inherit. Before the PR the unconditional fchmod hid this for mkdir.
- Mount options that force modes (vfat, exfat, ntfs-3g with umask, fmask or dmask): creation mode is rewritten and nothing detects it. Old mkdir fchmod would not help there either, so not a regression for mkdir, but mknod/mkdir contract is "exact" in the PR text.
A catch-all would be robust: mkdir already does `fstat` on the new fd and mknod does `fstatat`; if the observed mode differs from the request, run the fix-up chmod then. That costs nothing extra and covers every unknown alterer, with the same residual race only in the mismatch case.
macOS: `mode_may_change` has no ACL branch, but macOS never reaches the exact path (no private umask), so it always runs mkdirat(0o700) then fchmod by name. The mkdir race of #254 is therefore NOT fixed on macOS (mkdir_race is `cfg(target_os = "linux")`). The PR body says "Fixes #254 (all four items)" and does not say this.

### 4. mode_contract tests

They exercise the fix-up (see mutations above) and check both the returned Attr and the on-disk mode for create, mkdir and mknod across 7 modes including 0o4755, 0o1777, 0o2755, 0o070.
The ACL test self-skips (eprintln SKIP) when setfacl is missing or the fs refuses a default ACL.
CI cannot show this: nextest hides stderr of passing tests, so a silent skip would look green.
I could not read the CI job logs of the head (the logs endpoint returned nothing while the run was still in progress), so whether ubuntu CI really runs the ACL test is UNVERIFIED.
Suggestion: make the skip loud on CI (fail if `CI` is set and setfacl is missing, or assert via a printed marker), and set a default ACL through the `system.posix_acl_default` xattr directly so setfacl is not needed.

### 5. mkdir_race test

Runtime 0.68 s locally (20000 mkdirs, up to 200000 decoys), fails on old code (238 of 26539 here), passes on the PR.
Probabilistic by nature, but with a high hit rate on old code (about 1 percent of decoys), so a regression would be caught with near certainty; the false-green risk is the SKIP when unshare is refused (container with default Docker seccomp, which blocks unshare). Such a CI environment runs the test as a silent pass.
Flake risk on the pass side is nil: the assertion is "zero decoys changed".

### 6. Adapters and visible behaviour

PathVfs is used by the daemon passthrough backend, crates/cowfs-ctl treehash, and the FUSE/NFS test harnesses.
FUSE blocks `system.*` xattrs, so users never see the ACL in the first place; the kernel hands PathVfs an already umask-filtered mode.
Behaviour change that is visible: `mknod` under a parent with a default ACL now returns and stores the exact requested mode (previously ACL-filtered). `create` and `mkdir` already did this (unconditional fchmod before, conditional now), so only mknod changes. Net effect: the passthrough backend can create nodes more permissive than an admin's default-ACL mask intended. This matches MemVfs and Core semantics and the conformance suite (`mknod_masks_mode` expects 0o7777). It should be stated in the PR body and the Vfs docs.
