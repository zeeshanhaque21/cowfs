## 1. Import of fifo, socket and device sources: PASS

The tree walk uses `fs::symlink_metadata` for every entry, so nothing is followed (`crates/cowfs-core/src/import.rs:321`, `:338`).
A special source goes through `special_kind(&md)` and then `view.mknod(...)`; no `open`, `File::open` or `read` is reached for it.
The read-back only opens files for `FileKind::Regular` (`compare_bytes`), and the match arm for other kinds is `_ => {}`, so a fifo can never hang the verifier.
Kind is compared (`kind != want`), mode is compared for every non-symlink, and rdev is compared for devices (`import.rs` compare_dir, new `rdev` field in `Entry`).
Host to cowfs rdev formulas match glibc `gnu_dev_major`/`minor` on Linux and the 8/24 bit packing on macOS; I re-derived `0x810 -> (8,16)` and the mac `(8<<24)|16` by hand.
Test `imports_fifo_socket_and_device_nodes_as_the_same_kind` asserts kind, mode 0o640, nlink 1, size 0 for the fifo, kind for the socket, and kind plus `makedev(1,3)` for a device when root; non-root asserts the device name is absent.
CI: macOS and both Ubuntu test shards passed.
Note A (low): the device branch of the import test only runs as root and only with (1,3), so no CI run exercises the layout bits (minor above 255, major above 0xfff) in `import.rs::cowfs_rdev`. The conversion is only unit-tested in `sys.rs`.

## 2. Model tests: PASS for the vfs-test oracle, PASS WITH NOTE for the Core model

vfs-test oracle (`crates/cowfs-vfs-test/src/model.rs`): reads, writes and truncates on a special leaf expect InvalidArgument; `compare_leaf` compares kind, rdev, size 0 and mode.
I verified it catches broken backends by running `random_ops(i, 60)` over 2000 seeds against `MemVfs::with_fault`: `MknodDropsRdev` fails 596/2000, `SpecialReadOk` fails 177/2000, clean MemVfs fails 0/2000.
`MknodNoParentTimes` fails 0/2000 in the oracle; that fault is caught by the conformance check (parent mtime/ctime assertion in `mknod_fifo_attrs`), which is the pre-existing split of duty.
Note B (medium-low): the Core-vs-MemVfs model (`crates/cowfs-core/tests/model.rs`) `Entry` (line 353) and `dump` (line 364) record kind, mode, nlink, size, digest and xattrs but not `rdev`, and `MOp::Mknod` returns `Vec::new()` so the returned Attr is never compared either.
Core losing or corrupting a device number is therefore invisible to this model; only `cowfs-core/tests/special.rs` reopen tests and the conformance suite catch it.
The PR body says "kind and rdev compared" only for the vfs-test oracle, so this is not a false claim, but the Core model action is weaker than its name suggests. Adding `rdev: u64` to `Entry` is a one-line fix.

## 4. PathVfs::mknod: PASS WITH NOTE

Linux only: `sys::mknodat` is cfg linux (`sys.rs:217`) and the non-Linux stub (`sys.rs:232`) returns `ENOTSUP`, which `io_err` maps to `Error::NotSupported` (`table.rs`, `ENOTSUP | EOPNOTSUPP`). No panic path on macOS; the macOS native run skips the 16 checks by cfg in `tests/common/mod.rs`.
Errno: EPERM and EACCES map to PermissionDenied, EEXIST to Exists, ENOTDIR to NotDir, EINVAL to InvalidArgument; argument checks (`!kind.is_special()`, rdev on non-device) are done up front.
The FUSE log shows `mknod: ... Operation not permitted` for the device as a normal user, which is the expected mapping.
Note C (medium-low, hardening): `PathVfs::mknod` sets the mode with name-based `fchmodat(dir, name, mode, 0)` after `mknodat` (`crates/cowfs-vfs-path/src/lib.rs:305`), and `setattr` for a special node on a named location does the same (`lib.rs:214`).
That follows symlinks if the name is swapped between the two calls, and it contradicts the file's own comment at `setattr` ("a path based chmod could land on whatever was swapped into that name"); `create` and `mkdir` use `fchmod` on an `O_NOFOLLOW` descriptor.
`PathVfs` is not test-only: `cowfs-daemon/src/backend.rs:919` serves it as the path backend.
Fix: use the `O_PATH|O_NOFOLLOW` descriptor with `chmod_fd` (already added in this PR) in both places, or `AT_SYMLINK_NOFOLLOW`.
Also, if `fchmodat` fails after `mknodat` succeeded, the node is left behind and an error is returned.
Privilege: a root daemon on the path backend can now create devices for a mount client; the PR leaves that to the adapter ("no credentials here"), consistent with the trait doc, but worth confirming the FUSE adapter gates it.

## 6. PR body honesty: PASS, with one coverage gap understated

The body discloses all three weaknesses and the numbers it cites are true.
Device probe fallback: `kinds()` (`special.rs:24`) probes one device `mknod` and falls back to fifo and socket on `PermissionDenied` (`special.rs:37`). Through FUSE as a normal user `mknod_device_attrs_keep_rdev` returns `Ok(())` without asserting anything (it passes vacuously), as the body says. The native PathVfs job on ubuntu also runs unprivileged, so PathVfs device creation, the rdev round trip through `host_to_cowfs`, and the root branch of `special_files_through_mknod` (`mount.rs:81`) have never run anywhere in CI.
Note E (medium): the fallback is chosen from the backend's own answer, not from an explicit option. If Core or MemVfs regress to returning PermissionDenied for a device, every device case silently degrades to a pass instead of failing. The gate should be an explicit `Options` flag (for example `devices_need_root`) set only by the FUSE and PathVfs harnesses when `geteuid() != 0`, so MemVfs and Core always demand the device path.
ctime assertion: `mknod_fifo_attrs` (`special.rs:62`) now asserts only `atime == mtime`. Dropping it does not hide a bug in the shipped PathVfs, because PathVfs genuinely bumps ctime when it applies the mode after `mknodat`, and Core's `mknod` shares `new_child` with `create`, whose ctime is covered by the create checks and `operation_time.rs`. It does remove the only check that a fresh special node in MemVfs/Core has a sane ctime; a regression to ctime 0 or a stale value would pass. Cheaper and stronger replacement: keep `a.ctime >= a.mtime` for every backend and `a.ctime == a.mtime` where the backend does not declare post-create chmod.
Root branch never run in CI: confirmed by the log line `mknod: /tmp/.../chr: Operation not permitted`.
Local macOS receipts for `mkfifo/00.t` and similar are described, not reproducible from the PR; not re-run here.
