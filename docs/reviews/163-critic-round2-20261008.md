## 3. Crash safety of the new path

Sequence in `ingest_with` (crates/cowfs-core/src/import.rs) plus `replace_with_staged` (crates/cowfs-core/src/swap.rs):

1. `check_new_name_except(name, victim)`, remove any leftover hidden staging snapshot of the same name.
2. Create the hidden staging snapshot, `write_tree`, `fsync_snapshot`, `verify` against the source. Any error here unregisters staging; the old base is untouched.
3. `write_intent`: tmp file, sync, rename, sync the directory. Failure calls `rollback`; the old base is untouched.
4. `unregister(old)`. Failure calls `rollback`; old base kept. This is the point of no return.
5. `finish_swap`: fork staged into `name`, unregister staged, remove the intent file.

What a crash leaves:

- During step 2 or before the intent: old base intact, a hidden staging snapshot (not listed). Cleared by the next ingest or swap of that name, NOT by `Core::open` (see finding C).
- After the intent, before step 4: `Core::open` runs `swap::recover`, `finish_swap` sees the target still exists, drops staging and the intent. Old base intact, new tree discarded, record stale. A retry converges.
- After step 4, before the fork: `recover` forks staged into `name`, so the new tree is rolled forward. No window where the name is gone with nothing to restore it, because the staged tree was fsynced and verified before the intent existed.
- After the fork: only cleanup of staging and the intent remains, which `recover` repeats idempotently.

`recover` is shared with `swap_snapshot`, and `promote_base_survives_a_failure_at_every_step` (crates/cowfs-core/tests/swap.rs) injects faults at steps 1 to 5 and reopens, so the roll-forward machinery is exercised by existing tests.
What is NOT exercised: `replace_with_staged` itself. It contains no `self.fault(n)` call, `ingest_replacing` has no test in cowfs-core at all (grep: no reference outside src), and nothing reopens a store after a replacing ingest that failed after the old tree was removed.
Assessment: acceptable, not a blocker. The ordering is the same as `swap_snapshot` steps 2 to 6, the intent record has the same format, and the recovery code is the one already fault-tested. The builder states this gap openly in the PR body and the design doc.
Recommendation: add `fault()` seams to `replace_with_staged` and one core test that mirrors `promote_base_survives_a_failure_at_every_step` for `ingest_replacing`. File it before merge.

## 4. Replacing a plain user snapshot of the same name

Behaviour: `base_refresh` on a name that is a plain user snapshot (no base record) replaces it, silently, with no way back.
Comparison: the passthrough backend does the same today (`taken` is "any snapshot with that name" and it swaps), so this is parity, not a regression, and it is documented in the PR body, the design doc and `docs/v1-daemon.md`.
Mitigations: the default name is `<repo basename>-base`; a collision needs the user to pick that name or pass `--name`.
How bases are distinguished: only by the daemon's base record (`base_meta`), which `invalidate_base_record` itself treats as the marker ("a name with no record is not a base").
Should it refuse instead: arguably yes for an unrecorded name, but a bare refusal would wedge a legitimate retry after the documented crash window (installed, not yet promoted, so no record exists). A safe version needs an explicit replace flag or a record written before install.
Verdict: non-blocking. Suggest an issue to add a refusal for an unrecorded existing name unless the caller asks to replace it, and say so in the CLI help in the meantime.

## 6. Findings

A. Retry after a post-removal failure can destroy the only copy of the new tree.
If `finish_swap` fails after the old target was unregistered, the staged tree and intent are kept in the live process, as designed. A later refresh of that name starts by unregistering any leftover staging snapshot (`ingest_with`, same as `swap_snapshot`). If that retry then fails or is cancelled, the old base, the staged tree and a dangling intent are all gone; the next `Core::open` can only log `last_flush_error`. Needs a double failure, so narrow. Fix: roll forward pending intents before starting an ingest of the same name. Issue, not a blocker.

B. Record handling after a pre-removal failure.
On a replacement the daemon clears the old base record first and restores it only for `Cancelled` and `InvalidParams`. Errors raised before the old tree is touched (disk full during `write_tree`, the 255-byte intent-file failure in the length test) leave a perfectly intact base reported stale. Conservative and safe, but pessimistic. The doc says so.

C. Orphan hidden staging is not removed by `Core::open`.
The design doc ("which `Core::open` and the next ingest of that name clear") and the module doc of swap.rs say open removes a staging snapshot with no intent. `swap::recover` iterates intent files only; nothing else in `Core::open` deletes `*.cowfs-swap0`. A crash during the long staging write therefore leaves a hidden snapshot holding blocks until that same name is refreshed again (names never refreshed leak). Hidden, so no user-visible residue, but the doc claim is false. Fix the doc or add the sweep.

D. Concurrency (issues 167, 170 already filed).
Two refreshes of one name share the staging name, and the restore of a saved record is not guarded. Accepted by the builder, tracked.

E. Replacing a base with live holders or forks is unverified (the builder says so). `replace_with_staged` uses `unregister` exactly like `remove_snapshot` and `swap_snapshot`, so it behaves like promotion today.
