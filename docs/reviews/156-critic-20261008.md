## What the test pins

A flaky backend (flip_every 3) holds 300 durable files after sync.
One unsynced create stays pending and is visible in the session.
Flipped reads run until corruption is detected (a panic counts as detection, as in review.rs).
The test then asserts health().poisoned is true and a further create is refused with Error::Corrupt.
It drops the handle, reopens the image, requires check() to pass, and requires the directory to equal exactly the 300 durable names.
The absence of the pending file is the documented bounded loss.
db.rs confirms the mechanism: note() sets poisoned on Error::Corrupt and check_writable refuses writes while poisoned.

## Would it fail on changed behavior

It is a policy pin, not a bug fix, so there is no old behavior that fails it.
It fails if a corrupt-seeing handle persists the pending window on drop, if the handle stops poisoning, or if writes are accepted after poisoning.
No assertion is weakened.
The detection loop is bounded and asserts detection happened, so it cannot pass vacuously.
