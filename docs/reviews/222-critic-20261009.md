# Critic review: PR 222 (ci/changed-tests-nextest), per-PR changed-crate test selection

Reviewer: fresh-context critic, read-only. Head cd1d7fb, base 2dc6703 (includes PR 213).
Scratch clone only; the primary checkout was not touched.

## Verdict: BLOCK

The selector can drop tests that exercise a changed crate through a binary, and it can also fail a PR that only touches the dropped-from crate.
The fix is small (see "Required before merge").
Everything else is PASS or PASS WITH NOTES.
The pre-registered merge rule (beats full on wall-clock AND macOS job time WITH NOTHING DROPPED) is not met, because tests are dropped by design and the "0 dropped" evidence is circular (section 6, 8).

## BLOCK: crate tests that drive another crate's binary have no cargo edge

Counterexample 1, false skip.
A PR that changes only `crates/cowfs-cli/src/**` selects `{cowfs-cli}` (verified with `select()` on the head tree).
`cowfs-treehouse` depends only on `cowfs-ctl` (cargo metadata), so it is not an rdep of cowfs-cli, cowfs-daemon or cowfs-core.
Yet its integration tests execute the `cowfs` binary that cowfs-cli builds and the `cowfs-daemon` binary:
- `crates/cowfs-treehouse/tests/spawned_server.rs:20-37` (`cowfs_bin()`, "A spawned `cowfs serve --stub`", 6 tests in the full run).
- `crates/cowfs-treehouse/tests/sandbox_treehouse.rs:31-34,530` (15 tests, one drives `cowfs serve`).
- `crates/cowfs-treehouse/tests/real_project_acceptance.rs:95-123,863,1023` (`require_bin("cowfs-daemon")`, 14 tests).
So a regression in `cowfs serve`, in the daemon, or in anything core that reaches those binaries can break treehouse acceptance tests, and the filtered run never runs them.
The trial evidence shows the drop: the core-shape closure is `cli, core, daemon, fuse, gc` and "Skipped: ... treehouse" (PR body), while the full run had 151 treehouse tests on macOS and 154 on ubuntu (re-derived from run 37911686796 logs).
The same applies to `cowfs-daemon/tests/namespace_durability*.rs:97-104,194-198`, which run the `cowfs` binary; that one happens to be covered only because cowfs-cli is an rdep of daemon.

Counterexample 2, false failure (reproduced).
A PR that changes only `crates/cowfs-treehouse/**` gets `-p cowfs-treehouse`, so cowfs and cowfs-daemon are not built.
I ran `cargo nextest run -p cowfs-treehouse --profile ci --no-tests=pass -E 'rdeps(=cowfs-treehouse)'` on a clean target dir in the scratch clone.
Result: 151 run, 5 failed, 2 skipped, with `cowfs-daemon is not beside this test binary` from `real_project_acceptance.rs:113`.
In CI the rust-cache restore might hide this with a stale binary from main, which would instead test against a stale `cowfs`/`cowfs-daemon` (also wrong).
Either outcome is a defect: the full path builds every binary with `--workspace`, the filtered path does not.
No trial shape touched treehouse, so no trial caught this.

Required before merge (any one of):
- Add the runtime edges explicitly: a small table in select-tests.py (`treehouse` depends at runtime on `cowfs-cli` and `cowfs-daemon`), applied to the rdeps closure, and add those crates to `-p` so the binaries are built. Keep the table honest with a test that greps `crates/*/tests` for `CARGO_BIN_EXE_`, `sibling_bin(`, `daemon_bin(`, `current_exe` plus a sibling name, and fails when a crate execs a workspace binary that is not declared.
- Or map any change in cowfs-cli, cowfs-daemon, cowfs-core or cowfs-treehouse to FULL (smaller win, zero reasoning).
- Either way, add a selector test for "change in cowfs-cli selects cowfs-treehouse" and for "change in cowfs-treehouse builds cowfs and cowfs-daemon".

## Findings by requested area

### 1. Path classes

Checked with `select()` on the head tree (all behave fail-closed unless noted):
- Member crate `Cargo.toml` only: selects that crate plus rdeps. Correct.
- New crate dir (`crates/cowfs-new/...`): not in head metadata? It is in head metadata when the crate has a Cargo.toml, and root-level `Cargo.lock` normally changes too, so FULL. A new crate with no new lock entries and no dependents would select just itself; acceptable.
- Deleted crate or renamed crate dir: old paths are unplaced, so FULL. Correct (unit test covers rename).
- `tests/` dir change (for example `crates/cowfs-ctl/tests/golden/wire.tsv`): selects the crate and rdeps. Correct.
- `build.rs`: none exist in the workspace (`ls crates/*/build.rs` empty). A future one inside a crate selects the crate. Fine.
- `.cargo/`, `rust-toolchain*`, `deny.toml`, `Cargo.lock`, root `Cargo.toml`, `.config/nextest.toml`, `.github/**`, `scripts/**`, `spikes/**`, any unknown root file: all FULL (verified output).
- `docs/**`, root `*.md`, `bench/**`: mapped to ignore. I grepped `crates/**/*.rs` for `include_str!`, `include_bytes!`, `CARGO_MANIFEST_DIR`, `../..`, `scripts/`, `bench/`, `docs/`.
  `CARGO_MANIFEST_DIR/../../bench/out/...` is an output directory (`namespace_durability.rs:92`, `namespace_durability_gate.rs:76`, `real_project_acceptance.rs:128`), and `namespace_durability.rs:448` only hashes listed source files for provenance.
  `scripts/cowfs-ns-run.sh` appears only in messages (`mode_b.rs:595`, `cli.rs:412`).
  No test reads a file under docs/ or bench/. No `include_*` of a path outside its crate exists. Ignore mapping is safe today.
  Note: the ignore rule is a repo convention with no guard; a future `include_str!("../../../docs/x")` silently becomes a hole. A cheap lint (grep for `../../` in crates/*/src and tests, fail if it targets docs/ or bench/ and is not `bench/out`) would pin it.
- Markdown inside a crate dir selects the crate (good, README doctests).
- One non-cargo seam remains: the treehouse-to-binaries edge above. That is the only path class I found where truth is larger than the selection.

### 2. rdeps correctness

The selector's closure was compared with a reverse closure computed from full `cargo metadata` resolve (all dependency kinds) for all 15 workspace crates: identical for every crate (0 differences).
Edge kinds seen in this workspace: dev (`cowfs-vfs-path` to `cowfs-vfs-test`, `cowfs-gc` to `cowfs-core`), target-specific (`cowfs-fuse` under linux, `cowfs-nfs` under macos in daemon), and the self dev-dependency on store with `fault-injection`.
Target-specific and optional edges are included regardless of host (superset, safe).
Build-dependencies are in `dependencies` with kind build and are followed.
Renamed dependencies: the selector uses `dep["name"]`, the real package name, which is right.
There is no test-only workspace member today; one would be handled as an ordinary crate.

Feature unification note (PASS WITH NOTES).
`--workspace` unifies `cowfs-store/fault-injection` into every test build, because `cowfs-gc` and `cowfs-store` dev-depend on it.
`cargo tree -p cowfs-cli -p cowfs-daemon` shows `cowfs-store []` (no feature), while `cargo tree --workspace` shows `[fault-injection]` everywhere.
So with `-p`, cowfs-daemon and cowfs-core tests run against store built without the seam, a different binary than the full run.
No test outside store and gc is gated on that feature (grep shows only `cowfs-store/tests/{compact,round4,round5}.rs`, `fsio.rs`, `cowfs-gc/tests/crash_inject.rs`), so nothing is dropped today, and the filtered build is closer to production.
But the claim "filtered equals full restricted to the closure" holds by test name, not by build configuration.
It also lowers rust-cache hits for those crates.
Document it, or add a note to the summary.

### 3. Shards, doctests, `--no-tests=pass`

- `--partition hash:S/N` applies after the filterset, so shards split the selected tests; edge shards ran 34 s and 36 s with 44 tests per OS, so neither was empty.
- `--no-tests=pass` is too lax as written. If the filterset ever matches nothing (typo, a crate with zero tests, nextest semantics change), every shard and macOS (a single 1-of-1 partition) pass silently.
  The macOS job cannot legitimately be empty when the closure contains a crate with tests.
  Suggested guard: in filtered mode run `cargo nextest list -E "$FILTERSET" $PKG_ARGS --message-format json` once and fail if the count is 0 while PKG_ARGS is non-empty and the selection is not bench or docs only; keep `--no-tests=pass` only for `of > 1`.
- Doctests: `cargo test --doc -p` runs only lib crates of the closure. `cowfs-cli` is bin only (no doctests exist for bins in cargo), so edge shows "no doctests". Correct.

### 4. Fail-closed behaviors

- Selector exception: `main` has no catch, non-zero exit, `Select tests` fails, later steps are skipped, `test` is failure, `check` fails. PASS.
- No changed files, or an unresolvable base: FULL or error. PASS (unit tested).
- `push` to main and `workflow_dispatch`: `--event != pull_request` yields FULL without calling git. PASS.
- `pull_request_target` and `merge_group` do not trigger this workflow. PASS.
- Force-push and re-runs: a new merge SHA or the same fixed merge SHA, diff is stable. PASS.
- First push of a branch: a PR event always has a merge ref. PASS.
- Shallow clone, fetch-depth 2: HEAD^1 is valid on the GitHub merge commit; confirmed by all six trial runs succeeding with real selections. PASS WITH NOTES: nothing checks that HEAD is a two-parent merge. If GitHub ever hands the job a head commit that is not a merge (or a squashed single parent), `HEAD^1` is the PR's own parent and the diff shrinks to the last commit, a silent false skip. Add `git rev-parse --verify HEAD^2` to the selector for `pull_request` and FULL (or fail) when it is absent. Better still, diff against `github.event.pull_request.base.sha` with `fetch-depth: 0` on that ref, or `git merge-base`.
- Missing outputs fail OPEN. In the `Nextest` step the branches are `MODE = full`, then `-n "$PKG_ARGS"`, then a final `else echo "no crate selected: no tests"` that exits 0. If `steps.select.outputs.mode` is ever empty (renamed step id, output lost), MODE is empty and PKG_ARGS is empty, so the job passes having run nothing. `scripts/test_ci_workflow.py` has no case for an empty MODE. Make the empty branch `[ "$MODE" = filtered ]` explicit and `exit 1` on any other MODE value. The Doctests step has the same shape.

### 5. `check` aggregate

Unchanged. `needs: [lint, fault-seam, test, linux-fuse, linux-namespaces]`, `if: !cancelled()`, and `test ... = success` for each, so a selector failure (test failure) or a skipped required job fails `check`. PASS.

### 6. Trial evidence re-derived

Timings: re-computed from `gh run view` JSON for runs 37911686108/-004 (edge), -684581/-686796 (core), -683895/-686582 (forced); every table value in the PR body matches (for example edge macOS 126 s vs 999 s, queue 239 s vs 394 s).
Dropped-test comparison re-derived from the job logs for both OSes, edge and core:
- core macOS: filtered 731 tests; full 1875 total, 731 inside the closure; dropped 0, extra 0.
- core ubuntu: filtered 726; full 1874 total, 726 inside the closure; dropped 0, extra 0.
- edge macOS and ubuntu: filtered 44; full inside closure 44; dropped 0.
So the arithmetic in the PR is right, but the comparison is circular: it restricts the full run to the same closure the selector produced, so it proves the filterset implements the closure, not that the closure is complete. The tests that matter are the ones outside it: 1144 (macOS) and 1148 (ubuntu) in the core shape, including the 151/154 treehouse tests above. No negative control (a deliberate breakage that only an out-of-closure test catches) was run.
"Beats full" on macOS job time is real and not queue noise: 126 s vs 999 s and 346 s vs 1094 s are job run times, and the work shrank by 98% and 61%. The forced-full pair (1008 s vs 1082 s, identical work) bounds macOS job-time noise at roughly 70 s.
Wall-clock is noise dominated: the forced pair did identical work yet finished in 1022 s vs 1833 s, almost all macOS queue wait (9 s vs 744 s). A single sample per arm cannot support a wall-clock claim smaller than that gap; the edge (977 s apart) and core (1388 s apart) gaps exceed it, but the PR's own excluding-queue figures (183 s vs 1005 s, 352 s vs 1100 s) are the defensible ones.
Arms also differ in layout (full arm used main's old workflow, filtered arm the new one) and all six runs competed for the same runner pool.

The `Nextest` step has no pipe, so pipefail is irrelevant there. No step names that 213 or the existing tests rely on changed; new steps `Select tests` and `Nextest` were added, and `scripts/test_ci_workflow.py` (18 tests) passes. PASS.

### 8. Pre-registered rule

Rule: merge only if it beats a same-window full run on BOTH wall-clock and macOS job time with nothing dropped.
- Wall-clock: beaten in all three shapes, but the forced-full shape shows the noise floor exceeds the claimed effect for any shape whose gain is under ~800 s, and there is one sample per arm.
- macOS job time: beaten in the edge and core shapes by a wide margin; tied (noise) in forced-full.
- Nothing dropped: not met. By design 2292 test results (core shape, both OSes combined) are not run, and the evidence that "0 dropped" is circular. At least the treehouse tests are dropped that the changed binaries can break.
Verdict against the rule: not met.

Additional evidence I would want:
- The fix above, then a trial where cowfs-cli (or cowfs-daemon) is changed and the treehouse binary-driven tests run.
- A negative control: a deliberately broken `cowfs serve --stub` in a throwaway PR must turn the filtered run red.
- A treehouse-only trial (it is red or stale today).
- Three or more repetitions per arm on a quiet runner pool, reporting medians of macOS job time and queue-free wall-clock.
- A total test-ID diff between filtered and full for every shape, listing each skipped test with the reason it is outside the closure (an allowlist reviewed by a human), instead of restricting to the closure.
- A trial for each remaining path class: Cargo.toml-only, tests-only, new crate, deleted crate.
