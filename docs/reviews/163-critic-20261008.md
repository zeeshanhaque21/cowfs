# Critic review of draft PR 163 (warm base publication on the Core, issue 123)

Verdict: BLOCK.
Reviewer: fresh-context critic, read-only on source.
Method: gh and git against the PR head, plus one throwaway test in a scratch clone (scratchpad `c163`, not the leased worktree).

## Reason (3 lines)

1. A refresh of `<name>` silently deletes any user snapshot named `cowfs-import-<name>` and still reports success.
   Reproduced, not theorised.
2. The delete happens before the new tree is ingested, so an ingest failure also destroys it, and a case-variant name wedges the refresh forever.
3. The fix is cheap and local (stage under the Core's reserved hidden name, or refuse instead of delete), so admitting the loss as "remainder" is not acceptable.

## 2. Data loss and crash safety (the blocker)

Code: `import::replace` (crates/cowfs-daemon/src/import.rs, around line 345).
For a tree backend the staging name is the plain `cowfs-import-<name>`.
Before ingesting anything it does `if snaps.list().contains(&staging) { snaps.remove(&staging) }`.
That is an exact-name delete in the user namespace.

Reproduction (scratch clone, one test, real CoreBackend, real git repo):

```
BEFORE ["cowfs-import-warm"]
RESULT ok=true AFTER ["warm"]
```

A user snapshot `cowfs-import-warm` was created, `base_refresh` for `warm` returned Ok, and the user snapshot is gone with no warning in the report.

Severity: data loss, silent, success-reported.
Worse than the doc admits:

- The delete runs before `replace_tree` ingests.
  If the ingest then fails (disk full, cancel, verify mismatch), the user snapshot is already destroyed and nothing was published.
- `validate_snapshot_name` does not protect this.
  It refuses a leading dot and the reserved `.cowfs-swap` substring (crates/cowfs-snapname/src/lib.rs:63-80), and `cowfs-import-x` has neither, so any user may legitimately own that name.
  The dot prefix was the only thing that made the passthrough staging name uncollidable, and the Core branch deliberately drops it.
- Case variants wedge instead of delete.
  Reproduced: with a user snapshot `COWFS-IMPORT-other`, `refresh other` fails with `already_exists: that snapshot name is already taken`, because `Core::ingest` calls `check_new_name`, which compares `name_key` (case and NFC folded), while the daemon's pre-clear uses exact match.
  The refresh then fails on every retry until the user renames their snapshot.
- Length: staging is `cowfs-import-` plus the name, so a legal base name of 243 to 255 bytes now yields an illegal staging name and a confusing `invalid snapshot name` error from inside the ingest.

The design doc lists the collision under failure modes and the PR body lists it under "Not met".
Documenting a silent data-destroying path is not the same as acceptable, and the Core already provides the right seam.

The seam: `crates/cowfs-core/src/swap.rs` reserves `<target>.cowfs-swap0`, which the name rules refuse for callers, which the root listing hides, and which `Core::open` garbage-collects.
`Core::ingest` already stages into that hidden name and publishes with `finish_swap` (core import.rs:107-150).
The Core's own module doc says "An import stages into the same name: its crash leaves nothing a caller can see".
The PR throws that property away by making the staging snapshot a visible, user-namespace, user-collidable name, then pays for it with a second fork (swap) and a post-hoc remove.

Crash safety of the sequence as written:

- Old base is never lost.
  Taken path goes through `Core::promote_base`/`swap_snapshot`, which writes an intent file, removes the victim, forks into place, and rolls forward on `Core::open`.
  This part is sound and is the strongest piece of the diff.
- A crash between ingest and install leaves a visible `cowfs-import-<name>` snapshot, listed to users, until the next refresh of that same name removes it.
  A crash after swap and before the daemon's `snaps.remove(staging)` leaves the same visible garbage next to a fully published base.
  Neither is a half base, but both are user-visible residue that the hidden-name design would not have.
- Free-name path: `rename(staging, name)` is one metadata transaction, atomic, and `rename_locked` moves the (absent) staging record.
  Then promote and `set_base_meta` are separate steps.
  A crash between them leaves a plain snapshot `<name>` with the new tree and no base record.
  It is not reported as a base, and a retry sees `taken=true` and swaps, so it converges.
- `taken` only means "a snapshot of that name exists", not "it is a base".
  A refresh of a name that is a plain user snapshot replaces it through swap with no check.
  This is inherited from the Path backend semantics ("replacing what is there") and is not new, but it is the same class of silent overwrite and should be refused or documented in the user-facing docs.
- Swap error after the point of no return: `CoreSnapshots::swap` deliberately leaves the record invalidated, so the base reports stale, never fresh.
  The daemon then removes the visible staging; the swap's own intent refers to the hidden `.cowfs-swap0` fork, so that removal is safe.
  Correct.
- If the swap succeeded but `snaps.remove(staging)` fails, the refresh returns Err although the base has already been replaced and its record invalidated.
  Honest (stale), converges on retry, but the error is misleading.

## 3. Atomicity with 115 and 124, provenance

Provenance goes through the same code as the Path backend: `base_refresh` calls `promote` then `set_base_meta` then `create_meta` for both, and `replace_tree` only replaces the tree step.
`CoreSnapshots::swap` invalidates the old record inside `BaseMetaStore::exclusive`, so the old commit cannot survive a replaced tree.
`rename` moves the record under the same lock.
So the 115/124 per-method guarantees hold, and the first-publish and replace unit test covers the end result.

What is not covered, and is newly reachable on the Core: the sequence `replace` -> `promote` -> `set_base_meta` is not one critical section.
I found no per-operation serialisation of `Request::BaseRefresh` in crates/cowfs-ctl/src/server.rs (only a global in-flight cap that answers `busy`).
Two concurrent refreshes of the same name can interleave as A swap, B swap, B `set_base_meta`, A `set_base_meta`, leaving the tree from B under a record claiming A's commit while reporting fresh.
They also share the hidden `<staging>.cowfs-swap0` name, and `Core::ingest` unregisters a "leftover" with that name, which would remove a concurrent peer's in-flight snapshot.
This is UNVERIFIED (I did not run a concurrent test) and the composition is inherited from the Path backend, so I rate it non-blocking, but the PR should state it, since the doc claims atomicity only per step.

## 4. Do the tests fail on old behaviour, was anything weakened

`the_core_publishes_a_warm_base_by_ingesting_the_checkout` calls `import::base_refresh` directly with a real CoreBackend.
On the old code `replace` would call `snaps.create(".cowfs-import-warm")` on the Core and fail with the invalid-name error the PR cites, so the test does fail before the change.
It does not pass through `Handler::base_refresh`, so the removed `can_ingest` gate is covered only by the daemon test.
It checks first publish, replace, no residue, reopen, commit read back, repo untouched.
It has no case for: a user snapshot named like the staging name (the blocker), a failed ingest leaving the old base intact, a base with forks, or a crash/fault-injection step (the Core has `set_swap_fault`, unused here).

`the_core_daemon_publishes_base_refresh_and_leaves_no_worktree` replaces a refusal test.
Removed assertions: the `unsupported` and `stores snapshots as trees` message checks and the "nothing published" check, all of which are now false by design, so removal is legitimate and not a weakening.
Added assertions are weaker than the test name suggests: exit 0, `listed.contains("-base")` (a substring match on the listing text) and worktrees unchanged.
It does not check the base is promoted, fresh, or carries the commit; only the 17-minute ignored acceptance does.
It also silently returns when the host cannot mount (`Core::start` Skip), so on a runner without NFS or FUSE it is a no-op reported `ok`.
Suggest `base status` json plus `commit` equality in that test, since it is the one CI-visible end-to-end check.

## Required to unblock

1. Remove the visible user-namespace staging name for the Core.
   Preferred: add an ingest-with-replace to `cowfs_core::import` that stages in the hidden `<name>.cowfs-swap0` and installs with `finish_swap`/`promote_base`, so no user snapshot is created, deleted or collidable, the extra fork and the post-remove disappear, and a crash leaves nothing visible.
   Minimum: refuse with `already_exists` if `cowfs-import-<name>` exists (exact or `name_key` match) instead of deleting it, and never delete before the ingest has succeeded.
2. Add a test: user snapshot `cowfs-import-<name>` survives a refresh (or the refresh is refused and the snapshot is intact), including after an injected ingest failure.
3. Fix the stale refusal text in docs/v1-daemon.md, docs/linux-namespaces.md and the acceptance file header, or list them in the PR as deliberately deferred.
