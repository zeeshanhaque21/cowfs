## (a) Interval rule correctness

Claim 1 holds.
I fuzzed 200000 random cases (both platforms, 1 to 6 reps per arm, unequal counts, three scales) comparing `g2_decision` to the ground truth "run `verdict()` at the four corners (min or max native, min or max cow); decided only if all four agree".
73113 cases were decided, 0 mismatches.
`verdict()` is monotone in each median, so the corners are exact for any median inside the ranges.
Boundaries are consistent with `verdict()`: macOS FAIL on `add >= B` matches `min_cow - max_nat >= B`, PASS on `add < B` matches `max_cow - min_nat < B`; Linux PASS on `<= 1.5x` matches `max_cow <= 1.5*min_nat`, FAIL on `>` matches `min_cow > 1.5*max_nat`.
Degenerate arms: exactly the budget fails, 1.5x exactly passes, both arms identical passes.
Edge inputs:
- zero wall: `lo <= 0` gives UNMEASURABLE before `g2_decision` runs.
- negative, NaN, inf wall_s: refused as INVALID by `file_problems` (exit 3) before any gate logic. Called directly, `g2_decision` with a NaN rep is not safe (`[5,nan,5]` returned PASS), but unreachable from the CLI.
- fewer than 3 reps: UNMEASURABLE ("need 3") before the decision.
- unequal rep counts: fine, min and max do not care.
Platform: `on_macos = sys.platform == "darwin"` is the platform where `compare.py` RUNS, not where the reps were measured. Files from cachyos compared on a Mac get the macOS budget. Pre-existing (the same flag drives `verdict()`), but the new rule inherits it. `gates.py` records `platform.platform()` in the meta record, so a refusal on mismatch would be cheap. Low severity, not in scope.
Design notes on the rule itself:
- `g2_decision` re-implements the two `verdict()` formulas. No test pins the two together. The fuzz above shows they agree today; a one-line corner-check test would stop drift.
- More reps can only widen min and max. Going from 3 to 10 reps makes UNMEASURABLE more likely, never less. The rule bounds the sample median by the sample range, which is not a confidence interval on the median. A bootstrap or order-statistic interval on the median would behave properly with n. This is a real design weakness, not a bug against the issue text.

## (b) Mixed-run exit precedence

INVALID is global: every input file is validated and all problems collected in `bad` before any comparison, then `return 3`. No per-file ordering bug.
Then `if fails: return 1`, `elif unmeasurable: return 2`, else 0. The `fails`/`unmeasurable` counters span all gates, so FAIL on g1 with g2 UNMEASURABLE gives 1 and `RESULT: FAIL (1), 1 unmeasurable`.
Tests cover FAIL over UNMEASURABLE, UNMEASURABLE alone is 2, INVALID over FAIL (rebuilt_count 100). There is no test for UNMEASURABLE plus PASS on other gates, but the "unmeasurable alone" test has g1 PASS plus g2 UNMEASURABLE, so that case is in fact covered.
The `RESULT: FAIL (n)` prefix is preserved, so greps on it still match (`docs/benchmark-coverage.md:57` still true).
The repo-wide contract in `bench/fsx-gate/run-fsx-gate.py` already says FAIL outranks UNMEASURABLE, so this aligns compare.py with its sibling.

## (d) 115-unit floor

`G2_MIN_UNITS = ceil(0.9*127) = 115`, one definition in `gates.py`, used at `gates.py:168` (rep refused, no row) and `compare.py:264` (file INVALID). No copy left.
127 is measured at pin 3f4fba2 with `--tests`. Under `--locked --offline` at a fixed pin the unit set is deterministic, so a legitimate run does not drop below 115. A different target set, feature set or a changed workspace (a crate removed) would be INVALID by design.
That is acceptable and arguably the point: g2 numbers from a different workload are not comparable. The refusal message names the count. The one cost is that a re-pin that shrinks the graph needs a matching constant edit, and the constant is a guess-derived 90 percent.

## (e) Is g2 now vacuous? Plainly: nearly, on macOS.

Numbers, using the measured 17.37 / 22.97 / 29.34 s native spread (1.69x) and a cowfs arm of the same shape plus 0.5 s:
- macOS (1.0 s budget): `g2_decision` returns None, UNMEASURABLE. Verified by running it.
- Linux (1.5x): None, UNMEASURABLE. PASS would need `max_cow <= 1.5 * 17.37 = 26.1 s`, but the cow max is about 29.8 s.
- macOS PASS needs `max_cow - min_nat < 1.0`. With both arms having the same range and zero true overhead, I get PASS up to a range of 0.9 s and None from 1.0 s, i.e. about 4 percent of a 23 s workload. The old PR 216 "quiet" reps (1.28x) are UNMEASURABLE on macOS.
- macOS FAIL needs `min_cow - max_nat >= 1.0`: with that native range, cow min must be at least 30.3 s, a cow arm that is slower than native's worst rep.
- Linux PASS at a true +2 percent overhead tolerates ranges of about 38 percent (max/min about 1.6x) per arm. That is workable on a calm host, so Linux is decidable, macOS is not unless the host is exceptional.
So: on a Mac, a 1.0 s absolute budget on a 23 s workload cannot be tested with 3 reps of normal noise, and the rule correctly says so. This is not a bug, it is the honest answer, but it means issue 232's practical outcome is "g2 on macOS mostly returns UNMEASURABLE and g12 returns INVALID". The doc says "only results far from the budget are decided" which is accurate yet undersells that realistic PASS on macOS is out of reach; the budget needs to be relative (like Linux) or the workload far heavier to be testable. The readiness doc should say that in one line and cite the 4 percent figure.
