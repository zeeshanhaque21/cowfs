## 2. Is the production change load-bearing and complete

Code: `Canonical::build_command` in `crates/cowfs-treehouse/src/mode_b.rs` (line 641) builds the helper command and sets `CARGO_INCREMENTAL=0`.
`run_build` (line 656) is the only function in the crate that runs a build command, and its canonical arm ends in `c.build_command(dir, command)`.
The non-canonical arm is untouched (`/bin/sh -c`, no env change), as stated.
Callers of `run_build`: both arms of `BaseRefresh::run` (lines 517 and 534), the slot-given and the leased-slot arm.
A repo-wide search for `Command::new` and `CARGO_INCREMENTAL` finds no other build path in `mode_a.rs`, `mode_b.rs`, hooks or the daemon.
So every cargo invocation inside the canonical flow goes through `build_command`.

Gaps that are by design, not bugs:

- The pre-flight probe (`c.args(dir, "exit 0")`) does not set the variable.
  It runs no cargo, so this is harmless.
- The variable only applies to `base refresh --build --canonical`.
  A user who later builds inside a slot, or runs cargo themselves in the namespace helper, gets whatever environment they have.
- On macOS `Canonical::validate` returns `Unsupported`, so the production setting never applies on macOS.
  The macOS 46/46 result is evidence about the variable itself, not about the shipped route.

Override of the caller's value: yes, unconditionally (`.env(...)` replaces any inherited value).
This is stated in the doc comment, in `docs/linux-namespaces.md`, and in the PR.
I tested the strongest case on this Mac: with `[profile.dev] incremental = true` in the workspace and `CARGO_INCREMENTAL=0` in the environment, no `target/debug/incremental` directory is created.
So the env var also beats an explicit profile setting, which is what "overriding" needs to mean.
That is intended and consistent with the doc, but it is a hard override with no opt-out.

Unit test: `get_envs` equality on the command, exactly one env entry.
It would fail if the `.env` call were removed, and the doc comment correctly explains why a run-based test would pass vacuously under rust-cache.
It does not check that `run_build` actually uses `build_command` (a future inline of the command would pass the test).
That is a small residual hole, not a blocker.

Performance and the 1.5x bar: not contradicted by the code path, but there is a real trade-off that is not documented.

- Project bar (`docs/design.md` line 111, `docs/v1-benchmarks.md`): clean `cargo build` within 1.5x of native.
  Benchmarks g1/g2 line 30 say `CARGO_INCREMENTAL` is left at the project default, and they do not go through `run_build`, so the bar numbers are unaffected by this PR.
- Clean builds are not slowed by `CARGO_INCREMENTAL=0` (incremental only adds work on a first build).
- Measured here (macOS, harness fixture, rustc 1.99.0): build with `CARGO_INCREMENTAL=0`, then build again with the variable unset and no source edit.
  Cargo recompiled `mac`, `app` and `lib` (all workspace members).
  Control: default env twice recompiled nothing (0.01 s second build).
  Same variable twice (`=0` then `=0`) also recompiled nothing.
- Consequence: a base prebuilt through the canonical route is only warm for slot builds that also run with `CARGO_INCREMENTAL=0`.
  A slot that builds with the default env pays a full workspace-member rebuild on its first build, and an edit-and-rebuild after that is non-incremental if the user keeps `=0` (slower than the incremental default for large crates).
  Registry dependencies are unaffected because incremental applies only to workspace members.
- This does not contradict the 1.5x bar as written, but it does weigh against the warm-slot goal, and it should be a stated, deliberate choice in the docs.
  Zee's decision (promise covers cargo) implies this cost, so it is acceptable, but it must be written down.
  This is the one required doc fix: add two sentences to the "What is promised for cargo" section naming the trade-off and the workaround (set `CARGO_INCREMENTAL=0` in slot builds, e.g. in the project's cargo config or env, to keep the base reusable).
  I measured only a tiny fixture and did not time a large real workspace, so I make no numeric claim on slowdown.

## 3. Evidence re-run (my numbers, macOS arm64, rustc 1.99.0, cargo 1.99.0)

Method: the PR's own `run.sh` and `an.py`, fixture copied to `proj/`, N = 4 (the PR used 5), scratch dir only.

- Default (`CARGO_INCREMENTAL=1`): 475 file instances, 37 identical (7.8%).
  Differing classes include `debug/app`, `liblib-<h>.rlib` (0/2 rlib), both dylibs (0/2), 116 `.o` under `debug/deps`, and the whole incremental tree.
  This matches the PR's macOS "before" claim (binary, rlib, dylib and many `.o` differ).
- `CARGO_INCREMENTAL=0`: 46 files, 46 identical (100%) across 4 builds, including `debug/app`, rlib x2, dylib x2.
  This matches the PR's "46/46" exactly.

  The cross-slot run in `ns.sh` passes the variable with `env $cfg cargo build`, not through `run_build`, so the shipped route (helper plus `build_command`) was never exercised end to end in a run; only its env is unit-tested.

## 4. Is the promise honest and no wider than the evidence

Mostly yes.

- Scope words are present in the docs: Linux, clean rebuilds, target inside the snapshot, one workspace, rustc 1.99.0, release not measured, `CARGO_TARGET_DIR` outside and incremental rebuilds not measured.
- The fixture is a fair stress for the claim: it has a proc-macro crate, a path dependency, and a `build.rs` that writes a generated file into `OUT_DIR`.
  So it covers proc macro, build script and a dependency, which are the usual sources of non-determinism, and they all came out identical.
- Limits of the fixture, which the docs state partly: no registry dependencies, no `cargo test` build, no `-C debuginfo` changes, no build script that embeds time or env, no native (cc) compilation, and `lib::here()` uses `file!()` which is path-sensitive and is the thing the canonical path makes stable.
  The doc's sentence "including binaries, rlibs, proc-macro libraries, build-script outputs, dep-info files and the fingerprint files" is accurate for this fixture.
  It reads slightly broader than "43 of 43 on one fixture", though the following bullets pin it down; I would move "on the test workspace" into the same bullet.
- The macOS mechanism sentence (debug map paths and mtimes) is flagged in the evidence file as likely, not isolated.
  My run did not isolate it either.
  Note the incremental-id mechanism seen on Linux probably explains much of the macOS `.o` diff too, so that sentence is weak; it is low stakes because macOS is not in the promise.
- Dep-info and fingerprint `timestamp` files were identical in my macOS run, which is plausible but means the promise on "fingerprint files" rests on those not recording wall time on this toolchain.
