## 3. Release safety and feature unification

`cargo tree --workspace -e normal,build,features -i cowfs-store` in the scratch clone shows 0 `fault-injection` lines.
The same command with `dev` edges shows 1, so the positive control is real.
`cargo tree -p cowfs-daemon -e normal,build,features -i cowfs-store` (default features) shows 0.
The only crate that depends on `cowfs-daemon` is `cowfs-cli`, and it names no feature, so the shipped CLI and daemon get the store feature only if something enables the daemon feature.
Only `crates/cowfs-store/Cargo.toml` (self dev-dependency) and the new daemon feature name `fault-injection` in any Cargo.toml.
The workspace uses `resolver = "2"`, so dev-dependency features do not unify into a `cargo build --release` of the daemon or CLI.
The script cannot pass vacuously on the binary check.
It builds `cargo build --release -p cowfs-daemon` into `target/seam-check`, greps `release/cowfs-daemon` (the `[[bin]]` name, same path on macOS and Linux), then touches the store source and rebuilds with the feature.
If the binary path were wrong, `grep -ac` prints nothing, `[ "" = 0 ]` is false and the check fails loudly.
The with-feature build must show more than 0 hits, and CI shows exactly 1, so the needle is a real string literal in the artifact.
One theoretical weakness: the negative tree checks use `cargo tree | grep -q X && FAIL` under `set -o pipefail`.
If grep exits early and cargo tree is killed by SIGPIPE, the pipeline status is nonzero and the failure branch is skipped.
I ran the identical pipeline 10 times on the dev tree (30 lines of output) and it matched 10 of 10, so it is a theoretical race only.
Real hazard that is already handled: `cargo test --workspace` unifies the feature into `target/debug/cowfs-daemon`.
`build_fault_daemon` therefore refuses to run if the plain daemon carries the seam, so the harness fails closed instead of testing a fault binary as "normal".

## 4. Harness false-PASS analysis

Receipts are recorded in the template build, before any crash, and the template is shut down cleanly so the removal is committed.
Readback is on a fresh daemon and a fresh mount of the same store, so nothing is served from the dead daemon's cache.
Each point clones the same template (`cp -R -c` on APFS, plain copy on Linux), so the fixture is identical per point.
Only d1 uses `FAULT_DAEMON` and the env var; `daemon_env` strips any inherited `C7D_*` key from every other daemon.
Evidence in `bench/out/crash88/f173-d/fault-n001/records.jsonl` (read from the lease tree, not modified): d1 `cmdline` is `target/fault-daemon/debug/cowfs-daemon`, the restart `cmdline` is `target/debug/cowfs-daemon` on the same cloned store path.
`assert.gc_death_is_77` records `rc: 77` read from the child's exit code, and `assert.gc_request_failed` records `gc_rc: 1`.
`crash.image` records the raw pack dir before reopen (pack-00000000.cpk 268327872 bytes present, plus a 37 MiB second pack).
Second gc freed 268327872 bytes, which equals the source pack size, so the restart really reclaims the sealed pack.
The summaries match the PR claims: `f173-c` has the control completed, 18 points in phase gc all passing, n=19 completed, source pack present for 1..13, missing for 14..19, `closed` empty.
The control point asserts `freed_bytes > 0` (`control_gc_freed_bytes`), and the failing-first with 12 MiB garbage is a documented run.
The stage fails closed when no point crashed inside the gc, when the first point already completes with `lo > 1`, and (for full sweeps) when no image has or lacks the source pack.
Process hygiene: children start in a new session, `kill_verified` uses a recorded process identity (no `pkill -f`), every daemon and mount is torn down in `finally`, sockets and lock files are unlinked, and the store lives under `bench/out/crash88*/` inside the project.
Passing points delete their 300 MiB store clone; failing points keep it for diagnosis.
Gap in rigor: "died during gc" is inferred (daemon alive after ready, then exit 77 after the gc request, and the gc request failed), not proven by a gc-in-progress marker.
The inference holds because the idle daemon has no other boundary source and startup is separated (a death before ready lands in phase `startup`), but a marker such as a gc progress line before death would make it direct.
The `fault-n001` second-gc stderr does contain gc progress messages for the restart, not for the killed daemon, so no such marker exists for d1.

## 5. Scope and honesty

The reason (288 MiB per matrix rep is too costly, and `gc_crash` still frees 0 bytes) is stated in the PR body under "Differs from the task text" and in `docs/crash-injection-173.md`.
The deviation is justified and disclosed.
The doc and PR list what is not covered: power loss, metadata-commit edge, freeze `meta.sync` window, write-path ordering, mutation 2, CI job for the sweep.
Mild overclaim: the doc says slice 2 "Closes gap 1 at daemon level", but the matrix case is unchanged and the sweep is a manual stage, so gap 1 is closed only for someone who runs the stage by hand.
Stale text: the slice 1 caveat still says "The CI workflow has no release build step", which this PR makes false (the check now builds two release daemons).
No mutation at the daemon level was run to show the stage detects a corrupting gc; the only negative controls are the old-fixture failing-first and the removed feature line.
