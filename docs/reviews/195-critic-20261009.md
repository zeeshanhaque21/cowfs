## 3. Semantics

Sites that can produce a size or offset past `MAX_FILE`, all now `FileTooBig`: Core `op_write` (`off.saturating_add(len) > MAX_FILE`), Core setattr size (`size > MAX_FILE`), MemVfs setattr size, MemVfs write.
Genuine out-of-space remains `NoSpace`: store `LimitExceeded` mapping in `cowfs-core/src/error.rs`, inode ceiling in `ino.rs` and `inner.rs`, `ns.rs:177`, `lib.rs:731`, PathVfs `ENOSPC | EDQUOT`.
PathVfs now maps `EFBIG` to `FileTooBig` (before: it fell to `Io("errno 27")`, EIO). That is a strict improvement.
FUSE uses `Error::errno()`, so EFBIG comes for free; the variant is in the errno test list.
NFS table maps to `NFS3ERR_FBIG`; `VARIANTS` and `KNOWN` are both updated, and that test guards future variant additions.

Boundary exactness, tested with a temporary test in the scratch clone (discarded) against Core:
- truncate to `1<<42` is accepted and size reads back `1<<42`; truncate to `(1<<42)+1` is `FileTooBig` and the size is unchanged.
- write of 1 byte at `MAX-1` (ends exactly at `MAX_FILE`) succeeds; write at `MAX`, and 2 bytes at `MAX-1`, are `FileTooBig`.
- write at `u64::MAX` and `u64::MAX-1` with 2 bytes: `FileTooBig`, no panic, no wrapped small size (saturating add).
- truncate to `u64::MAX` and to `i64::MAX+1`: `FileTooBig`.
NFS sattr size is `u64` end to end (`set_size3::size(n)` to `Some(n)`), so there is no negative or sign case. FUSE setattr size is `u64` from the kernel, and the kernel's `inode_newsize_ok` rejects above `s_maxbytes` before the daemon.

Mapping completeness: `cargo check --workspace --all-targets -j2` in the scratch clone finished clean (113 crates). `Error` is `#[non_exhaustive]` and all consumers use wildcards, so the compiler cannot prove completeness. A grep of every `NoSpace`/`NOSPC` site across all crates shows no other table needing the new arm.

NFS FSINFO facts: the adapter does not override FSINFO. The vendored `crates/nfsserve/src/vfs.rs:163` advertises `maxfilesize: i64::MAX`. The server accepts at most 4 TiB (`1<<42`).
So a native client never refuses locally and always asks the server; that is why the SETATTR error path (and its FBIG code) is the one that matters. It also matches the PR's pjdfstest design (the client sees FBIG from the server).
RFC 1813 does not list NFS3ERR_FBIG among SETATTR's documented errors, but WRITE does, and Linux nfsd returns it for setattr. The PR's real pjdfstest run on the NFS arm is the evidence the macOS client surfaces it as EFBIG. I did not re-run pjdfstest (needs a mount and lease); that claim is taken from the PR text and is unverified by me.

macOS oracle (native APFS, python `ftruncate` in the scratchpad): truncate to 999999999999999 succeeds (sparse); `1<<42` succeeds; `i64::MAX` gives EFBIG; `pwrite` at 999999999999999 succeeds.
So native macOS passes ftruncate/12.t #2 by success, cowfs passes it by EFBIG. Both are in the script's accept set (EFBIG, EINVAL, 0). Cowfs is stricter than APFS here, which is a deliberate 4 TiB design limit and not a regression.

## 4. ci.yml run count

The count is the `N run,` line, and `run` excludes skipped checks (`runner.rs:332`, `results.len()`).
So 127 to 128 for one new un-skipped check is correct, and the bump is traceable to the PR (the failing first run on `fed058c` showed exactly the opaque failure).
Hard-coding is sound only while every branch remembers to bump. Sequence:
- PR 195 lands: 128.
- #103 slice D unskips 6 fallocate checks in the FUSE harness (the skip block in `crates/cowfs-fuse/tests/conformance.rs`): `run` rises by 6, so it must bump to 134. Failure message is the opaque `Missing full conformance report`.
- #107 slice A adds 16 `special` checks, skipped in FUSE until slice C: `run` stays the same, `skipped` rises by 16. No bump now; slice C (unskip) will need one.
Every bump collides textually on the same ci.yml line, and a green branch can go red only after merge ordering changes, since the number depends on the combination.
Better design (recommendation, not blocking): derive instead of hard-code. Parse the final report line and assert `run + skipped + heavy_not_enabled + above_level` equals the number of checks in `conformance/list.rs`, and separately assert the skipped set equals an explicit expected list (or `skipped` is at most a named cap). That catches a silently dropped check, needs no bump per new check, and yields a message naming the numbers. At minimum, include the observed line in the assertion message.

## Non-blocking notes

1. Gap in the "all places" claim: MemVfs `fallocate` still returns `NoSpace` for a range past `MAX_FILE` or an overflowing `offset+len` (`memvfs/vfs_impl.rs:414-417`). Linux returns EFBIG. Core has no fallocate yet, so this is consistent today, but slice B and D should return `FileTooBig` and `docs/fallocate-103.md` should be updated. There is no conformance check for it, so nothing would catch a disagreement between Core and MemVfs.
2. The PathVfs `EFBIG` mapping has no direct test (only the generic conformance check, which does not exercise it on a real filesystem).
3. The FSINFO `maxfilesize` mismatch (`i64::MAX` advertised, 4 TiB enforced) is a candidate follow-up: advertising `1<<42` lets native clients reject locally. Not needed for g3; file an issue if wanted (I filed none).
4. A zero-length write at an offset past `MAX_FILE` also returns `FileTooBig` (the check runs before the `len == 0` return). POSIX allows a zero-length pwrite to succeed trivially. Harmless.
5. The pjdfstest re-run (3/3 ok both arms) was not independently re-run; its output directory is not in the primary checkout.
