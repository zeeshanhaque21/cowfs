## 1. #178 fail closed

Default `replace` is false at every entry point.
Callers of base_refresh: cowfs-cli (new `--replace` flag, commands.rs), control API (server.rs:1210 dispatch), daemon handler.rs:486, cowfs-treehouse ctl.rs:214 (hardcoded `replace: false`).
The unrecorded-existing check runs inside `import::base_refresh` itself, so there is one gate, not per-caller copies.
Error is `already_exists` and names `--replace`.
Normalisation and case variants: a plain snapshot "Café" NFC refreshed as NFD, and "Mine" refreshed as "mine", both fail closed on both backends and the user tree is untouched.
The error text is misleading there: Core says `already_exists`, the path backend says `io_error: cannot install ...: name is taken`, because the `existing` lookup uses exact string `list().contains(&name)` instead of name_key.
Not a data-loss path, but the no-flag message does not tell the user about the aliasing.
A crashed or failed first publication (installed, not yet promoted) leaves an unrecorded snapshot, and the retry is refused.
That is documented in the PR body.
Note: cowfs-treehouse hardcodes `replace: false` and its CLI has no flag, so a treehouse-owned `<pool>-base` stuck in that state can only be unstuck with `cowfs base refresh --replace` or by deleting the snapshot.
Suggest a follow-up: on failure after install, base_refresh removes the snapshot it just created, or treehouse gets a `--replace` passthrough.
A failed refresh of an existing base is safe: invalidate_base_record keeps a `promoted_unknown` record, so the base stays a base and the retry needs no flag.
Residual TOCTOU: the existence check (import.rs, `existing`) and the later `taken` in `replace()` are separate reads, and user `snapshot_create` does not take the guard, so a user creating that name in the gap can still be replaced on the path backend.
Narrow, not reproduced, noted only.

## 2. #167 per-name guard

Lock is a process-global `Mutex<Vec<(store, name_key)>>` used as an in-flight set, not a held lock.
The mutex is held only for the push or retain, never across the refresh and never across an await, so there is no deadlock with the Core's store LOCK flock (it takes none) or the swap recovery.
The RAII guard `Refreshing` is held for the whole function body including promote, set_base_meta and the read-back, and drops on every exit.
Crash: in-memory only, so nothing stale survives a restart.
Key is `name_key(name)` (NFC plus lowercase), so two spellings serialise, which the stress confirms; it is keyed by the unresolved `store_path()`, fine with one backend per process.
A second concurrent refresh answers `busy` instead of waiting, which is a behaviour choice and is documented.
It does not cover a refresh versus another writer of the same name (`snapshot_swap`, user create).
I stress-tested refresh versus `swap("warm","other")`, 30 rounds on both backends: 0 inconsistent states, so no counterexample, but the interleaving is unguarded by design.
Files: this PR touches only crates/cowfs-daemon/src/import.rs and ctl, snapname, cli, treehouse.
PR 220 (swap recovery on open) lives in crates/cowfs-core/src/swap.rs and the Core open path, which this PR does not edit.
No file overlap, so either can merge first.
Semantic coupling only: #231 relies on the Core staging name `<name>.cowfs-swap0`, which the PR 220 fix must keep.

## 3. #170 length

Limit enforced at the first call: control API for base_refresh and snapshot_promote (server.rs:1196 area and 1210), and again inside base_refresh for the derived default name, which never passes the API.
Uses `name.len()` (bytes), not chars.
BASE_NAME_MAX = 255 - 15 = 240.
Derived names: swap-NAME.tmp (+9), .cowfs-import-NAME (+14), NAME.cowfs-swap0 (+12), and the path backend `.cowfs-retired-NAME` (+15, used by swap, not refresh) all fit at 240.
Unit test asserts the three the PR names; the retired name also fits only because 240 happens to equal 255 - 15.
Verified end to end: a 240-byte name refreshes twice (second is the swap) on both backends; 250 bytes is refused with invalid_params and nothing is published.
Compat: validate_snapshot_name is untouched, so already-published names of 241 to 255 bytes stay listable, readable, deletable, renamable and cloneable.
They can no longer be re-promoted or refreshed.
The refresh of such a name already failed before this PR (File name too long), so nothing that worked stopped working, except idempotent re-promote of an existing long base, which is now rejected.
Treehouse derives names with the 255 validator (naming.rs finish), so a very long repo directory name passes there and is rejected by the daemon with a clear invalid_params.
Acceptable edge.
