## (2) Symptom 2: does the new test exercise the server

Yes, and it is not a tautology; it is a server-side pin of an assumed client sequence.
unlink_open_nlink109.rs:17-24 sends CREATE, RENAME to `.nfs.silly`, GETATTR (nlink 1), LOOKUP of the old name (NOENT), REMOVE of the new name, GETATTR (STALE).
The test passes as written (cargo test -p cowfs-nfs --test unlink_open_nlink109, 1 passed).
Mutation 1: MemVfs getattr returns nlink 0 for regular files. Test FAILS at unlink_open_nlink109.rs:20 (left 0, right 1).
Mutation 2: MemVfs drop_name no longer decrements nlink. Test FAILS at line 23 (REMOVE no longer yields STALE).
Mutation 3: MemVfs skips the free branch on REMOVE. Test still passes, because STALE comes from `nlink == 0` in `live_dir`/node lookup, not from the free. This mutant is equivalent for the handle, so it is a limit of the test, not a defect.
Limits to note:
- Backend is MemVfs (common::memfs), not Core. The Core nlink-0 behaviour is cited from crates/cowfs-core/tests/core.rs:585, not exercised here.
- No real client is involved, so the sequence is the client's behaviour as read from source, not observed on the wire.
- The test cannot show that the client sends RENAME; only the mount test (mount.rs, ignored, needs mount_nfs) shows a `.nfs*` name via the real client.
