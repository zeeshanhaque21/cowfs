## What is right
Meta::replace_snapshot writes the same rows as remove plus rename in one redb transaction.
The victim is read from s.names, filtered against id, skipped by the dirty flush, and its root is queued in REAP with next_reap bumped. This matches Extra::Remove.
The in-memory session mirror is updated only after the commit.
Same-name is a no-op, a missing id is NoSuchSnapshot, a bad name is Invalid.
No on-disk format change.
Core::move_name: purge_live removes registry entries by id (retain on by_id), so it does not delete the new by_name entry that now points at the staged snapshot. I checked this because it was the likeliest bug.
The registry swap (by_name insert and by_id remove) is one critical section.
The removed flag is set under ns and flush locks and undone if the commit fails. The guards are scoped to the if block, so purge_live can retake them without deadlock.
Busy is checked before the intent is relied on and again at the commit. A Busy return in finish() happens before removed is set.
Test counts in the PR body match git (swap.rs tests 18 to 25, src/swap.rs 5 to 7, snapshot_replace 5 new, backend 28 to 28).
Changed assertions are explained and each is a consequence of the new order.

## Findings

F1 (doc, must fix): docs/v1-core.md is stale and the PR only touched its lock table.
Lines 152-172 still describe the old order: "3. remove the old target, 4. fork the staging snapshot, 5. remove the staging snapshot", and say "a snapshot name never disappears without a record that explains it".
Line 572 says "forks once and renames the staged snapshot into place".

Line 775 describes the durability trace as ending in "the victim unregister"; the trace point is now victim_removed before the replace commit.
Also docs/v1-daemon.md:94 and docs/warm-base-publication-123.md:25 still describe remove-old then fork. The latter is a historical note and may stay.
Fix: rewrite the "Snapshot replacement is crash-safe" section to the new 4-step order and the one-commit guarantee.

F2 (behaviour regression, decide or document in the user-facing doc): a failed replace commit leaves the OLD target live and writable with the intent pending.
Writes made to the target after the Err are silently discarded when the next open or recover_target rolls forward.
Before this PR the target was already removed at that point, so nothing could be written to it.
The PR documents it in the module doc and the PR body (lines "Cost of the uncertain case"), so it is not a hidden claim.
It is still silent data loss for the caller who saw an Err and reasonably believes nothing changed.
Suggested fix: on a commit error, re-read meta to learn whether the replace landed. If it did not land, roll back (drop the intent and the staging snapshot) instead of leaving the intent pending. Keep the pending intent only when the outcome is truly unknown.
At minimum, state this in docs/v1-core.md and the control API docs.

F3 (recovery semantics change, acknowledged in PR body): an image with the intent file, the old target and the staging snapshot now rolls forward on reopen.
This includes a real crash between the intent sync and the replace commit, where the caller never got an Ok.
An unacknowledged promote can therefore take effect after a restart, and writes to the old target made between the intent and the crash are discarded.
Both are bounded to the fork-plus-flush window and the target is normally a read-mostly base. No test exercises a real mid-sequence crash for this state, only fault-seam errors followed by reopen. Fault 3/4 do cover the same image, so coverage is acceptable.

F4 (low): during move_name with a victim, removed is true on the victim for the duration of the metadata commit (which can wait on a store fsync).
In that window the name still resolves to the victim, but operations on it fail. The PR says "exactly one of old/new answers to the name"; strictly, answers but may error for that window.
Not a data risk. Worth one sentence in the docs.

F5 (low, pre-existing pattern): an open racing between the open_handles check and removed.store can leave a handle on a victim that is then removed. This is the same race as unregister has; the meta doc comment already says handles keep reading until the reaper frees the tree.
