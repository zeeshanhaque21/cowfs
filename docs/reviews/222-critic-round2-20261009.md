Guard blind spots.
The guard is `CARGO_BIN_EXE_<bin>|(join|_bin|bin_path|binary)\("<bin>"` over crates/*/tests only.
I probed it with sample lines; it MISSES all of these shapes:
- `Command::new("cowfs-daemon")` (PATH lookup);
- a `const` name, then `.join(DAEMON)`;
- a loop variable, `for n in ["cowfs-daemon"] { sibling_bin(n) }` (the exact shape at real_project_acceptance.rs:509);
- names built with `format!` or `concat!`;
- `with_file_name("cowfs-daemon")` and `p.push("cowfs-daemon")`;
- `PathBuf::from("target/debug/cowfs-daemon")`;
- an env var naming the binary;
- a shell or python script under tests/ that runs a binary.
src/ `#[cfg(test)]` modules, benches/ and examples/ are not scanned.
None of these shapes reaches an undeclared binary today, so this is drift risk, not a current hole.
Cheap hardening: fail when a crate's tests/ or src/ contains the exact quoted name of another crate's binary without an edge.
That catches the PATH, const, loop, push and with_file_name shapes, and today it would only match crates that are already declared.

Note A (pre-existing, not introduced by this PR; it should be its own GitHub issue).
`cowfs_bin()` in spawned_server.rs:20 and sandbox_treehouse.rs:31 looks for `current_exe().parent().join("cowfs")`, which is `target/debug/deps/cowfs`.
Cargo puts the binary at `target/debug/cowfs`; the local target has `target/debug/cowfs` and no `target/debug/deps/cowfs`.
`sibling_bin` in real_project_acceptance.rs pops `deps` and is correct; these two helpers do not.
So the tests that need `cowfs serve` return early and report PASS in every run, full or filtered.
In the cli-full run, `a_second_process_can_drive_the_daemon_over_a_real_socket` passed in 0.017 s on macOS.
This is why the builder's negative control (a broken `cowfs serve --stub`) was caught only by the 19 `cowfs-cli::cli` failures and by no treehouse test in either arm.
The treehouse -> cli edge is still real.
Non-ignored acceptance tests drive `cowfs import`, `cowfs snapshot promote` and `cowfs snapshot list` through `Core::cli`, and they ran for 13 s to 31 s on macOS in CI.
For example, `the_core_daemon_publishes_base_refresh_and_leaves_no_worktree` took 13.2 s, and `every_implemented_mode_b_postcondition_holds_over_the_real_core` took 31.4 s.
`Core::cli` also returns `None` when the binary is missing, and some callers `unwrap_or_default`, so these tests can pass silently too.
That pattern belongs in the same issue.
It does not create a filtered-vs-full difference, because both arms behave identically.

## 6. Pre-registered rule

Rule: merge only if it beats a same-window full run on BOTH wall-clock and macOS job time, with nothing dropped.
- macOS job time: met in all three pairs (417 vs 1042, 318 vs 1022 and 268 vs 950 s). Each gap is far above the roughly 70 s noise of the round-1 forced-full pair.
- Wall-clock: NOT MET as written. The two green pairs win (755 vs 1804 and 353 vs 1811 s), and the break pair loses (1309 vs 1101 s) because its filtered arm queued 1035 s for macOS against 145 s. Wall clock without the queue wins all three (422 vs 1048, 346 vs 1029 and 274 vs 956 s), but that is a different metric from the one pre-registered. The green wins are also partly queue luck.
- Nothing dropped: met under the edge model, re-derived per test ID. It is not proven against edges the scan cannot see.

Still unproven:
- repeatability (one sample per arm);
- completeness of the edge model beyond the scan;
- behaviour under `-p` feature unification for third-party crates. Filtered builds unify features over the selected packages, not the workspace. Any difference would show up as a false failure or as changed behaviour, and push-to-main full runs are the backstop.
