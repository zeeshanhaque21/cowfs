## Findings

### F1 (major): temp name is predictable, so the "never chmods a swapped-in node" claim is not fully true
The temp name is `.cowfs-mknod-<pid>-<seq>`.
The pid is public and seq is a process-wide counter from 0, and readdir exposes the name.
Between `mknodat(tmp)` and `openat(tmp, O_PATH|O_NOFOLLOW)` another process with write access to the directory can rename or hard-link a node onto `tmp`.
`openat` then opens that node, `chmod_fd` chmods it, and the rename puts it at `name`.
For a hard link to a victim file this chmods the victim, which is the same class of bug as #211, only narrower.
No fstat of the opened fd checks that it is the fifo, socket or device just made (type, rdev, nlink == 1).
The new tests only swap at `name`, never at the temp name, so this is untested.
Fix: use a random temp name (getrandom, 128 bits).
Optionally also check `fstat(fd)` type and nlink after the open.

### F2 (minor): crash leaves a stray temp node, and a stale one can cause a spurious EEXIST
If the process dies between `mknodat(tmp)` and `renameat`, `.cowfs-mknod-*` stays in the directory.
It is visible to every reader, since only `.cowfs-swap` is in the snapname RESERVED list.
After a restart, a reused pid with seq 0 hits EEXIST on `mknodat(tmp)`, so mknod fails with Exists although `name` is free.
There is no sweep.
Random names (F1) make the collision go away.
The leak stays, so either reserve the prefix in readdir or sweep at open.
Failure paths inside the function do clean up (`unlinkat(tmp)` on any error).
That is fine.

### F3 (minor): RENAME_NOREPLACE unsupported gives EINVAL instead of a fallback
`renameat2` with RENAME_NOREPLACE is the only path now, on ACL parents and on hosts with no private umask.
Filesystems without NOREPLACE support return EINVAL, so mknod fails there.
The old code did mknodat plus chmod by name and worked.
This is low probability, because ACL-capable filesystems nearly all support NOREPLACE.
It is an unmentioned behavior change.

### F4 (minor): chmod_fd needs /proc
It goes through `/proc/self/fd/N`.
In a container without /proc the ACL fallback now fails.
There is precedent: src/lib.rs:212 already uses it.
Not a blocker, but state it.

### F5 (info, macOS)
`mknodat` is Linux only (sys.rs:215).
On macOS `mknod` is unsupported, and the whole native conformance mknod group SKIPs ("needs mknodat, which only Linux has"; reproduced locally on the PR branch and on main).
So `mknod_private`'s non-Linux arm is dead code.
Its comment ("Where mknodat exists but the descriptor chmod does not") describes a platform that does not exist, so it could be a plain `Err(NotSupported)`.
It cannot cause a umask regression in practice.
CI mac "pass" says nothing about this PR, since the fallback never executes there and the tests are `cfg(linux)`.
RENAME_EXCL and the macOS arm of `renameat` are irrelevant here.

### F9 (correct, checked)
- Control flow: `exact` is false whenever `mode_may_change` is true, so the ACL path always goes private. When there is no ACL and a private umask exists, the fast exact path is unchanged. The old trailing `fchmodat(name)` is gone, so no chmod by name remains.
- `mode_may_change` is now evaluated before creation. An ACL set between check and create is a theoretical gap, and equally so in the old code.
- Mode: the temp node is created with type | 0o600 and chmod'ed to the exact mode, including setuid/setgid/sticky. Umask and ACL are applied at the temp creation and then overridden by chmod, matching the old contract. The default ACL mask entry is not re-applied (chmod on a node with an ACL sets the mask from the group bits). This is the same as the old behavior.
- Error mapping: EEXIST comes through the rename and maps to Exists. EPERM from device mknod comes from `mknodat(tmp)`. The cleanup `unlinkat` result is ignored, which is fine.
- TOCTOU chmod vs rename: chmod is on an fd bound to the inode and the rename moves that same inode, so no race at `name`. Only the F1 window (the temp name) remains.
- Scope: two files, no creep.
- The `host` rdev is passed through unchanged. The temp mknod uses `(ty_mode & !MODE_MASK) | 0o600`, which keeps the type bits correctly.
