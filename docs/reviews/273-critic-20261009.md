## B. require_treehouse! semantics

- `CI` set to any non-empty value, including the string "false", counts as required.
  Acceptable (every CI provider sets CI=true; nobody sets CI=false deliberately), but worth knowing.
- `CI=""` or unset: optional. `COWFS_REQUIRE_TREEHOUSE` unset, "" or "0": optional; anything else: required.
  Matches the test table in `the_requirement_follows_the_environment`.
- An unusable binary (present, fails --version) also panics when required (fails closed, good).
- Mutation on the cachyos box: I restored the old macro, 5 tests ran, 2 failed (a_missing_treehouse_fails_the_test_when_ci_is_set and ..._explicitly_required).
  The brief expected 3 of 5; the real number is 2, because the skip test, the env-table test and the found-binary test are not sensitive to the macro body (the env table fails if `treehouse_required` is broken instead).
  The probe runs the real macro in a child of the same test binary with env_clear and PATH="", so it is not a copy.
  Note: an empty PATH makes split_paths yield one empty entry, so the lookup tries ./treehouse relative to cwd; harmless here (crate dir has none) but the probe should also set current_dir to the tempdir.
- Old treehouse on a dev machine: the cachyos box has ~/.local/bin/treehouse v2.0.0.
  With the PR, with or without CI set, 13 of 15 sandbox_treehouse tests fail with `unknown flag: --json`.
  This is pre-existing (find_treehouse returns Ok for any binary that answers --version) and not caused by this PR, but the PR's message "skip on a dev machine" is wrong for an old binary: it fails, not skips.
  Suggested follow-up: in find_treehouse parse `--version` and return `TreehouseMissing::Unusable("need >= 3.1")` below 3.1.0, so the gate skips (dev) or fails with a clear reason (CI), instead of 13 confusing failures.

## C. mode_b.rs slot-leak fix

- Commit 28ba955 replaced the old success-path release with `guard.keep()`; the PR adds `th.return_slot(&slot, true, guard.lease_id())?` before `keep()`.
- Success path: build ok, slot returned once, guard disarmed, no double return.
- Build failure: `?` leaves the guard armed, Drop returns the slot (unchanged, best effort).
- Return failure on the success path: `?` propagates with the guard still armed, so Drop makes a second best-effort return.
  Acceptable (error is surfaced, second attempt cannot hurt, drop never panics), slightly untidy.
- Non-build paths (`(None,_)` and `--slot`) are untouched.
- Behaviour change callers may notice: `BaseRefreshed.slot` now names a returned (available) slot, with built_in_slot true. Same as before 28ba955.
- Mutation on the box with the real treehouse v3.1.2 binary: PR passes base_refresh_runs_the_build...; removing the added line fails it with "the build slot was returned: ... status leased".
  So the test now guards the leak, and the fix is correct.
