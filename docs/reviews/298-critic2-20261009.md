## Can the re-read call a landed replace "not landed"?
No, not by construction.
replace_did_not_land requires id old to be named target AND id new to be named staged.
A landed replace renames id new to target and deletes id old in one transaction, so both conditions cannot hold afterwards.
The test is id-based, so a name that was reused cannot fool it.
The staging name is reserved, so no other writer can put id new back under it.
Meta::durable_snapshots opens a fresh redb read transaction on the file, not the session mirror, so it sees a commit that succeeded on disk even when the session was never updated.
That matters for the case where the commit succeeded but Err came afterwards: db.rs has an "after the batch commit" fault, and move_name also has a post-commit snapshot_by_id that can return Err.
In both, the re-read shows the replace landed, the intent stays, and open rolls forward. Correct.
Real I/O failure of wtx.commit(): redb 4.3.0 latches io_failed and later reads return PreviousIo.
durable_snapshots then errors, is_ok_and gives false, and the intent stays. Conservative, which is the safe direction.
The residual theory is an fsync error on the final god-byte write that redb reports but that still reached disk, followed by a read that works.
redb latches on write failure and checks the latch on reads, so I could not build that sequence. Label this as not proven impossible, only not constructible from the source I read.
Even then the rollback's unregister would hit the same latched backend and fail, and its result is ignored.
The real cases the rollback now catches are errors before anything is written: the before_sync hook failing (run_hook), begin_write failing, a NodeWriter error, or a caught panic. Re-reading shows old untouched, so rollback is right.

## Does the re-read race with other writers?
Only in the safe direction.
Another thread that renames or removes the old target, or the staging snapshot, between the failed commit and the re-read makes the check false, so the intent stays. Same as before F2.
The read is a point-in-time snapshot; there is no check-then-act on it, because unwind re-checks the registry (snap_by_name(target).id == old.id) and rollback is idempotent.
I found no path where concurrency turns "landed" into "not landed".
