# Critic report round 2: PR #220 (swap recovery, issues #176 and #177), head 9f8e27e

## Verdict: BLOCK (cross-name staging collision loses a pending tree; PR body claims such targets are refused, they are not)

The round 1 finding is fixed: a target named `base.tmp` now rolls forward after a fault past the point of no return and a reopen.
The new data-loss path below is the #177 mechanism itself, reached through a second name instead of a retry of the same name.
It is pre-existing on main in mechanism, but the PR body states it cannot happen ("such a target cannot even get an intent file ... so the swap is refused"), and that statement is false.
The task required such targets to be refused before any destructive step; nothing refuses them.
Fix is small (see Fix).

## Blocking finding: two targets sharing a 200-char prefix share one staging snapshot

`staging_name` keeps the first 200 chars of the target (crates/cowfs-core/src/swap.rs, `staging_name`).
Targets `A = "a"*200 + "1"` and `B = "a"*200 + "2"` are 201 bytes, valid snapshot names, and valid base names (`BASE_NAME_MAX` is 240, crates/cowfs-snapname/src/lib.rs:27), so both reach the swap through the daemon.
Their intent files are 206 bytes, well under the 255-byte file name limit, so both get an intent file.
The PR body's disclosure only holds for targets over 250 bytes.

Counterexample 1 (pending A destroyed by an unrelated import of B), probe `r2_staging_truncation_collision_import`:
1. `ingest_replacing(A, v1)`, then `set_swap_fault(4)` and `ingest_replacing(A, v2)`: old A removed, intent `swap-A` names staging `aaa...a.cowfs-swap0`, which is the only copy of `A-new`.
2. `ingest(B, v3)` with no fault: `recover_target(B)` finds no `swap-B`, then the "leftover staging" removal in `ingest_with` unregisters `aaa...a.cowfs-swap0`, A's only tree.
3. Reopen: `recover_intent(swap-A)` gets `NotFound`, removes the intent and sets `last_error` "neither A nor its staged tree exists".
Result: A is gone before and after reopen (`A before reopen None, after None`), B is fine.
The same removal is in `swap_snapshot` (promote_base), so a promote of B does the same.

Counterexample 2 (A rolled onto B's tree, B lost), probe `r2_staging_truncation_collision_both_pending`:
1. Both A and B exist; fault 4 on a replacing import of A (`A-new`), then fault 4 on a replacing import of B (`B-new`).
2. B's call removes A's staging as a leftover, stages `B-new` under the same name and leaves `swap-B`; both intents now name one staging snapshot.
3. Reopen: `swap-A` sorts first, `finish_swap` forks the shared staging (B's tree) into A, then `swap-B` finds it gone.
Result after reopen: `A=Some("B-new") B=None`.
This is the "rolling onto a tree other than the one the intent names" case the review asked about.

Live variant (by code reading, not run): the daemon serialises base_refresh per name (`REFRESHING`, crates/cowfs-daemon/src/import.rs:232), not across names, so two concurrent ingests of colliding names can each remove the other's in-flight staging snapshot with no fault at all.

Not a regression in mechanism (main also removed the leftover unconditionally, and main cannot inject the fault 4 state because `replace_with_staged` had no seams there), but the PR claims #177 is fixed and documents the collision as refused, so the claim and the code disagree on a data-loss path.

## Fix

Make `staging_name` injective: when the target is longer than the kept prefix, append a short digest of the whole target (for example the first 200 bytes on a char boundary, then `-` and 16 hex chars of a hash, then `.cowfs-swap0`).
Old intents name their staging snapshot explicitly, so stores written by main still recover; only the torn-intent branch derives the name, and the orphan sweep removes anything it misses.
Also, in `read_intent`, accept a record only when it ends in `\n` (the writer always writes it); that closes the torn legacy temp misparse below.
Do not add a `staged == staging_name(target)` equality check: an intent main wrote for a target over 200 chars records the old truncated staging name, so the check would refuse it and the sweep would then remove the only copy of its tree.
A staged-name sanity check, if wanted, must accept both the legacy and the new derivation.
Add the two probes above as regression tests and correct the PR body sentence.

### 2. Name hazards with the new prefixes

Intent files are `swap-<target>`, temps are `tmp-swap-<target>`; `intents()` takes every `swap-*` name and open deletes every `tmp-swap-*` name.
No user target can make its intent start with `tmp-swap-`, because every intent starts with `swap-`.
A target `tmp-swap-x` has intent `swap-tmp-swap-x` and temp `tmp-swap-tmp-swap-x`; a target `swap-y` has intent `swap-swap-y`; both roll forward (PR test plus code reading).
The torn branch now uses `strip_prefix`, so `swap-swap-y` derives `swap-y`, correct.
A target `swap-` is valid and has intent `swap-swap-`, distinct from all others.
`x.tmp` has intent `swap-x.tmp`; the legacy drop rule compares against `swap-x.tmp.tmp`, so it is not dropped.
Newlines, NUL and other control characters are refused by `validate_snapshot_name`, and names are UTF-8, so the two-line record cannot be forged by a name.
Long targets: the temp name is target plus 9 bytes, so targets of 247 to 255 bytes fail at temp creation, before step 3, and roll back (base names are capped at 240, so bases never hit this).
The 200-char staging collision is not refused at all: see the blocking finding.
Other root files starting `swap-`: none found besides intents (the PR body says `ino.rs` uses fixed names; not re-audited beyond a grep of `swap-` in core).

### 3. Legacy stores written by main

A complete old temp `swap-a.tmp` for target `a` records target `a`, matches `swap-a.tmp` exactly, and is dropped; correct, because the old writer renamed before anything destructive, so a temp never carried authority.
A complete old intent for target `a.tmp` is also named `swap-a.tmp` but records `a.tmp`, so it does not match and is recovered; the two cases cannot coexist since they are one file name.
So the exact-name rule does not delete a legitimate pending intent of a target named `a.tmp`.
Low, new versus main: a torn old temp whose cut falls inside the target line is read as a complete intent for a shorter name.
Probe `r2_legacy_torn_temp_with_staging_present`: store with `abc` and a crash-image staging snapshot `abc.cowfs-swap0`, plus a torn `swap-abc.tmp` containing `abc.cowfs-swap0\nab`.
Reopen creates a visible snapshot `ab` from abc's half-written staging tree (`list ["abc", "ab"]`, `ab/f` missing); main ignored that file and created nothing.
No user data is lost (abc keeps its old content), but a spurious partial snapshot appears, and if `ab` had its own unrecoverable intent, `finish_swap` would remove `swap-ab`.
It needs an old binary crashing mid-write on a filesystem that keeps a partial page, so it is low; requiring the trailing `\n` in `read_intent` (see Fix) closes it.

### 4. recover_target

Double roll forward: `finish_swap` forks only when the target is missing, so a second recovery only removes staging and intent (covered by `open_recovers_a_pending_swap_and_a_second_open_changes_nothing`).
Wrong tree: for one name, `finish_swap` takes both names from the intent, so it cannot roll onto another tree, except through the shared staging name (counterexample 2).
Finish failure: `recover_intent` returns the error except `NotFound`, `recover_target` propagates it, and both callers return before any removal, so intent and staging stay; correct.
`NotFound` is swallowed by design for a store whose staged tree is already gone; it also covers the "target already exists" return of `finish_swap`, which is the idempotent case.
Concurrency: a same-name race inside one Core is still possible from Core's side.
The daemon serialises base_refresh per name through the `REFRESHING` set (crates/cowfs-daemon/src/import.rs:232), but promote (`handler.swap`) takes the `HolderGuard` lock, not that set, so by code reading (not run) a same-name promote racing a base_refresh is not excluded by it.
Cross-name races remain (blocking finding).
Store `LOCK` flock is held for the Core's life, so another process cannot interleave.

### 5. Orphan sweep

Runs in `recover` after every intent is processed, inside `Core::open`, under the store flock.
`named` is rebuilt from the intent files left after recovery, so a failed recovery still protects its staging snapshot.
The match is `is_staging` (`contains(".cowfs-swap")`), which `validate_snapshot_name` refuses in user names, so no user snapshot can be swept.
Ordering is correct.
