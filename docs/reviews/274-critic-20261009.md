## 1. Production-path safety (feature off)
Every changed line in non-cfg'd code:
- `Io::remove_file`: `std::fs::remove_file(path)?` then a `log_data` call that compiles to an empty fn (the closure is dropped unevaluated), then `Ok(())`. Error and `NotFound` handling is identical: the error is returned untouched, so each caller's own `NotFound` arm (discard) behaves as before.
- 5 call sites swapped from `fs::remove_file` to `io.remove_file`: `create_pack` failure cleanup (`let _`), `save_torn` write failure (`let _`), sidecar pruning (`.is_ok()`, then the same `sync_dir`), `index.cix` removal (`?`, then the same `sync_dir`), `discard` (same NotFound arm). Ordering relative to the surrounding fsyncs is unchanged line for line.
- `copy_batch`: `target.write_all_at(&raw, c.len)?` became `g.io.write_at(&target, &pack_path, c.len, &raw)?`. Without the feature `write_at` is `file.write_all_at(buf, off)?; Ok(())`. Same offset, same bytes, same position in the loop, no new fsync, no extra copy of `raw` (the `to_vec` is inside the lazy closure).
- Only cost: `pack::pack_path(g.dir, c.to)` is evaluated eagerly (a `format!` plus `join`, about 2 allocations) for every record copied, because the path is an argument and not a closure. Nit, not a blocker: compaction is dominated by the read and pwrite, and `put` already builds the path the same way at `store.rs:1056`. Hoisting it out of the loop (it is constant per `c.to`) would remove it.
- Alloc test: `fsio::alloc_tests::write_at_allocates_nothing_without_a_log` passes on the box. It covers `write_at` only; there is no allocation test for `remove_file` (it allocates nothing: the closure is only called when a log is active) or for `copy_batch` (it allocates the path, above).
- Full `cargo test -p cowfs-store` passes with and without `--features fault-injection` on the box (the dev-dependency self-edge turns the feature on for test builds either way, so tests never exercise the feature-off code; the lib build itself is exercised by the seam script and CI).

## 2. Model fidelity
- Unlink rule: a gone file needs `p < k` and a later dir fsync of the same directory (`packs` vs root, per-directory now, was a single global value). Otherwise a coin flip. A cut with the unlink itself in flight (`p == k`) is also a coin flip. That matches ext4/xfs: an unlink is durable only after the directory fsync, and an un-synced unlink may or may not persist. Survivors still get their earlier data ops applied.
- Small imprecision: `unlinked` keeps the last unlink position per name and `gone` removes the file for the whole replay, so a name unlinked and then rewritten later in the same log would stay absent. Pack ids are never reused and nothing here rewrites an unlinked name, so it is conservative and unreachable today.
- `LogOp::Rename` skip: true. Only `write_whole` renames (ack, wm cut sidecar, `index.cix`; verified by grep). A real rename is atomic (old or new, never torn), and the model gives old before the `Whole` op and new after.
- Pre-existing wart, harmless: callers call `io.log_whole` BEFORE `io.write_whole`, while the doc comment of `log_whole` says "after the real one". So for a cut inside `write_whole` (tmp create, tmp fsync, dir fsync) the model shows the new content, never the old. The old-content image is produced by the cut at the op before the `Whole`, and no other file changes in between, so no coverage is lost. The comment is wrong and should be fixed.
- `LogOp::DirSync` for the root directory is keyed by directory name and mapped to `.` by anything not named `packs`. Fine.

## 4. Fault-seam script: `crashmodel` needle is VACUOUS
- Experiment on the box: release `cowfs-daemon` built WITH `--features fault-injection`: `crashmodel` hits = 0 (`oplog_start` = 1, `C7D_EXIT` = 1). The daemon never references `crashmodel`, so the linker drops it. The needle cannot trigger with the feature on, so it would also pass if the module were compiled in.
- The PR body and the script comment say "no positive control, builder explains". Honest as far as it goes, but the check protects nothing. `count_bin` ORs the three needles, so the existing `rel_on > 0` positive control passes on `C7D_EXIT`/`oplog_start` alone, which can mislead a reader into thinking `crashmodel` is controlled.
- What actually protects the gate: `pub use fsio::LogOp` is itself `cfg(feature)`, and `crashmodel` imports it, so removing the `cfg` from `pub mod crashmodel` fails to compile (E0432, tried on the box). That is real enforcement, the grep is decoration.
- The rlib is a usable alternative: `grep -ac crashmodel libcowfs_store.rlib` gives 10 with the feature and 1 without, so a strict `== 0` does not work there either. Suggest dropping the needle, or replacing it with the compile-fails argument in a comment. Not a blocker.
