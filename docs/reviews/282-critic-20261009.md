## is_root() call sites (6 in the PR, 7 on main)
The old check was uid 0 of /proc/self. The new one is a mode-0 open probe (CAP_DAC_OVERRIDE).
- Line 560 (EACCES on a mode-0 file): needs DAC bypass. Correct, and more correct than before.
- Lines 788, 875, 890 (access, default_permissions, owner write of read-only file): all are DAC-bypass questions. Correct.

## A. Persistent worker correctness
- Jobs routed through the worker are only mkdirat and mknodat with explicit modes (lib.rs:274, 327).
  create (O_CREAT, lib.rs:244), symlinkat, linkat and temp files stay on the calling thread. Confirmed by reading every call site.
- A job cannot change the worker's cwd or root: the closure only holds a dup of the dir fd and the name.
  The unshared fs_struct is private to the worker.
- Panic: catch_unwind turns it into an io error and the worker lives. A unit test covers it.
- Deadlock: a job cannot call back into PathVfs (it only sees an owned fd and bytes). The worker sits in State under the PathVfs Mutex, so jobs are serialised exactly as the old spawn-per-call was (the lock was held across the spawn before too). No new contention class.
- Many threads: 8 threads x 2000 mkdir through an Arc<PathVfs> on the box, all correct, modes exact (0777 with process umask 0022), 625 ms in a debug build at load 12.
- Drop: joins the thread after dropping the sender. State is dropped by the last Arc, so there is no leak on clone. A test checks /proc/self/task for the tid.
- N1 (fork, latent regression): after fork() the child has the channel but not the worker thread. Counterexample built on the box: warm the worker with one mkdir, fork, mkdir in the child: the child hangs forever (killed by SIGALRM, termsig 14). The old spawn-per-call code worked in a forked child.
  I grepped the repo (crates, scripts): no fork without exec, no daemonize, no pre_exec. Command spawns exec. So nothing hits it today.
  Suggest one line in the UmaskWorker docs: "not fork-safe: do not use PathVfs in a forked child". An optional hardening is to record the pid at start and drop the worker if it differs.

## B. Umask leak (independent poller)
Python 3 (`-I`) poller reading /proc/<pid>/status and every /proc/<pid>/task/*/status during 20000 mkdir plus 5000 mknod, on the box.
22300 samples. The process line was always 0022. Only worker-thread entries ever showed 0000 (the thread that did unshare). No leak.
The PR's own test (3000 mkdir plus mknod) also passes on the box.

## C. Fallback when unshare is refused
Read of `start()`: a refusal at creation sends the error back, the thread is joined, and only EPERM/EACCES/ENOSYS/EINVAL is cached as permanent. Transient ones (ENOMEM) leave `live` as None, so the next call retries. This keeps the PR 266 rule.
Verified with a seccomp filter on the box (unshare returns an errno), test binary under strace:
- EPERM (1): 25000 creations succeed through the chmod fallback, finished in 0.94 s, refusal cached.
- ENOMEM (12): same creations succeed, strace shows 25000 unshare attempts for 25000 creations (retried every time, as designed), modes correct.
- N2 (test gap): UmaskWorker::start hardcodes detach_umask, so the permanent versus transient rule for the worker is NOT covered by a unit test (the injected-unshare tests cover the old with_private_umask path only). The behaviour is right today; a regression would go unseen. Worth a follow-up issue.

## D. The sudo -n root test
- What runs as root: the test binary of this same job (current_exe), re-run with `--exact special_files_through_mknod --ignored`, with env COWFS_TEST_AS_ROOT=1 set through `sudo -n env`. Nothing downloaded, nothing else.
- Files: the Fixture uses a tempfile TempDir (under /tmp, since sudo resets TMPDIR) and a FUSE mount inside it. It cleans up on drop. A hard failure could leave a root-owned tmp dir, which is acceptable for a test.
- Not a silent pass: the child asserts it holds CAP_MKNOD, the parent requires exit success, "1 passed" in the output and no "SKIP" (Fixture prints SKIP when FUSE is unusable). If sudo works but the child is not root, can_make_devices() fails the assert.
- On a dev machine with passwordless sudo it runs the test binary as root once. Disclosed in the docs comment. If sudoers restricts the command, the test fails loudly and does not skip.
- Missing sudo fails on GITHUB_ACTIONS and skips elsewhere. Reasonable.
- N3 (evidence): the PR body says the root branch is "UNVERIFIED until linux-fuse runs". It has now run: the linux-fuse log shows `special_files_through_mknod_as_root ... ok` (run 37967770594). The log does not show the child output, so it proves the safeguards passed. All 8 checks are green.
