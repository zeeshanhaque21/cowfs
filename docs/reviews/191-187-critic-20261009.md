## 2. Store format safety (highest risk): PASS

Trace of the version 3 upgrade:
- `Tx::new_child` and `new_child_at` set `*self.special |= kind.is_special()` (tx.rs 230 and 291).
- `Inner::commit` (db.rs, the only code that writes tree nodes; the other begin_write sites write only inode reservation floors, recovery counters and the reaper's REAP/NODES/REFS) inserts `meta["version"] = 3` in the same `wtx` that writes the dirty tree and `ino_reserved`, when `s.special` is set (db.rs 772), then `wtx.commit()`.
- Atomic by construction: one redb write transaction, two_phase_commit. A crash before the commit leaves no node and version 2; a crash after leaves node and version 3. There is no state with a special node and version 2.
- The flag is restored on a failed or panicking batch (db.rs 1048-1076). Test a_failed_commit_of_the_first_special_file_leaves_version_two injects a failure before the commit and proves version 2 and no node after reopen.
- `Tx` is constructed in exactly one place, and the field is mandatory, so the compiler guarantees no mutating path skips the flag.
- Session flag is initialised from the stored version on open (db.rs 1724) and is sticky: a store that once held a special stays at 3 (documented in the design doc; a fifo created and deleted in the same session also bumps; this is conservative, not a bug).
- `open_recover` rolls back to the previous redb commit, which is self-consistent (either before the bump, version 2 without nodes, or after it).

What an old build does with a version 3 store, proven in a scratch clone:
- I built the pre-PR code (0cfb7bf) and the PR code (64bd7ee) in scratch worktrees, created stores with the PR code (a plain store, a store with a fifo, a store with a char device) and opened each with the pre-PR code.
- Plain store (version 2, no special): old build opens, lookup works, `check` Ok. So a store that never held a special file stays byte compatible with old builds.
- Store with a fifo: old build returns `Format("format version 3, this build reads 2")` from `Meta::open`. Same for the char device store.
- Code path: db.rs `Meta::init` compares `version != FORMAT_VERSION` right after the magic check and before any inode record is read (db.rs 1677 on both sides). No write transaction happens before that check.
- The test in check.rs that "simulates" an old build by writing version 99 is a proxy only; the real old-build refusal above is the actual proof and I recommend the builder add it (even as a documented manual step).

New build on old stores:
- Version 2 store opens, `special` flag false, nothing changes until the first special file is committed, at which point it upgrades silently and irreversibly (no prompt, no backup). This is as designed; I flag it as a documentation point for the upgrade note in slice B/C user docs (non-blocking, N3).

fsck:
- `check` accepts versions 2 and 3, and reports a special inode in a version 2 store, a special with extents, link target, size or covered, and a record length that does not fit its type (decode enforces 86 for non-devices, 94 for devices).
- Core `special_nodes_survive_sync_fork_and_reopen` calls `check` after sync, after fork and after reopen with a fifo, socket and block device and passes; so a legitimate fifo is not flagged and nlink accounting works (generic `names == nlink` rule for non-directories).

GC and reaper:
- cowfs-gc and `live_blocks` walk extents and tree nodes, not inode records (`InodeRec::decode` is called only from `read::inode` and `check`). The reaper works on node ids. Device records of 94 bytes are therefore never decoded by GC.
- `drop_inode` releases chunks only for `FileType::File` (tx.rs 162) and deletes the inode prefix, so an unlinked device leaks nothing.

Hard-coded 86 assumption: `rg` for 86, 94 and INODE_LEN over all crates finds only types.rs (definition) and the check.rs tests. No other fixed-offset reader exists.

Snapshot, fork, rename of snapshots, import:
- Special inodes live in ordinary tree nodes; fork shares them. Core test proves fork plus independent unlink of one name.
- Snapshot rename (`Extra::Rename`) goes through the same `commit`; the version flag is session level, so it is unaffected. Not directly tested with a special inode, but there is no inode-level code on that path.
- Host import (`cowfs-core/src/import.rs` 248-262) still refuses fifo, socket and device sources with the existing message; unchanged and safe. ctl `treehash` maps all four new kinds to `Kind::Other`, equal on both sides.

Residual store-format notes (non-blocking):
- N1: the version stays 3 forever after the first special file; no downgrade tool. Fine, but say it in the changelog-equivalent doc.
- N2: until slices B and C land, FUSE and NFS adapters answer EIO or NFS3ERR_SERVERFAULT for any special node (`fuse/src/fs.rs` file_type wildcard, `nfs/src/convert.rs` ftype). The only creators are library users and tests (Core::mknod), so a version 3 store cannot arise from a mount yet; once B or C merges, a store mounted through the other adapter will show EIO for such entries. The design doc states this for slice A; keep the slice order B and C close together.

## 3. Semantic correctness

Reviewed against pjdfstest mkfifo/00.t and mknod/00.t (type f) as summarised in the design doc, and the Linux/macOS behaviour I know.
- Mode: `Core::make` masks with MODE_MASK (ns.rs 199); mknod_masks_mode proves 0o170644 -> 0o644 and 0o7777 kept. Umask is the client kernel's job (NFS client and FUSE kernel apply it before the call), so no umask at the Vfs layer is correct.
- nlink 1, size 0, blocks 0, one creation time, parent mtime and ctime move: pinned by mknod_fifo_attrs (the only check that looks at the parent times; shared `new_entry` path means the other kinds follow in MemVfs, and in Core all kinds use one `make`).
- rdev: cowfs canonical (major<<32)|minor, round trips through mknod, getattr, lookup and readdir_attrs including u32::MAX (check mknod_device_attrs_keep_rdev) and after reopen (Core test). Meta stores it as 8 bytes little endian in the 94-byte record. The 32-bit minor/major are lossless for the macOS (8/24 bit) and Linux (12/20 bit) encodings.
- Error ordering: mknod follows `create`: name validation (EINVAL, ENAMETOOLONG), then stale parent, NotDir, ReadOnly, Exists. Checked for Exists over file and dir, NotDir in a file, Stale, empty/dot/dotdot/slash/NUL names, and a name of NAME_MAX+1. Not checked: Exists over a symlink or a dangling symlink (pjdfstest mkfifo/00.t does this), and EEXIST versus ENAMETOOLONG precedence (cannot arise).
- Device permission policy (non-root -> EPERM) is decided in the adapters, not in `Vfs` or Core: design doc and the trait doc say so. Core and MemVfs let any caller create a device. This is consistent because the Vfs has no credentials, but it means the policy is untested in slice A and every future adapter must remember it. Flag for slices B and C (N4).
- unlink/rename/link/rmdir: pinned by special_hardlink_unlink_rename (shared inode, nlink 2 then 1, rename over a special replaces and drops nlink to 0, rename over a directory is IsDir, rename keeps inode) and special_dir_ops_error (rmdir NotDir, mkdir Exists).
- readdir type bits: special_readdir_kinds for `list`, and `readdir_attrs` kind+rdev for devices only. A fifo or socket entry in `readdir_attrs` is not checked (N5, small gap).
- chmod and times: special_setattr_mode_and_times (all four kinds, ctime bumps). chown does not exist in the Vfs.
- truncate: setattr size on a special is InvalidArgument (matches Linux EINVAL for truncate of a fifo) in MemVfs, Core and meta (`Invalid`). read, write and readlink are InvalidArgument as for a symlink.
- open: succeeds and pins the inode (special_open_release, special_unlinked_with_handle_survives: getattr works with nlink 0). The Vfs does not implement fifo I/O; the client kernel does. Correct for NFS and FUSE.
- xattrs on special nodes: the design says allowed, but no check covers it (N6).
- fallocate on a special node: main now has fallocate (see B2); MemVfs gives InvalidArgument; Linux gives ENODEV for a fifo. Out of scope here; mention to the #103 owner.

Strength of the 16 checks:
- They fail on a no-op implementation (reproduced: 16 red at 11d9760).
- Mutants I applied to MemVfs in the scratch clone: (a) mknod stores rdev 0: 4 checks fail (mknod_device_attrs_keep_rdev, special_hardlink_unlink_rename, special_setattr_mode_and_times, special_unlinked_with_handle_survives). (b) read of a special returns Ok(empty): special_io_is_invalid fails. Both mutants were killed.
- There are no special-specific entries in `Fault` or in `tests/mutations.rs` (FAST list unchanged), unlike the fallocate work; the "every fault is caught" machinery therefore does not cover mknod, and the existing shared-path faults only cover it by accident. Non-blocking, recommend 3 or 4 faults (rdev dropped, fifo read allowed, special unlink keeps nlink, parent times not moved) in slice D.
- The Posix and Cowfs level labels for the new checks are not backed by a native run, because PathVfs skips all of them (the design doc says so honestly). The "native control" cannot validate that ext4, btrfs or APFS agree (for example size 0, blocks 0, readlink on a fifo = EINVAL). N7.

## 6. The treehouse acceptance failure

Facts only:
- Test: `crates/cowfs-treehouse/tests/real_project_acceptance.rs` `the_acceptance_receipt_states_what_was_measured` (line 2383). It reads `acceptance.jsonl` from `COWFS_ACCEPTANCE_EVIDENCE` or `bench/out/ready-real-project/` and asserts it is not empty. The records are written by the other tests of the same binary.
- Therefore it depends on test ordering and timing inside one `cargo test` run (the siblings are slow and write at their end; this test is instant), and on whether that evidence directory already holds records.
- Reproduction, independent of this PR: I ran only this test on 64bd7ee with `COWFS_ACCEPTANCE_EVIDENCE` pointing at an empty directory. Result: FAILED, "the receipt is empty, so this run measured nothing at all", 0.00s.
- CI: it printed `ok` in the ubuntu job of run 37874201684 (head 64bd7ee, line "test the_acceptance_receipt_states_what_was_measured ... ok"), and the macOS and ubuntu jobs were green on the previous push; the main branch runs for c3c6fbd and c48e89b were still in progress at review time (the latest completed main run ce403b8 is green).
- Conclusion: not caused by PR 191 (the diff does not touch cowfs-treehouse); it is a test that passes or fails by scheduling and by what the run left behind. On a machine with many cores the fast test can run before any sibling writes a record. It should be fixed or made order independent by its owner; I did not touch it.
