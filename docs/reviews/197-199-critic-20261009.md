### 2. Reproduction

I reproduced the original flake on the new code's strategy.
I added a temporary probe (scratch only, reverted) that runs the old per-fault random search with ChaCha seeds 0..300 (seed as u64 little endian in a 32 byte array) for all six faults.
That is 1800 runs of 2000 cases each, in debug, 713 seconds.
Result: exactly 3 failures, all TruncateNoZeroFill, at seeds 60, 162 and 230.
These are the same three seeds the builder reported, so the failure is independently confirmed and the seed mapping matches.
Every other fault was detected on all 300 seeds.
Max shrunk length per fault across 300 seeds: LinkReplaces 6, ModeNotMasked 5, NoHardlinkNlink 8, ReadPadsEof 4, RenameNoReplace 6, TruncateNoZeroFill 8.
So the 12 op limit is never exceeded for the six faults, and the only flake mechanism is "not detected at all" for TruncateNoZeroFill, about 1 percent per run.
The new test file at the PR head passes locally: 4 of 4.

### 3. Mutation

For each of the six faults I replaced that fault's witness with a benign sequence inside `oracle_catches_broken_backends` and ran the test.
TruncateNoZeroFill, RenameNoReplace, LinkReplaces, NoHardlinkNlink and ModeNotMasked: the test fails with "<fault> survives its own witness".
ReadPadsEof: with a lone `Create` as the replacement the test still passes, because the post-Create tree check already catches the padding.
With an empty sequence or a lone `Mkdir` it fails with "ReadPadsEof survives its own witness".
So all six witnesses detect their fault.
The `Write` and `Read` ops in the ReadPadsEof witness are not what catches it; the code comment says so honestly (see N1).

### 4. Determinism or reduced probability

This is a real determinism fix for the gating test.
`oracle_catches_broken_backends` now has no randomness: it runs six fixed op sequences through `run` on a healthy `MemVfs` (must pass) and on the faulted one (must fail).
The random search is a separate test using `TestRunner::new_with_rng` with `TestRng::from_seed(ChaCha, [0x5a; 32])` and `failure_persistence: None`, so nothing is read from or written to a regressions file for that test.
`Config { cases: 2000, ..Config::default() }` sets cases explicitly, so `PROPTEST_CASES` cannot change it.
`max_shrink_iters` and similar still come from `Config::default()`, which reads `PROPTEST_*` env vars.
No `PROPTEST` env is set in `.github/workflows/ci.yml`, so this is not a CI risk.
The pinned seed is deterministic for a fixed proptest version (Cargo.lock has proptest 1.11.0) and strategy.
It will pass or fail the same way on every run and platform, and it passed on ubuntu and macos in CI.
The residual risk is one-time: a change to the `op()` strategy or a proptest upgrade can make the pinned seed miss a fault.
That then fails every time, not intermittently, which is the right failure mode, and the doc comment says to re-seed or add a witness.
The seed is not special: seeds 60, 162 and 230 miss TruncateNoZeroFill, so about 1 percent of seeds would fail the TruncateNoZeroFill search, and 0x5a repeated happens not to be one.
This is accepted since the witness already gates detection and the search is secondary coverage.
`memvfs_matches_oracle` (300 cases, healthy backend, default unseeded proptest with default failure persistence) is unchanged.
A failure there would be a real divergence, not a detection flake, so it is out of scope.

## PR 199 (fix/flake-treehouse-receipt)

### 1. Head and CI

Head is 937b48ab6f178fa79e5733575491879f295edae3, matching the PR.
CI run 37880382839 ran on exactly that head and finished `success` with all four jobs green, including check (macos-latest), which was pending earlier and has now completed.
I pulled the ubuntu, macos and linux-fuse logs: 0 lines with FAILED in each.
Ubuntu and macos both show `the_acceptance_receipt_states_what_was_measured ... ok` and `the_receipt_of_a_real_run_states_what_was_measured ... ignored`.
The PR is mergeable and clean against main.

### 2. Reproduction

Parent commit 3eb153b, old test alone on a fresh empty `COWFS_ACCEPTANCE_EVIDENCE` dir: fails with "the receipt is empty, so this run measured nothing at all" (real_project_acceptance.rs:2405).
A second run on the same dir passes, because the first run appended its own receipt-summary row, so the old test also satisfied itself.
New test at the PR head, alone, three fresh dirs (default mode, `COWFS_ACCEPTANCE_REQUIRED=1`, default mode again): passes each time, and writes 0 files to the evidence dir, so it no longer touches the shared receipt at all.
I did not run any heavy `#[ignore]d` acceptance tests.
The new `#[ignore]d` audit alone on an empty dir fails with "the receipt is empty".

### 3. Mutation

Each audit rule was disabled in turn, and the new test failed every time: warm-claim check off, required-mode skip check off, empty check off, no-outcome check off.
The new test therefore covers the four audit rules it claims to cover, in both modes.

### 4. Same code path as the real run

Partly.
The test builds its receipts with `record_typed_to`, which calls `write_record_to`, the same bottom writer that `record` and `record_typed` use, so row serialisation (`Field` types, JSON shape) is the real one.
The audit is the shared `audit_receipt` and `audit_row`, which are what the real-run audit and the write-time check use, so the rules tested are the rules applied.
The new write-time check lives in `write_record` (the wrapper), not in `write_record_to`, so the self-built receipts do not go through it.
No test exercises the `write_record` panic path: the new test calls `audit_row` directly.
I tried to mutate it away (replace the `audit_row` call in `write_record` with a no-op) and run the whole default test binary.
Five tests failed, but they are daemon and mount gates in my scratch environment, so I could not attribute them, and I did not run that mutation on an unmutated baseline.
Treat "nothing in the default suite fails if the write-time audit is deleted" as unproven rather than proven, and as a probable gap (see N4).
I checked all 22 `record(` and `record_typed(` call sites.
All carry an `outcome` field (three go through a `fields` or `manifest` vector that pushes `outcome` first), and none set a warm-base flag, so the new write-time panic will not break the heavy acceptance run.

### 5. The lost whole-run audit

The coverage loss is real and the PR states it plainly.
The default suite no longer audits the receipt a real run produced.
The replacement is the write-time row check (warm claims, missing outcome) plus the new `#[ignore]d` `the_receipt_of_a_real_run_states_what_was_measured`.
That test is not wired into any gate: it is not in `.github/workflows/ci.yml`, not in any script under `scripts/` or `bench/`, and is referenced only by its doc comment and `docs/verification/ready-real-project.md`.
Two properties are now checked only by a human running that command: "the receipt is not empty" and "no capability skip under `COWFS_ACCEPTANCE_REQUIRED=1`".
The skip-under-required property is not covered at write time: a `skipped-capability` row is legal at the writer.
Mitigating facts: the heavy acceptance itself is also manual and not in CI, and the old test only audited a real run if someone ran the whole file in the same evidence dir, which CI did not.
On the old code, CI passed only by sibling test order, as the PR says.
So the CI-visible loss is small, and the trade is acceptable, but the acceptance procedure now has one more manual step that nothing enforces.

### 6. COWFS_ACCEPTANCE_REQUIRED=1

Still fails loudly where it matters.
`audit_receipt(&skip, Mode::Required)` returns the "COWFS_ACCEPTANCE_REQUIRED=1 was set" error, tested directly, and mutating that branch away makes the new test fail.
The real-run audit applies `mode()` from the environment.
The new test passes under `COWFS_ACCEPTANCE_REQUIRED=1` because it passes the mode explicitly to both `Mode::BestEffort` and `Mode::Required` and does not depend on the env.

### 7. Scope and PR body

Diff is two files: `crates/cowfs-treehouse/tests/real_project_acceptance.rs` and `docs/verification/ready-real-project.md` (two table and prose edits that follow the rename).
The refactor into `audit_receipt` and `audit_row` and the removal of the unused `deadline` are inside the test being fixed.
Adding the write-time check is a behaviour addition beyond a pure flake fix, but the PR discloses it and it is the stated replacement for the lost audit.
The body is accurate: 3 of 3 old failures, new pass, mutation proof, the weaker-coverage sentence.
Trial merges with origin/main, PR 198 and PR 200: no conflicts.

## Non-blocking notes

N1. PR 197: the `Write` and `Read` ops in the ReadPadsEof witness are decoration; `Create` alone detects it. The comment is honest. Consider dropping them or noting that a read-based witness does not exist.

N2. PR 197: the pinned search is one seed, so it is a regression check, not exploration. If broader exploration is wanted, run a seed sweep on demand (an `#[ignore]d` test), which would also have caught the original flake earlier.

N3. PR 197: `witnesses()` lists 6 of about 25 faults. New faults from PR 198 or 107 will not be covered by this oracle test unless added by hand.

N4. PR 199: add a small test that `write_record` refuses a bad row (for example via `std::panic::catch_unwind` on a row with `warm_base_published: true` into a private evidence dir), so the write-time check, which is the stated replacement coverage, is itself under test.

N5. PR 199: `the_receipt_of_a_real_run_states_what_was_measured` is vacuous on a second run. It appends its own `receipt-summary` row (outcome measured) before it can fail, so a second run on an empty dir passes with a receipt containing only its own row (I observed fail then pass). It should exclude its own summary row from the emptiness check, or record the summary only after the audit passes. The old test had the same flaw, so this is not a regression.

N6. PR 199: wire the real-run audit into the acceptance command (a script or a final step in the documented procedure) so it cannot be skipped.

N7. Not verified: the five default-suite failures I saw in my scratch environment when I removed the write-time audit are unattributed. They are presumably daemon and mount gates that need built workspace binaries, but I did not confirm this against an unmutated baseline.
