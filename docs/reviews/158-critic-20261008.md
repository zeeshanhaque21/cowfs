## 1. Diagnosis: correct
Source: crates/nfsserve/src/nfs_handlers.rs lines 745-749 set `maxcount = dircount` for plain READDIR (only READDIRPLUS reads a separate maxcount).
Line 795 sets `budget = maxcount.saturating_sub(160)`.
With PAGE=120 the budget is 0, so the first entry is over budget, `written == 0`, and the server returns NFS3ERR_TOOSMALL (line ~822).
PAGE=300 gives budget 140.

## 2. Tests still page across the edits
Plain READDIR, PAGE=300.
`want = 300/24 = 12`.
Entry bytes for a 3-char name: 4 (bool) + 8 (fileid) + 8 (name padded) + 8 (cookie) = 28.
Budget 140 allows exactly 5 entries (the check is `> budget`, so 140 passes).
Dircount cost per entry is 23, so 13 would fit; byte budget is the binding limit.
Result: 5 entries per page, 8 pages for 40 files, page 1 has 5 (satisfies 1..39 and not eof).
READDIRPLUS, PAGE=300.
Helper sends maxcount = 2400 (common/mod.rs line 394), budget 2240.
`want = min(12, 2400/140 = 17) = 12`.
Dircount cap allows 13.
Each plus entry is at least 140 bytes, so roughly 12 per page (this is my estimate, not measured).
Result: page 1 has at most 12 entries, so at least 4 pages for 40 files.
The post-edit loop therefore crosses several pages in both modes.
Mutation reasoning (not run): the assertions are exact, so positional or index-based cookies would fail them.
Removing the first returned entry shifts later positions, which skips one survivor, and `count(n) == 1` fails for that survivor.
Removing a pending entry before the page boundary would likewise shift the next page.
Unstable cookies that re-list would trip the `unique.len() == all.len()` check.
No scratch mutation run was done; the claim rests on reading the assertions.
