## 3. Central question: test-only race, or can collect have it
Collect already handles the identical window: crates/cowfs-gc/src/lib.rs ~671-686 does `snapshot_by_id`, the between_lookup_and_walk seam, then `live_blocks_with_root` with `Err(NoSuchSnapshot) => continue` and `Err(e) => return Err(e)` (f501157, issue 83).
Source of the error: `live_blocks_with_root` (cowfs-meta db.rs ~2118) re-reads `s.snaps.get(&self.id)` under the session read lock and returns NoSuchSnapshot if removed.
After that point the root and a redb read txn are taken under the same lock, so the walk reads a fixed MVCC view and a later removal cannot fail an item.
So the only failing window is the root read, which both collect and the helper now guard.
Is the skip sound for the assertion? The race test (race.rs ~558-570) runs `collect`, then for every block in `parts.live()` asserts `store.get(blk).is_ok()`.
A snapshot removed before its walk has no root in the namespace, so its blocks are not referenced by it and need not exist.
A fork of it recorded its own root and is listed and walked separately, so shared blocks stay in the set via the fork.
Skipping can only drop blocks reachable solely through a snapshot that no longer exists, which collect is allowed to free.
Skip cannot fire for a snapshot that still exists, since NoSuchSnapshot means absent from `snaps`.
No false pass is introduced for any live snapshot; the check on surviving snapshots is unchanged.
Residual: the helper no longer asserts blocks for a snapshot removed in the window, but that is correct, not masking.
Conclusion: test-only race in the helper; collect has the same window and already handles it safely.
Caveat on strength: the helper's check is only as strong as the surviving snapshots, as before. Not a regression.
