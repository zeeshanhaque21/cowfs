# PR #250 critic (Refs #211, head cef56ac)

## Verdict: PASS WITH NOTES

No blocking counterexample found.
The swap race on the mknod mode is closed on Linux where `unshare(CLONE_FS)` is allowed, the umask never leaks, the probe is test-only, and CI on the exact head ran the race test for real (not skipped).
Two notes deserve follow-up issues: the default-ACL mode divergence (measured: `0o666` requested gives `0o640`; now inconsistent with `create`/`mkdir`, with the fallback path, and with the suite's exact-mode `mknod_masks_mode` check), and the same swap race still present in `mkdir`.

## (1) unshare(CLONE_FS) safety

- Umask isolation verified empirically: a thread did `unshare(CLONE_FS)` + `umask(0)` + `mknod(0o666)` and got `0o666`, while a second thread sampled the process umask 892,227 times and only ever saw `0o077`; the process umask after the join was still `0o077`.
- Kernel semantics agree: `unshare(CLONE_FS)` copies `fs_struct` for the calling task only and, unlike `CLONE_VM`/`CLONE_SIGHAND`/`CLONE_THREAD`, has no single-threaded requirement and needs no capability.
- cwd/root of other threads are irrelevant: the call uses `mknodat` on a borrowed dirfd, and the fd table is still shared (no `CLONE_FILES`), so the dirfd stays valid.
- Ordering is right: `umask(0)` runs only after `unshare` returned 0; on failure the thread returns `Ok(false)` before touching the umask.
- `cstr(name)?` runs on the caller thread before the spawn, so the spawned closure has no realistic panic source; a panic would still be converted to `io::Error::other` by `join().unwrap_or_else`, never propagated.
- Spawn failure (`EAGAIN` under `RLIMIT_NPROC` or memory pressure) goes through `spawn_scoped(...)?` and returns an error from `mknod`; it does not panic and does not fall back to the racy path.
  Note: falling back to the old path on spawn failure would trade a spurious `EAGAIN` for the disclosed race; returning the error is the safer default, so this is fine as is.
- Thread exhaustion / DoS: not possible from this code.
  `PathVfs::lock` (lib.rs:121) is a single `Mutex<State>` over the whole `PathVfs`, and `mknodat_exact` runs while it is held, so at most one mknod thread exists per `PathVfs` at a time, regardless of FUSE/NFS worker count.
- tokio: the work runs on a fresh std thread inside a synchronous `Vfs::mknod` call, so an async runtime around it is irrelevant (the calling worker simply blocks, as it already does on the lock).
- Cost: from the PR's figures, (1.3 s - 0.35 s) / 20,000 is about 47 us per mknod, a rough upper bound and not a measurement (the 20k loop also includes unlinks and contends with the helper thread's renames).
  `PathVfs` is a production backend (`crates/cowfs-daemon/src/backend.rs`), so this is on the daemon path; because it runs under the global lock, every other operation on that `PathVfs` waits for it.
  mknod is rare in real workloads, so a worker thread or pool is not warranted; flag only if a mknod-heavy benchmark appears.
- Optional, non-blocking: where `unshare` is refused, every mknod pays a thread spawn only to fail and then takes the fallback; caching the refusal in a `OnceLock` would skip that.
- Seccomp: Docker's default profile returns `EPERM` for `unshare` without `CAP_SYS_ADMIN` (PR claim, read from source; not measured by this critic), which hits the fallback cleanly.
  Unverified risk: a filter whose default action is kill (for example a systemd `SystemCallFilter=` without `SystemCallErrorNumber=` that excludes `unshare`) would SIGSYS the daemon on its first mknod instead of falling back.
  This applies to any syscall a sandbox forbids, so it is a deployment note, not a defect.
- User namespace: `CLONE_FS` needs no privilege, so the atomic path works there too.

## (2) Is the race really closed

- Yes for the mode: the requested bits are applied by `mknodat` itself, and no chmod by name follows on the atomic path.
- CI ran `mknod_race::mknod_mode_never_lands_on_a_node_swapped_in` on ubuntu in 4.439 s, so it took the atomic path (the skip returns in milliseconds).
- Attrs by name after creation (disclosed): a node swapped in between `mknodat` and `fstatat` is registered and its attrs returned.
  Not a regression: the same `fstatat` by name followed the chmod on main.
  It is the same outcome as a `lookup` racing an out-of-band rename in the backing directory, which `PathVfs` already tolerates for every operation; `register` maps the name to a node that really is there, so no stale mapping is created.
  The adapters pass the returned `Attr` through: FUSE `fs.rs:618` replies with it, NFS `adapter.rs:702` records it with `handed_out(Some(d.ino), &a)`; neither re-checks the kind it asked for.
  Through FUSE, the kernel's `create_new_entry` rejects a reply whose `S_IFMT` differs from the requested type with `EIO` and sends a FORGET, so no lookup ref leaks (from kernel source, not tested here).
  Through NFS, the client would get the swapped node's real handle and attrs, which is what a following `LOOKUP` would return anyway.
  Not a corruption path; the disclosure is accurate.
  Core (`cowfs-core`) has its own mknod and does not go through `PathVfs`, so it is unaffected.
- setgid parent: equivalent to before (from kernel source, not tested here).
  At creation the kernel strips `S_ISGID` via `mode_strip_sgid` in the same case (setgid dir, group-exec, caller not in group, no `CAP_FSETID`) where the old chmod would have dropped it.
- Default ACL (disclosed, but understated): measured in the VM with `setfacl -d -m u::rwx,g::r-x,o::---` on the parent, a requested `0o666` came out `0o640` on the new path and `0o666` on the old mknod+chmod path.
  Two inconsistencies follow that the PR body does not mention.
  First, `PathVfs::create` and `PathVfs::mkdir` still force the exact mode with `fchmod` (lib.rs:247, lib.rs:268), so in one directory a fifo gets the ACL-filtered mode while a regular file or directory gets the requested one.
  Second, a host where `unshare` is refused takes the fallback and still overrides the ACL, so the same request yields different modes depending on seccomp.
  Third, the suite's own contract is exact mode: `mknod_masks_mode` (special.rs:93) asserts `mknod(..., 0o7777)` returns `0o7777`.
  Run with a base directory carrying a restrictive default ACL, that check now fails on the atomic path where it passed before.
  CI has no default ACL on its scratch directories, so the conformance suite cannot see this.
  Why it still does not block: an exact mode under a default ACL is only reachable with a chmod after creation, which is the race being closed; no fd to the new node exists to `fchmod` safely.
  Recommendation: file a follow-up to pick one contract for all create paths (exact mode, or ACL-filtered like native), update `mknod_masks_mode` and the docs to match, and mention it in the PR body; not blocking for #211.
  No existing issue found (`gh issue list --search "default ACL"` and `"mknod mode"` returned nothing relevant).

## Out-of-scope finding: mkdir has the same swap race

`PathVfs::mkdir` (lib.rs:265-268) does `mkdirat(name, 0o700)`, then `openat(name, O_DIRECTORY|O_NOFOLLOW)`, then `fchmod`.
A directory renamed over the name between `mkdirat` and `openat` receives the requested mode, which is exactly the race this PR closes for mknod.
`mkdirat` honours the same per-thread umask, so the same `unshare(CLONE_FS)` + `umask(0)` helper would close it.
Not part of this PR; recommend a new issue (`gh issue list --search "mkdir race"` and `"mkdir chmod"` found none).

## (3) The probe

- Test-only: `host_can_make_devices` is called only from `crates/cowfs-vfs-path/tests/common/mod.rs:60` and `crates/cowfs-fuse/tests/conformance.rs:75`; `mknod_mode_is_atomic` only from `tests/mknod_race.rs`.
  Both are `pub` in the library, so they are reachable by downstream code, but nothing in production calls them.
- Cleanup: `force_remove_dir_all(&scratch)` runs whether the open or the mknod succeeded or failed.
- uid 0 without `CAP_MKNOD` and uid 0 in a user namespace both get `EPERM` from the kernel's `capable(CAP_MKNOD)` check, so the probe answers false; the PR's `unshare -r` run (main: 3 FAIL, branch: 16 run 0 failed) is the right reproduction of the user-namespace case.
- Minor: the scratch name is `.cowfs-mknod-probe-<pid>` with `create_dir`, so a leftover from a crashed earlier run with a recycled pid makes the probe fail with `EEXIST` and the harness panic at `expect`.
  Each test binary calls `run_suite` from a single test, so there is no in-process collision.
  An LSM denial returning `EACCES` instead of `EPERM` also panics the harness rather than falling back; acceptable for tests.
- `/proc/self` owner checks remaining: only `crates/cowfs-fuse/tests/mount.rs:27` (`is_root`, 6 call sites), as the PR body says.

- The mutation (MemVfs drops rdev) is plausible: `dump` compares whole `Entry` values, so any rdev mismatch fails the equality.
- Non-device nodes report rdev 0 on both sides, so no new nondeterminism.
- CI timings for the two `cowfs-core::model` tests: this head 3.1 s and 3.0 s (ubuntu), 2.8 s and 3.8 s (macOS); main run 37931022378 5.6 s and 5.5 s (ubuntu), 7.5 s and 6.6 s (macOS).

- `Fault::MknodDeviceDenied` plus `device_permission_denied_falls_back_only_without_privilege` pin both directions of the fallback, so the old uid guess cannot creep back unnoticed.
