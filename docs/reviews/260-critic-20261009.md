## Attack 1: is the fix right
Old cowfs_bin used current_exe().parent(), which is target/debug/deps, where only hash-suffixed cowfs-<hash> test artifacts live.
The built binary is in target/debug, so the lookup was always None and the tests skipped.
New sibling_bin pops one level and pops deps if present, so it handles the cargo test layout and the nextest layout (nextest also runs from target/debug/deps).
Release profile and CARGO_TARGET_DIR work because the lookup is relative to the test exe, not to a fixed path.
It would not find a binary in a different profile dir than the test, which is correct.
CI log of the exact head (run 37943244857): on ubuntu 1/2 a_second_process_can_drive_the_daemon_over_a_real_socket and provision_refuses_a_path_that_is_not_a_slot PASS at about 10.1s each, and the same pair PASS at 10.6s and 10.3s on macOS.
Before the fix these were 0.02s skips, so they now do real work.
Both negative control tests PASS on both OS families.

That failure is the correct direction.

## Attack 3: the two "bug fixes"
Exit 1 on a stale base is intended product behaviour.
cli.rs:453 is deliberate code (`Ok(if out.fresh { EXIT_OK } else { EXIT_ERROR })`) and base status is documented as a freshness gate, with docs/linux-namespaces.md relying on the fresh flag.
The test was wrong, not the product.
Mode 0700 on the socket dir is a deliberate security check in crates/cowfs-ctl/src/socket.rs:36 ("must be owned by you and have mode 0700"), and the dir is auto-created 0700 elsewhere.
A test-created dir at default umask 0755 legitimately trips it, so this is a test-only fix, not a usability bug.

The positive control the_cowfs_binary_is_built_beside_the_tests covers the deps-pop logic.
