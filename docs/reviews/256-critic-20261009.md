### (c) Fail-open risks

Not reachable for review: the platform/fstype code the questions concern is not in the PR.
Net effect of the PR as pushed is fail-open: the accepted-divergence gate (ordinal-worse positions not in the list fail the verdict) is deleted, so a new cowfs divergence at a worse position is no longer a FAIL.
Design notes for the rebuild, to check when real code lands:
- Accept only `fuse.cowfs` (or the exact subtype cowfs mounts with), not any `fuse.*`; `fuse.fuse-overlayfs` from the fixture would otherwise pass as a cowfs arm.
  Reject `fuseblk` (ntfs-3g, exfat) and bare `fuse` unless cowfs is shown to mount with that type.
- macOS: accept `nfs` only; reject `nfs4`, `smbfs`, `autofs`, `webdav`, unless cowfs serves that protocol.
- A receipt with `platform=linux` and fstype `nfs` (or `platform=macos` and `fuse.*`) must be INTEGRITY, not "either family".
- "Receipt without platform accepts either family" is a loosening for old receipts; acceptable only if old receipts cannot be replayed as new runs.
- "Platform unknown means all entries apply" cuts both ways.
  On main, a listed entry in a compared case that is not worse yields a COVERAGE reason (`bench/pjdfstest.py:1187`), so applying a macOS entry to a Linux run that lacks that failure is stricter.
  It is looser when the exact test, position and signature regex recur on the other platform: a macOS waiver then covers a Linux divergence.
  The rebuild should test both directions.

### (e) Derive keeps other-platform entries

Logic in the diff: `entries += [e for e in existing if e["platform"] not in ("any", platform)]` only when a platform is known.
With a platform, other-platform entries from `--out` are merged back, as claimed.
With no platform, every rule applies, and derived entries keep the rule's own platform tag, so nothing is re-tagged.
Existing entries in `--out` are not merged back in that case, so any entry this run does not reproduce is dropped (the same as before the PR).
Moot until the script imports.
