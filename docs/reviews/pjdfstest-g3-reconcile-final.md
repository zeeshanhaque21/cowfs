## The writer is correct on every path I could reach

`write_exclusive` stages in the **target** directory, opens the staged file with `"x"`, writes, flushes and `fsync`s, then `os.link`s it into place and unlinks the staged name.
`link` is the one creation call that refuses an existing name atomically, so there is no precheck-then-write window.
On `FileExistsError` it unlinks the staged copy and returns "already exists, so nothing was written".
On any other `OSError` it **keeps** the staged file and names it in the message.
Staging never happens in the input run directory unless the caller explicitly aimed the output there, which is refused first.

Measured refusals, all with true process exit codes:

| case | exit | evidence |
| --- | --- | --- |
| fresh isolated `--output` outside the run | **1** | FAIL, file written, complete JSON |
| default `reconciliation.json` already present | **3** | sentinel bytes byte-identical before and after |
| `--output` inside the input run | **3** | refused |
| `--output` equal to the run directory itself | **3** | refused |
| `--output` written lexically as `run/../run/x` | **3** | refused, because both sides are compared resolved |
| `--output` through a symlinked parent resolving into the run | **3** | refused |
| `--output` to an existing file outside the run | **3** | sentinel bytes intact |
| `--output` to a hard-linked name | **3** | both link names unchanged |
| `--output` equal to one of the raw streams | **3** | refused, and covered by a test |
| run without an `identity.json` receipt | **3** | "no runtime identity was supplied" |
| nonexistent run directory | **3** | refused, no write attempted |

I pre-seeded exact sentinel bytes in every clobber scenario and compared them with `cmp` afterwards.
Nothing was overwritten in any case, no staged residue was left on the `FileExistsError` path, and no file escaped my own directory.

The written analysis is complete and carries what it should: `state FAIL`, `exit_status 1`, `runtime_identity` with cowfs `st_dev 436209661`, `analysis.analyser_sha256` **`58309aec6f19dd88638e37d7f7152d6f`**, which matches the head's script byte-for-byte and is independent of any host checkout, input hashes for `cases.jsonl`, `identity.json`, `summary.json` and **all ten raw streams**, `tool_source_problems` empty, and the ordinal diagnostic retained.

## Blocker 1: without the pinned scripts the gate returns PASS

This is the serious one, and it is the exact hazard this whole gate has been built to exclude.

Same fixture, same records, same identity receipt, one variable:

| invocation | result |
| --- | --- |
| `--reconcile <run> --tool <pinned tool>` | **FAIL, exit 1**, 25 established regressions, 26 unpairable |
| `--reconcile <run>` with no tool at the default path | **PASS, exit 0**, 0 established, 170 unpairable |

I reproduced it three independent ways: through the CLI with and without `--tool`, and by calling `verdict()` directly with `tests_root=None`, which returns `state=PASS exit=0 established=0 unpairable=170`.

The mechanism is straightforward.
`verdict()` builds `profiles` only when `tests_root` is supplied or a record carries `script_text`.
A normal `cases.jsonl` carries neither, so with no tool cache `profiles` is empty.
`pair_case` then receives `profile={}`, falls back to its documented default blockers `["no script profile"]` so route 1 cannot fire, and in route 2 the check `key[1] in script_sites` is false for every operation because `script_sites` is empty.
So **every pair is rejected** and the established set is empty regardless of what the streams say.
With no established regressions there is no `DIVERGENCE` reason, and the only reasons left are `COVERAGE`, which by design has no exit effect.
The gate therefore reports success on a run that contains 25 previously established regressions.

This is reachable in ordinary use.
`--tool` is documented as optional, `cmd_reconcile` only sets `tests_root` when the tool directory happens to exist, and that directory is a gitignored cache under `<repo>/bench/out/ready-g3/tool`.
A fresh clone, a different `--repo`, or a cleaned cache all produce a silent `PASS 0`.
No `INTEGRITY` or `CAPABILITY` reason fires, because nothing checks that the evidence needed to establish identity was available.

The asymmetry is the tell: `validate_runtime_identity` will not accept a run whose filesystem cannot be identified, and refuses on eleven distinct conditions.
Here the *identity of the assertions themselves* is unavailable and the run is scored anyway.
A missing `tests_root`, or an empty `profiles` map, should be an `INTEGRITY` refusal, the same way a missing `identity.json` now is.

## Blocker 3: the staging write leaks an uncaught exception and the wrong exit code

`write_exclusive` wraps only the `os.link` in `try`. The staged write itself is not:

```
with staged.open("x") as f:
```

Three reproducible triggers, each producing a bare Python traceback and **process exit 1**, which the taxonomy reserves for `DIVERGENCE`:

| trigger | exception |
| --- | --- |
| `--output` is a symlink whose target is unwritable | `OSError: [Errno 30] Read-only file system` |
| `--output` parent directory does not exist | `FileNotFoundError: [Errno 2] No such file or directory` |
| `--output` parent is an existing regular file | `NotADirectoryError: [Errno 20] Not a directory` |

An output-path refusal is an integrity condition and must exit 3 with an `INTEGRITY` reason, consistent with every other refusal in this harness.
Instead the process dies with a traceback and an exit code that a CI script would read as a real filesystem divergence.
That is a harness failure masquerading as a `FAIL`, which is the inverted form of the fake-gate hazard and just as damaging to an exit-status-driven pipeline.

The same case exposes a second property worth naming.
`cmd_reconcile` computes `out = Path(args.output).resolve()`, and `resolve()` follows symlinks, so `--output` may name a path in one directory and be written somewhere else entirely.
The inside-the-run check is applied to the resolved path, so redirection **into** the run directory is correctly caught, which I verified.
Redirection anywhere else is silent.
In my run nothing escaped, because staging to `/` was refused by the read-only root, but on a writable destination the writer would create the file there.
`write_exclusive`'s docstring says "staged in the target directory", which is true of the resolved target and not of what the caller asked for.

Wrapping the staged write in the same `try`, and refusing a `--output` whose final component is a symlink, would close both.

## Blocker 4: `source_head` is false attribution by construction

`analysis_provenance` records `analyser_sha256` correctly and that is the authoritative binding: mine reads `58309aec6f19dd88638e37d7f7152d6f`, the actual bytes of the script that produced the file, with no dependence on any checkout.

`source_head` beside it is not reliable.
It comes from `git -C <repo> rev-parse HEAD`, and `git` searches **upward**, so it reports whatever repository encloses the default `--repo` path, whether or not that repository contains the script.
My own run recorded:

> `analysis.source_head`: `025bde2f3ccea609f54edf67a9d86d66d28abeca`

That is my reviewer lease's HEAD.
The analyser's actual revision is `22340a9d`, and the two have nothing to do with each other.
For a git archive with no `.git` the same call returns an empty string, which reads as "revision unknown" rather than "no enclosing repository".

A field named `source_head` inside a provenance block will be trusted as the revision of the code that produced the file.
It should either be dropped in favour of `analyser_sha256`, or recorded together with `git rev-parse --show-toplevel` so a reader can see *why* it resolved, or explicitly labelled advisory.
