## 1. A: EXPORT returns an empty list

- Nothing legitimate needs EXPORT.
- `Mount::new` (crates/cowfs-nfs/src/mount.rs) passes `localhost:/<export_name>` straight to `/sbin/mount_nfs` and never asks the server.
- Apple's userland mount_nfs (apple-oss-distributions/NFS tag NFS-343.100.5, mount_nfs/mount_nfs.c, 3232 lines fetched) contains no MOUNT RPC calls (no clnt_call, no MOUNTPROC).
- The kernel does the MNT itself.
- No production code in the workspace speaks the MOUNT program.
- Only tests and the spikes/ vendor copy, which the workspace excludes, do.
- showmount against the server now lists nothing, which is the intended effect.
- The reply is a success header followed by `false` ("no first entry"), which is a valid empty export list in XDR.
- Completeness: `rg export_name crates/nfsserve/src` shows the only remaining handler use is the MNT path prefix match at mount_handlers.rs:91.
- No other MOUNT reply serializes the path (there is no DUMP handler that lists it).

## 2. B: one-shot gate

- On main the gate already gave the root handle to the first MNT and already ignored UMNT.
- The real behaviour change is that a repeat MNT from the claimer's source address is now refused.
- The other change is the `RootHandleTaken` diagnosis in `Mount::new`.

### Race

- An attacker that knows the path can still win the first MNT, exactly as before.
- The fix makes the loss loud: `mount_nfs` gets MNT3ERR_ACCES and `Mount::new` returns `RootHandleTaken`.
- `Mount::new` then sets `mount.server = None`.
- Dropping `Server` calls `runtime.shutdown_timeout(5s)`, which drops the accept loop and every connection task.
- The attacker's connection dies, and its handle is useless afterwards, because each server has a fresh MAC key and a fresh path.
- Residual (NOTE, pre-existing, not introduced): until that teardown, the attacker has full read and write access to the Vfs with the daemon's rights.
- That window is milliseconds to seconds (the mount_nfs exit plus up to 5 s of shutdown).
- It is enough for real damage, and any writes persist.
- "Fails loudly" detects the theft; it does not undo it.

### Path exposure

- The path is still in mount_nfs argv while it runs, as lib.rs documents.
- It is also in the mount table afterwards (documented, and the gate is closed by then).
- I did NOT verify whether another uid can read mount_nfs argv on current macOS.
- The docs assume it can, which is the safe assumption.
- The real fix, keeping the secret out of argv (prior review F2), is still open.

### rearm_mount, restart, multiple mounts

- Only Rust code holding the `Server` can call `rearm_mount`.
- No RPC reaches it, and nothing in cowfs-daemon or cowfs-treehouse calls it, so a client cannot reopen the gate.
- UMNT (proc 3) and UMNTALL (proc 4) do not rearm it (tested).
- A daemon restart creates a new `Server` with a new path, gate and key, so old handles become STALE or BADHANDLE.
- cowfs-daemon mounts each export through its own `cowfs_nfs::Mount::new` (crates/cowfs-daemon/src/mounts.rs:146).
- So each mount has its own server, path and gate, and gates do not interfere (`two_servers_never_answer_each_others_mnt`).

### Minor notes

- Misattribution: `RootHandleTaken` is chosen whenever mount_nfs exits non-zero and any MNT was refused.
- If mount_nfs failed for another reason after the legitimate MNT succeeded, and a late attacker MNT was refused, the error wrongly blames a stolen handle.
- That case is rare, and it still correctly signals that a second MNT happened.
- Silent attempt: if mount_nfs succeeds while `mnt_was_refused()` is true, someone else tried to mount the secret path.
- Nothing logs that, and an `eprintln!` would make it a useful intrusion signal.

## 3. C: eviction ignores NULL calls

- `served` now increments in two places only: in `fh_or_fail` after `fh_to_id` succeeds, and on a successful MNT.
- `fh_or_fail` holds the only `fh_to_id` call in nfsserve's handlers, so every handle-bearing procedure is covered.
- `handle_rpc` still updates `active` for every call, so idle-timeout behaviour is unchanged.
- An attacker without a handle keeps all its connections at served=0.
- At the cap the victim is therefore the served=0 connection with the oldest `active`, never a connection that already used a handle (verified by the new test).
- The attacker cannot raise `served`: NULL, EXPORT, UMNT, a refused MNT and forged handles do not count.
- A valid handle requires both the secret and the gate.
- At the cap the server never refuses or hangs a newcomer.
- `enter` always kicks the connection with the lowest (served, active) and admits the new one, even when every connection is "protected".

### Residual (NOTE, reasoned from Apple source, not tested)

- A kernel NFS socket has served=0 until it sends its first handle-bearing call.
- During the initial mount that gap is wider than a reconnect.
- The kext first opens the NFS socket and checks it with a NULL ping (`nfs_connect_search_ping`, kext nfs_socket.c:1042).
- Only then does it open a separate MOUNT socket for the MNT, and that new connection triggers `enter`.
- A local user who knows only the port can hold the other 63 connections and keep them fresher with nonstop NULL calls.
- They tie with the kernel socket at served=0 and win the `active` tie-break, so the kernel NFS socket is kicked mid-mount.
- mount_nfs then retries mount(2) once (default foreground retrycnt is 1, after a 5 s delay, on errors like ECONNRESET or ETIMEDOUT).
- If the first attempt's MNT already claimed the gate, the retry's MNT is refused.
- The result is a mount DoS, not handle theft.
- main behaves the same here and worse in steady state, where the flood's NULL count outranked the client.
- So this is not a regression.
- The same sub-millisecond window applies to a reconnect of a running mount, but a hard mount just reconnects again.
- A possible follow-up: break ties at served=0 by connection age rather than `active`, or count the NULL ping on a connection that later presents a handle.

### Pre-existing, not in the diff

- `enter` removes connections idle for over an hour from `live` without kicking them, so they stop counting toward the cap.

## 4. Claims in the PR body

- The claim that `install_signal_cleanup` is deliberately not wired in the daemon is accurate.
- crates/cowfs-daemon/src/daemon.rs:254-259 explains why, and main.rs never calls `install_backstop_signal_cleanup`.
- The claim that SIGHUP is unhandled is accurate.
- main.rs `watch_signals` registers only SIGINT and SIGTERM.
- So SIGHUP's default action kills the daemon without unmounting, like SIGKILL.
- The claim of a hard mount with no dead-server timeout is accurate.
- `MountOptions::default()` has `soft: false`, the option string uses `hard`, and the daemon uses the default.
- tests/mount.rs:810 asserts the mount is stale after SIGKILL, and line 815 asserts the sweep clears it.
- The AppleDouble spot-check matches the description.
- In crates/cowfs-nfs/src/sidecar.rs, `side_write` and `side_setattr` take `sidecar_locks.of(ino)`, while `side_create` and `side_remove` do not.
- So the described REMOVE versus WRITE race is plausible as stated (not reproduced).

## 5. Regression risk for real macOS mounts

- The only behaviour change a real client can hit is that a second MNT is refused, even on the same connection.
- The kernel sends MNT once per mount(2) over TCP.
- In both xnu-7195.141.2 bsd/nfs/nfs_socket.c and the NFS-343.100.5 kext (kext/nfs_socket.c:1667), `nfs3_mount_rpc` runs only when `!(nm_sockflags & NMSOCK_HASCONNECTED)`.
- So reconnects never re-MNT.
- `nfs_aux_request` sets `sendat = 0` for SOCK_STREAM ("we only resend the request for UDP", kext line 6177).
- So a slow MNT reply is never retransmitted.
- The option string passes `mountport=`, so there is no portmap probe.
- The option string also passes `tcp`, so the MOUNT protocol runs over TCP.
- mount_nfs userland may retry mount(2) once on a transient error, and the retry sends a new MNT from a new socket.
- The old address-keyed gate refused that retry too, so the same-connection allowance never helped a real client.
- No preflight, probe or self-test in cowfs-nfs or the daemon sends MNT before mount_nfs.
- The reply cache covers only the NFS program, not MOUNT, but with no retransmission that does not matter.
- My conclusion is that the risk is low.
- That conclusion is reasoned from Apple source, not verified by a real mount in this review.
- Run `cargo test -p cowfs-nfs --test mount -- --ignored` on a working Mac before relying on it.
- The live daemon in spikes/nfs-loopback/out/live/bin is a copied binary.
- It gets none of the #43 fixes until it is rebuilt and redeployed.

## Follow-ups (not blocking)

1. Keep the secret out of mount_nfs argv (open since round 3 F2).
2. Log when a MNT was refused even though the mount succeeded.
3. Close the initial-mount eviction window in section 3, for example with a tie-break on connection age.
4. Run the ignored real-mount suite on macOS once the Mac builds again.
5. Take the per-inode sidecar lock in `side_create` and `side_remove`.
6. Decide whether the daemon should handle SIGHUP like SIGTERM.
