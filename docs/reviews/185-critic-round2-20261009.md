## 2. Round-1 blockers

### Blocker 1, release daemon check: fixed

`build_release` runs `cargo build --release --locked --message-format=json`, parses stdout line by line and keeps `compiler-artifact` messages with an `executable` for targets `cowfs-daemon` and `cowfs`.
`profile_problems` rejects `opt_level` 0, `None` or empty, anything but literal `debug_assertions: false`, and an executable whose parent directory is not named `release`.
The checked path is the artifact path cargo reported, so the directory check is on the artifact, not on a driver-built string.
A stale debug binary cannot be launched: the launched path is `arts["cowfs-daemon"]["executable"]`, which cargo just built or reported fresh under `--release`.
The sha256 is taken in `Daemon.__init__` from that same path after the build, so it is the digest for this build.
It is re-compared in `start()` and in `arm_state()` before and after every cowfs arm.
`prov()` additionally records that the live argv starts with that binary.
Residual gap, non-blocking: `.cargo/config` rustflags are not visible in the profile object, and `start()` compares the digest against itself a few lines after computing it, which proves nothing.
The meaningful comparisons are the ones in `arm_state`.

### Blocker 2, cowfs arm re-checked: fixed

`arm_state` runs before and after each cowfs arm and checks daemon alive, `mount_entry` fstype `nfs` with a source starting `localhost:/cowfs-`, `st_dev` of `mnt/base` differing from `st_dev` of the output dir, and the digest.
`localhost:/cowfs-<32 hex>` is the real export name: `crates/cowfs-nfs/src/mount.rs:31` and `lib.rs:75`.
Another NFS mount cannot satisfy it, because `mount_entry` takes the longest mount point containing this private mnt, and a plain `localhost:/` mount of another tool does not start with `localhost:/cowfs-`.
A dead daemon fails `alive`.
A native directory fails kind and source.
Any failure appends a problem and breaks, and any recorded problem forces exit 2 and INVALID.
Residual, non-blocking: the export is not tied to this daemon's pid or log, and `os.stat` on a stale NFS path can hang before the INVALID is recorded (builder already lists this).

### Blocker 3, non-sample minimums and the doc line: fixed

`param_problems` runs in `main` before `run`, so nothing starts when it fails.
It requires g1, g2 and g3 present, scale >= 100, reps >= 5, baseline window >= 300 and load cap <= 4.0.
Bypass attempts checked: `--scale 0` and `--reps 0` fall back to the full defaults, not to weak values.
`--gates "g1, g2, g3"` (spaces) fails the set check, so it is refused, which is safe.
`--load-cap nan` passes `param_problems` but the baseline comparison `p95 <= nan` is false, so the baseline is refused and the run is INVALID.
The only bypass is `--sample`, which labels `NOT_A_GATE_RESULT` in verdict.json and in the printed line.
The doc line about the foreign daemon now says other cowfs daemons do not count as foreign, which matches the `FOREIGN` regex (cargo, rustc, cc1, ld only).
Result logic is fail-closed: PASS or FAIL is only returned when `problems` is empty, and main returns 2 for any problem.

### Blocking: the per-rep load check makes a g1/g2 PASS practically unreachable

`run()` lines 409-411 flag every rep whose `load1_before` or `load1_after` exceeds `q.limit`.
`q.limit = min(baseline p95 + 1.0, 4.0)`, so it is at most 4.0.
`bench/gates.py` records `load1_after` immediately after the rep (lines 508-512), and g1 and g2 are `cargo build -j 4`.
The 1-minute load average after a multi-minute 4-wide build on this machine is expected to be at or above 4, and `load1_before` of reps 2..5 follows right after the previous build.
So the arm's own build load marks its own reps hot, every native and every cowfs arm gets a "reps above load1 limit" problem, and the run ends INVALID.
That hides a PASS, after hours on a scarce quiet window.
It is not measured here (nothing timed is allowed), but it follows from the code, and the builder lists the same risk as open.
The doc blocker list ("check on the quiet-host sample") defers it, but the sample only helps if a quiet host is available, and the fix is small.
Fix options: apply the rep-load check to g3 only; or to `load1_before` of rep 0 only; or drop it and rely on the pre-arm quiet window plus `compare.py`'s own ceiling of 30 and the 2x arm skew limit.

### Significant, same area: the baseline starts right after the release build

`run()` calls `build_release()` and then `q.baseline()` immediately.
After a cold release build the first 15 to 60 seconds of the 300 s baseline window still carry the build's decaying load1.
`p95` of 60 samples is `xs[57]`, the third highest, which sits in that tail.
Result: either the baseline is refused (false INVALID) or `limit` is pushed up to the 4.0 cap, which loosens the bar the doc says is derived from an idle baseline.
The doc itself says to take the baseline after 5 minutes of no heavy work.
Fix: sleep or wait for load1 to settle after the build, or build before taking the lock window, or drop the first minute of load samples.

### Non-blocking

- `newest(label)` globs `g12-ID-n1-*.jsonl` in the shared `bench/out`; a run id such as `x-n1` can collide with run id `x`. Use an exact per-run directory or reject ids ending in an arm tag.
- Lock reclaim has a narrow race: two waiters can both see a stale owner, one re-creates the lock, and the other then unlinks the new owner file. Low probability, fail-open only for the CPU lock.
- `window()` runs `top -l` as a subprocess and is never killed on exception paths; harmless.
- `mount_entry` does not decode `\040` escapes for paths with spaces; the repo path has none.
- A `launched_from_built_binary` failure appends a problem but the arms keep running, which wastes time on an already doomed run.
- Ruff 0.16.2 with default rules reports 6 style findings (SIM102, FURB192, PLW1510, EXE001, RUF100, C408); there is no repo ruff config and CI does not run it.
