## 1. POSIX claim

Verified against the 2018 edition (pubs.opengroup.org/onlinepubs/9699919799/functions/V2_chap02.html), XSH 2.9.7 "Thread Interactions with Regular File Operations":
"All of the following functions shall be atomic with respect to each other in the effects specified in POSIX.1-2017 when they operate on regular files or symbolic links:" (the list includes pread(), read(), readv(), pwrite(), write(), writev()).
"If two threads each call one of these functions, each call shall either see all of the specified effects of the other call, or none of them."
So a 4 KiB pread() that returns half of one pwrite() and half of another violates 2.9.7 for threads, which is what the conformance check exercises.
Linux behaviour (reasoned, from kernel knowledge, not re-verified in source here): the generic buffered write path takes the inode lock (i_rwsem), while filemap_read() copies from page-cache folios without it, so a reader can memcpy a folio while a writer is mid-copy into it.
This is a long-known, deliberate Linux deviation (discussed repeatedly on linux-fsdevel, for example by Dave Chinner); XFS is the notable exception, taking the IOLOCK shared for buffered reads (reasoned, not measured here).
Note: comments in the PR and in conformance.rs say "every Linux filesystem" / "native ext4/btrfs/tmpfs"; the measured set is ext4, btrfs and tmpfs; XFS likely does not tear, so "every" is too strong.
FUSE without writeback cache writes through: fuse_perform_write copies into page-cache pages and sends WRITE under the inode lock, and readers hit those pages without it, so the same mechanism applies on a cowfs mount.

## 2. Is the new test sound

O_DIRECT reaches the daemon: the mount does not set FOPEN_DIRECT_IO (only FOPEN_KEEP_CACHE, fs.rs:408) and no writeback cache, so an O_DIRECT read takes the generic IOCB_DIRECT path into fuse_direct_IO and becomes a FUSE READ.
Empirical proof: the cheap split-read mutant below produced 22 tears in 6000 O_DIRECT reads, which only a daemon-served read can produce (22 tears in one run); the CI bench also reports "read 4 KiB (O_DIRECT, one round trip)" at about 35 us.
The open fails loudly (panic, no fallback to buffered), so an EINVAL would fail the test, not pass it.
Alignment is correct: buffer `#[repr(align(4096))]`, offsets multiples of 4096, length 4096.
Short reads are caught by `assert_eq!(got.len(), PG)`.
`reads >= 1000` floor is sound; CI and cachyos both did 6000 reads (the ROUNDS cap), well clear of the floor and the 20 s CAP.
Vacuous-skip risk: `rig()` returns None and the test passes when FUSE is unusable, but the linux-fuse CI step asserts `"SKIP: /dev/fuse" not in log`, so CI cannot pass silently.

Mutation results (cachyos, Linux 7.2.8, own scratch, since removed):

| Mutant in fs.rs `read` | O_DIRECT test result |
| --- | --- |
| none (baseline) | 20/20 pass, 6000 reads, 0 torn each |
| two half reads with `yield_now()` between | 9/9 FAIL (assert torn == 0; one run showed 22 torn) |
| two half reads with `sleep(300us)` between | 10/10 pass, 0 torn |

Why the slow mutant survives: fs.rs `dispatch` runs a request inline on the single request-loop thread when its class is cheap (under `inline_below`, 100 us) and otherwise on lane `lane_index(ino)`, a per-inode FIFO.
Inferred, not instrumented: WRITE is classed slow here (FLUSH_BYTES = 4096 makes every write republish), so a slow READ lands on the same lane as that inode's WRITEs, and they serialise and cannot interleave.
The test's sensitivity therefore depends on the adaptive cost classifier and varies with per-runner timing.
Overlap between a READ and a WRITE of one inode exists only when one class is inline and the other is on the lane.
So the claim in the new doc comment, "an adapter that split a READ into several `Vfs` calls, or a `Core` read that assembled chunks across a concurrent write, fails this", is conditionally false: it holds only while reads are classed cheap.
End-to-end atomicity still held in the slow mutant (serialisation guarantees it), so this is a test-documentation gap, not a cowfs bug.

## 6. Is "kernel page cache, no cowfs fix" adequately supported

Yes, for the question #45 asks.
The native controls (tmpfs, btrfs) tear with no cowfs code, by the same mechanism.
The daemon cannot hand the kernel a torn block: Core `op_read` (io.rs:39) snapshots the `Arc` chunk list and copies the overlay under the node read lock, then assembles outside it, so a read is a consistent snapshot by construction (reasoned from source).
`core_view_keeps_aligned_4k_blocks_atomic_while_flushing` asserts that directly with truly concurrent threads and FLUSH_BYTES = 4096, so every write republishes a chunk list.
Chunk boundaries: store FastCDC is MIN 16 KiB / AVG 64 KiB / MAX 256 KiB, not 4 KiB aligned, so a 4 KiB block can straddle two chunks in the 64 KiB file; Core atomicity across chunk boundaries is therefore reachable by the existing core_view test (whether a given run actually straddles depends on where FastCDC cuts uniform data: unmeasured).
And the adapter's per-inode lane serialisation (above) adds a second guarantee on the mount path.
The lower mount tear rate (92/1000 vs tmpfs 1000/1000) is consistent with slower FUSE writes shrinking the memcpy-overlap window; nothing in it points at cowfs.
What would settle the remaining gap: a Core-level unit test that pins a 4 KiB block across a known chunk boundary (construct the chunk list explicitly) and races reads against a republish, rather than relying on where FastCDC happens to cut.
