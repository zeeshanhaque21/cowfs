## (1) Fail-open

Measured with build_receipt in acceptance mode.
- `tree_ignored` key absent, no flags: exit 0.
- `tree_ignored` key absent, both helper flags given and matching: exit 0.
- Old-format runs therefore validate, and so does a run where recording silently produced nothing.
- This is not a regression (identical to origin/main) and a planted `ltp/fsx` is still caught by the digest compare because the old script recorded `fsx_sha256`.
- It does leave every other ignored output ungated for old-format meta even when the operator passes both flags.
- Safer choice: when either helper flag is given, a missing `tree_ignored` key is INVALID ("meta: tree_ignored was not recorded").
  Without flags, keep backwards compatibility for old runs.
- Recording failure: `tree_status=$(git status ...)` has no exit check and the script is `set -u` only.
  If `git status` fails (dubious ownership as root, index.lock contention, read-only tree) both `tree_porcelain` and `tree_ignored` are empty, which reads clean.
  `tree_head` empty would be caught, but a status-only failure would not.
  Fix: `tree_status=$(git -C "$XFS" status --porcelain --ignored) || { echo "git status failed" >&2; exit 2; }`.
  Pre-existing for tree_porcelain, now covers both keys.
- Flags are optional, so a bare acceptance run with a clean tree and no flags still passes without any helper digest check.
  Acceptance mode should require both helper digests (as it already requires the daemon digest).

## (2) Digest enforcement

Measured: `--fsx-sha256 ''` and `--fsstress-sha256 ''` are dropped by the `if v` filter.
With ignored paths present that is INVALID (not vacuous pass).
With a clean tree it is silently "not given" (exit 0), so an empty flag is a silent no-op rather than an error. Reject empty strings in argparse.
Uppercase expected, trailing whitespace expected and 8-char prefix expected are all INVALID (exact compare, fail closed).
Meta digest present but empty with expected given is INVALID.
One digest only with ignored paths is INVALID (tested in the PR).
Residual: `include/config.h`, `src/*` helpers, `common/config`, `tests/*/group.list` and results dirs are only covered by the two digests, so a hand-built `config.h` or a planted `src/t_*` binary with the genuine fsx/fsstress passes.
Cheaper stronger option: `xfstests_build.sh` records, and `g5_root.sh` recomputes, one `ignored_manifest_sha256` = sha256 of sorted `sha256sum` over `git ls-files -o -i --exclude-standard` (excluding `results/` and `tmp.*`), and g5_diff compares it with a `--ignored-manifest-sha256` flag.
It needs no reproducible builds because it compares the recorded build to the run tree, not to a rebuild.
Recommend requiring it in acceptance mode once built; keep the two helper digests as the interim gate.
Track as an issue.

## (4) Bash safety and injection

Measured with a repo containing an ignored file whose name is `out<newline>tree_porcelain=<newline>fsx_sha256=abc`.
git quotes it as `"out\ntree_porcelain=\nfsx_sha256=abc"` (backslash-n, not a real newline), and under `bash` the meta line stays one line.
Under `dash` and `zsh`, `echo "tree_ignored=$(...)"` interprets the backslash-n and emits real newlines, giving meta lines `tree_porcelain=` and `fsx_sha256=abc"...`.
`parse_identity` is last-wins, so in such a shell a crafted filename could override `fsx_sha256` with an attacker-chosen value, equal to the expected digest.
Current exposure is low: shebang is `#!/bin/bash`, the box launcher uses `bash`, and a repo-planted filename needs write access to the tree.
It is still a real latent injection because it depends on `echo` backslash handling (e.g. `bash` with `xpg_echo`, or `sh g5_root.sh`).
Fix: use `printf 'tree_ignored=%s\n' "$(...)"` for these two lines, and/or have `parse_identity` or `build_receipt` reject duplicate meta keys.
Spaces in names are quoted by git only with other special characters, so `.split()` on `tree_ignored` is display-only ambiguity, not a gate issue.
