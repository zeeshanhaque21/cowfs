## 1. Root cause
Correct.
GitHub Actions default shell on Linux is `bash -e {0}` with no pipefail, so `cargo ... | tee` exits with tee's status.
`shell: bash` expands to `bash --noprofile --norc -eo pipefail {0}`, so a nonzero cargo fails the pipeline.
Precedent already on main: the linux-namespaces step uses `shell: bash` with the same tee shape (main ci.yml:125, branch ci.yml:127).
Not re-verified against live GitHub docs (no network fetch done); this is from known documented semantics.

## 2. Coverage of cargo-through-tee steps
Every `| tee` in .github/workflows is covered (only ci.yml exists).
Branch lines: 128 (already had shell: bash), 166-167 xattr, 171-172 page-cache, 179-182 forget, 186-187 fuse-tests.
No other job (lint, test, fault-seam, check) pipes anything.
Note A (comment is wrong, behavior is silently weaker than claimed): ci.yml:171 comment says "a cargo build failure fails the step".
It does not.
`cargo | tee || true` makes `|| true` apply to the whole pipeline, pipefail included, so a compile error also exits 0.
The PR's own test proves it (test_ci_workflow.py:111-112 asserts rc 0 on cargo exit 101).
The step is still safe in practice because Enforce asserts `^1 run,` in native-page-cache.log (ci.yml Enforce, "Native page-cache control did not run the check"), so a build failure that produces no report is caught later.
Recommendation: fix the comment to say the build failure is caught by the Enforce `1 run,` assertion, or make the step real: `cargo ... | tee log; rc=${PIPESTATUS[0]}` and tolerate only a test failure.
The `|| true` itself is deliberate and sane (torn read is the known native-kernel limit, issue #45).

Test `test_main_shape_passes` feeds the known FAIL line plus `test result: ok` and passes.
False negatives: `test result: FAILED` is printed by libtest for every failed binary regardless of `--nocapture`, so it is the reliable catch.
Note B: under `--nocapture` libtest prints `test x ... ` then the test's own output, so the per-test `FAILED` can land alone on a later line and the `test .* \.\.\. FAILED` alternative can miss it.
The `test result: FAILED` alternative covers that case, so no gap, but the first alternative is weaker than it looks.
Also Enforce only runs when earlier steps succeed (no `if: always()`), so after the shell fix the new assert is belt and braces.
