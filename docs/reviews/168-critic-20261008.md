## 3. Policy

The check compares the requested uid against `self.core.uid`.
`Core.uid` comes from `mounter()` (`geteuid()`, fs.rs line 170 to 174), and `file_attr(&s, self.uid, self.gid)` is what `getattr` and `lookup` report.
So the compared value is the same value the kernel sees as the owner of every file, not `req.uid()` of the caller.
That is the right comparison: "no change" means "the uid getattr already reports".

Refusing for all callers, including root and `allow_other` callers, is right for this filesystem.
cowfs cannot store a second owner, so any success for a different uid is the same lie issue 160 describes (success, then readback shows the old owner).
Under the default `default_permissions` mount the kernel already refuses a non-root chown to another uid, and a non-owner chown, before the adapter runs.
So the adapter check only changes behavior for root callers (and for `nodefault_permissions`), which is what the test's comment says.
For an `allow_other` non-mounter caller, the files appear owned by the mounter, so the kernel refuses their chown first, and naming their own uid is also another uid and is refused.
That is the same answer native gives a non-owner.

Legitimate flows, assessed from code and general tool behavior, not run:
Non-root tools do not break. git checkout, cargo, and non-root `cp -a`, `tar -x` or `rsync -a` either do not chown or chown to the caller's own uid, which equals the mounter's uid and passes.
Root-run ownership-preserving tools (`tar -p` or `--same-owner`, `rsync -a`, `cp -a`, `install -o`) will now see EPERM where they used to see silent success, and may print an error or exit nonzero.
This is the same consequence the PR 161 critic recorded for NFS, and the same honest direction: before, they believed ownership was preserved when it was not.
How each tool reacts to EPERM is unverified here.
`cp -a` as root is the most likely to complain, since GNU cp only tolerates chown EPERM when it lacks chown privileges.
Gid is accepted and ignored in both adapters, so `chgrp` to any group still "succeeds" with the gid unchanged.
That matches the stated NFS policy and is a known, documented divergence, not a regression.

## 4. Mode in the same request, and the setuid case

The check sits at the top of `setattr`, before `SetAttr { mode, size, atime, mtime }` is built, and returns `reply.error(e)`.
So nothing in the request, mode, size or times, is applied when the uid is refused.
For a chown on a regular file the kernel pairs the uid with a mode that clears the setuid bit (ATTR_KILL_SUID turned into ATTR_MODE in `notify_change`), so mode and uid arrive in one setattr.
Refusing first keeps the setuid bit.
The mount test covers this: file `s` created with mode 0o4755 reads back `0o4755` before and after a refused chown to `uid + 1`.
It also covers mode `0o644` file `f` with uid-only and uid+gid requests, readback of `(uid, gid)` unchanged, then own-uid, own-uid plus gid, and gid-only chowns all returning success.
Note that a successful chown to the mounter's own uid on a setuid file still clears the bit, as native does, and that path is unchanged.
Size is checked after the guard too, so a truncate paired with a refused chown does not truncate.

## Non-blocking notes

1. The macOS `check` job passes the mount test only by the skip path, so it adds no behavioral signal. Whether macFUSE or FUSE-T ever sends uid in a setattr that was not a chown is untested; if one does with the mounter's uid it passes, with another uid it would now fail.
2. Root-run ownership-preserving tools (`tar`, `cp -a`, `rsync -a`) now report an error. Worth a line in release notes. Unverified against a real mount.
3. `Core.uid` is the mounter's `geteuid()` at mount time. A process that changes euid after mounting would see getattr and the check agree with each other but not with the new euid; no such caller exists in the repo.
4. The red-then-green discipline was done correctly. Issue 179 (pipefail) remains a real hole, since the red job still concluded SUCCESS; until it is fixed, every FUSE PR needs this manual log grep.
