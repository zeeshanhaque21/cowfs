## Attack 1: where the rule lives

The rule is `cowfs_vfs::mknod_needs_root(kind, rdev)` in crates/cowfs-vfs/src/types.rs, re-exported from lib.rs.
FUSE (crates/cowfs-fuse/src/fs.rs:642) calls it directly.
NFS (crates/cowfs-nfs/src/adapter.rs:1140) calls the same function through a new trait method `NFSFileSystem::mknod_needs_root` that the nfsserve handler consults.

## Attack 2: NFS caller identity and what the check is worth

The uid comes from the AUTH_SYS credential in the RPC call (nfsserve/src/rpcwire.rs:47).
Credentials are not authenticated at all.
AUTH_NULL, or any call with no AUTH_UNIX credential, leaves the connection context at `auth_unix::default()`, which has uid 0 (tcp.rs:260).
So AUTH_NULL counts as root, as the PR body says.
Also the context auth is per connection and only overwritten when an AUTH_UNIX call arrives.
Real security value, stated plainly: against a hostile NFS client this check is worth nothing, since it can send AUTH_NULL or uid 0.
The real protection is the one the crate docs state: loopback only, a random export path only mount_nfs is told, a one-shot MNT gate, and MAC-keyed handles.
The uid check only stops an honest client that is not root from creating device nodes, i.e. it reduces accidental misuse and mirrors native semantics.
This is unchanged by the PR; the PR does not claim more, and the issue's premise (that NFS had no check) was wrong, which the PR body states.
What the PR newly changes on the wire: the 0:0 char device is now allowed for any uid, same as FUSE.
That is harmless: a whiteout has no device behind it and an AUTH_NULL client could already create anything.

Consistency when the daemon and the mounting user are uid 501:
Every non-whiteout device is refused before and after the PR, for the NFS path (the macOS client sends the user's uid, or refuses first as the existing comment says).
FUSE does the same for a non-root `req.uid()`.
So both adapters now agree: non-root gets fifo, socket and whiteout only.
Regression check on fifo and socket: `mknod_of_a_device_needs_root_but_a_fifo_does_not` and `mknod_creates_fifo_socket_and_devices_with_type_mode_and_rdev` pass on the merged tree.
I could not run a real macOS client; the Mac cannot build new native binaries. Not exercised.

## Attack 3: edge cases

The unit test `mknod_privilege_rule` covers block 0:0 (needs root), char 0:1 and char 1:0 (need root), block 8:0, fifo and socket.
Block with rdev 0 is not a whiteout: correct, and tested in both the unit test and the NFS test.
Char with major 0 and minor nonzero: needs root, tested (0:1).
The mode-with-both-type-bits case does not reach the rule: both adapters map the type first (`mknod_kind`) and a bad type is BADTYPE or an error before the privilege check.
Representation: cowfs rdev is `(major << 32) | minor`.
NFS converts the two u32 specdata fields with `makedev(specdata1, specdata2)`, so 0:0 is exactly 0 and any nonzero field makes it nonzero.
FUSE converts the kernel dev_t with `rdev_from_kernel`, so 0 is 0 and any nonzero major or minor is nonzero.
Both use the right field and the same encoding, so the zero test is correct in both.
Non-device kinds: the rule checks `is_device` first, so a stray nonzero rdev on a fifo is irrelevant.
AUTH_NULL as root: see attack 2. It is treated as root (pre-existing, loopback-gated), not newly introduced.

- No real macOS mknod run; fifo and socket regressions are covered only by the raw NFSv3 tests.
