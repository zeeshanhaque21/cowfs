## Challenge to decline C (NULL flood evicts pre-MNT kernel socket)

Verified in crates/nfsserve/src/tcp.rs `enter`: victim is min by (served, active).
`served` counts only valid-handle calls or successful MNT, so NULL cannot raise it.
Among unserved sockets the oldest-active loses, so cap newer connections evict the kernel socket.
The builder's core claim holds: before its first handle call the kernel socket is a NULL-pinged unserved socket, same as an attacker's.
Forged handles fail the MAC so the attacker cannot get served above zero. No server-visible discriminator exists.

Ideas checked and why they fail or are weak:
- Per-peer-address accounting: all clients are 127.0.0.1, useless. Per source port is one-per-connection, same as no accounting.
- Evict newest unserved instead: protects the older kernel socket but locks out a legitimate reconnect, which the existing test served_but_silent_connections_do_not_lock_the_client_out forbids.
- Grace period for young unserved sockets: attacker who connects first fills the cap and the client is refused for the grace window. Moves the DoS, does not remove it.
- Reserved slot for the first connection after listen: that connection is mount_nfs's MNT socket, which is already served after MNT. The kernel socket is a later, different connection. Does not help.
- Rate limiting NULL-only connections: attacker needs only cap-many sockets, low rate suffices at cap 4. At the default cap 64 it needs 64 fresh sockets inside the few-ms window between MNT and the first GETATTR.

Severity is low: window is startup only (after the first handle call the socket is served and protected), requires a local process, the default cap is 64, and the loss is a failed or retried mount, not data exposure.
Cheap mitigation the builder did not mention: a bounded retry in Mount::mount (re-run mount_nfs, rearm the gate) when the first attempt fails with a reset or timeout. The kernel client also reconnects on its own with a hard mount.
Suggest filing that as the follow-up on #262 and leaving the server policy alone.
Feasibility of a server fix: no for a discriminator, yes for the retry mitigation (client side, small, testable with the existing flood helper).

## Challenge to decline B (first-MNT theft)

Export path is cowfs-<32 hex> from 16 bytes of random_key (mount.rs secret_path). Unguessable per server instance. Confirmed.
Leaks: mount_nfs argv (visible in ps while it runs) and the mount table or nfsstat -m afterwards. lib.rs already states both.
Gap in the PR argument: the PR says the mount table leak is harmless because the gate is closed.
That is true only while the gate stays closed. Server::rearm_mount (used for deliberate remounts) reopens the gate on the SAME export path.
So during a remount window any local process that read the path from `mount` can win the MNT race. The PR and lib.rs docs do not call this out.
A cheap fix exists and is not the revocation the builder rejected: make rearm_mount (or Mount remount) rotate the export name, so the old path read from the mount table is dead. This needs listener export name to be mutable or the server to be re-created. Worth a follow-up issue, not a blocker for a test-only PR.
Revoking on a refused MNT being a kill switch for a live mount: agreed, rejection is correct.

Claim that macOS sends MNT from an ownerless socket: NOT independently verified by me, I did not touch a live mount.
Supporting evidence in-repo only: peer.rs doc comment and the Mount option comment both state the kernel NFS client socket is invisible to lsof, and check_peer_uid defaults off for that reason.
Note mount_nfs userland (not the kernel) sends the MNT; whether that socket is owned by the mount_nfs process is a different claim from "kernel socket has no owner". The PR body conflates them. If MNT comes from the mount_nfs process, pid binding is conceivable for MNT even if not for the kernel NFS socket.
Recommend the builder either measure this (lsof during a mount in a throwaway directory, not a live mount) or soften the wording.

## Test quality

The pass test pins the exact boundary: 3 later connections survive, 4 evict at cap 4. It would catch a tie-break change, which is intended.
It asserts a vulnerability, so a real fix will turn it red. The comment says to flip it and un-ignore the other. Acceptable and documented.
Refactor into pinged_socket_survives(n) is clean, no behaviour change to the original assertion.
Minor: the ignored test uses 64 later connections against cap 4; meaningful, the number is arbitrary but larger than cap.
