## 2. Can verdict.json say PASS when it should not

### 2a. Release build is not verified (BLOCKING)

`Daemon.bin` is hard-coded to `REPO/target/release/cowfs-daemon` at line 119.
`prov()["release"]` at line 150 is `"/target/release/" in str(self.bin) and argv.startswith(str(self.bin)) and "--backend core" in argv`.
All three terms are true by construction because the driver itself built that argv from that path, so `release` is a constant True and can never be False.
The doc, lines 113 and 121, says a false `daemon.release` is how the debug artefact is detected, which the code cannot do.
The sha256 is recorded but compared with nothing, yet the doc line 114 lists "`daemon.sha256` equals the built binary" as a validity condition.
Nothing ties the binary to the PR head or to the doc's pinned digest c088fc08..., nor checks its age against the sources.
A debug binary copied to target/release, or a stale release from another commit, is accepted.
Also `--backend` only has `core` and `path` (crates/cowfs-daemon/src/daemon.rs:21), so the doc phrase "debug backend" conflates a build profile with a backend.
Fix: have the daemon report its profile (for example `cfg!(debug_assertions)` in `--version` or a control call), assert it, and compare the digest with an expected value passed on the command line or from a freshly built manifest.

### 2b. Cowfs arm provenance is checked once, at startup (BLOCKING)

fstype of the mount is asserted once at line 137 and recorded at line 229.
Before each of the four arms the driver calls `q.check(d.proc.pid)`, which only uses the pid to exclude the daemon from the foreign-process scan.
It never checks that the daemon is still alive, that the mount is still nfs, or that the arm root `mnt/base/g12` is still on it.
`gates.py` does `root.mkdir(parents=True, exist_ok=True)` at line 151 and re-clones the corpus.
If the daemon exits and unmounts between arms, c2 (or c1) silently runs on the plain local directory under bench/out and cowfs equals native.
Rep counts, loads and native-native would all pass, compare.py would return 0, and the verdict would be PASS.
This is a hypothesis from reading the code, I did not reproduce it, but nothing in the code rules it out.
The meta record in each JSONL has `root` but no filesystem type, so compare.py cannot catch it either.
Fix: before and after every cowfs arm assert `proc.poll() is None` and `fstype(croot) == "nfs"` and record it per arm, and add a post-run check as well.

### 2c. Non-sample runs accept overrides and still say PASS (BLOCKING)

`--scale`, `--reps`, `--gates`, `--load-cap` and `--wait` are honoured outside `--sample`.
`g12_run.py --run-id x --scale 1 --reps 1 --gates g3` goes through the non-sample branch and can write `result: PASS`.
`--load-cap 1000` disables the baseline refusal and sets limit to `min(p95+1, 1000)`, which on a baseline of 100 is about 101, so the quiet bar is effectively off (only compare.py's 30 ceiling remains).
verdict.json records `scale`, `reps` and `gates` but does not record the load cap or wait, and no floor is enforced.
The doc line 116 says "rep counts equal `--reps`", which is satisfied trivially at `--reps 1`.
A gate PASS should require gates a superset of g1,g2,g3, scale 100 and reps at least 5, or the result should be labelled something other than PASS.

### 2d. Checks that do work (verified in code)

Host not quiet: baseline refusal, per-arm 60 s window (load1 max, CPU idle floor, foreign cargo/rustc/cc1/ld) and a post-run check of every rep's load1_before/after, with non-sample break and INVALID if an arm is not quiet.
Native-native: median wall ratio per gate must be within 1 +/- 0.10, else a problem and INVALID (lines 266-271).
UNMEASURABLE: compare rc 2 or 3 sets INVALID (line 281), and compare.py itself returns 2 for NaN or load above 30 or 2x skew.
Partial gate coverage (issue #80): the driver counts reps per gate per file against `--reps` (lines 258-262), which covers it, subject to 2c on which gates are asked for.
A failed rep (cargo build non-zero, SystemExit 70) makes gates.py exit non-zero, and the driver stops with a problem; no row is written for the failed rep.
PASS needs `problems == []` and `compare_rc == [0, 0]`.

### 2e. Quiet bar derivation (non-blocking)

The effective limit is `min(baseline p95 load1 + 1.0, 4.0)` and the idle floor is `baseline median idle - 10`, so it is derived from a baseline measured in the same run, which satisfies the "never a guessed number" rule for the working limit.
The constants 4.0 ("25 percent of 16 cores"), +1.0 and -10 points are guesses and should be labelled as such, not as measured.
The doc is honest that no baseline exists yet: "Measured baseline: NONE".
Predicted defect, UNVERIFIED: `load1_before` and `load1_after` in gates.py are read around a `cargo build -j 4`, so the benchmark's own load (4 or more runnable) lands in load1 and rep 2 onward starts with the previous rep's decay.
With limit at most baseline p95 + 1.0 this probably marks every g1/g2 rep "above load1 limit" and every real run INVALID even on a quiet host.
A first quiet-host `--sample --gates g1,g2 --reps 1` would show it; the limit may need to be defined against pre-arm load only, or have an allowance for the arm's own jobs.

## 3. Cleanup and shared state

Good: store, mount, log and native root are under `bench/out/g12/ID/` (gitignored `/bench/out/`), `out.mkdir` is exclusive so a repeated run id is refused, daemon kill is preceded by an argv check (line 156), there is no pkill, and the CPU lock is the same atomic mkdir path and 15 minute wait as run-pair.sh and is released in `finally`.
SIGTERM is turned into SystemExit so `finally` runs.
The socket is under `~/.cowfs/sock/g12-ID.sock`, justified by the 104 byte AF_UNIX limit, with a unique name.
Issues, all non-blocking:

- `stop()` does not verify the mount is gone, though doc line 68 says "then the mount must be gone (`mount | grep cowfs`)"; add an `fstype(mnt) != "nfs"` assertion after the wait and record it in verdict.json.
- After a 60 s SIGTERM timeout it prints "left running for the operator" and then still unlinks that live daemon's socket (and a `.lock` sibling, whose existence in the daemon I could not confirm by grep). Skip the unlinks when the process is still alive.
- In the `finally` block, `LOCK.rmdir()` can raise (non-empty dir) and `d.stop()` raising would skip the lock release; split these into independent try blocks. Also the lock `owner` write happens outside the inner try, so a failure there leaks the lock.
- A SIGKILL leaves the lock, daemon and mount, and the next run just waits 15 minutes with no stale-owner check (the owner file holds a pid and would allow a verified reclaim).
- Unhandled exceptions (for example `statistics.median` of an empty list, `newest()` IndexError) leave no verdict.json and exit with Python's code 1, which collides with the driver's documented "1 = valid FAIL". Wrap `main` so any exception is INVALID with exit 2.
- The sample branch exits 0 even when problems were recorded, and `result` reads "SAMPLE, NOT A GATE RESULT" rather than showing INVALID; the problems list carries the truth, but a wrapper keyed on exit code would not see it.
- The lock path default is an absolute path in the primary checkout, which matches run-pair.sh and is intended shared state.

- Under the macOS g2 rule (add under 1.0 s) a run can PASS with a cowfs/native ratio above the tracker's literal 1.5x for a short native rebuild; the doc discloses the budget but not this consequence, and verdict.json carries no per-gate ratios (they are only in compare-N.txt).
