## 2. Validity rules and false-PASS paths

I read bench/g5_diff.py end to end plus the two shell scripts.

Native arm that is not native.
`check_identity` (g5_diff.py:123-129) requires fstype `ext4`, a `/dev/loop*` source and a loop backing file.
It also requires source equal to `TEST_DEV`, target equal to `TEST_DIR`, and exactly one mount with that source (g5_diff.py:116-122).
`make_record` additionally requires the console header `FSTYP` to be `ext4` (g5_diff.py:168-170).
A native arm that is secretly cowfs fails on three independent facts.
Unit test: `Identity.test_native_that_is_actually_cowfs`.

Cowfs arm that is not cowfs.
`check_identity` (g5_diff.py:130-138) requires a `fuse*` fstype, source `cowfs`, and a mount root equal to `/<this case's snapshot>`.
A plain directory, a loop mount or another FUSE filesystem fails.
Unit test: `Identity.test_cowfs_that_is_actually_native`, `test_cowfs_must_be_on_its_own_fresh_snapshot`.
Residual: the identity is measured by g5_root.sh itself before `check` starts (g5_root.sh:12-24, 79-82) and read back as text, so it proves the mount at case start, not during the case.
That is acceptable for the stated threat (wrong arm), and the residue listing (g5_root.sh:154) covers a case escaping to the bare directory.

Empty or skipped-everything run.
`n_pass == 0` or `c_pass == 0` gives UNMEASURABLE exit 2 (g5_diff.py:256-257).
`PASS_EMULATED` is not counted as a cowfs pass (g5_diff.py:252), and acceptance needs `both_pass == len(requested)` (g5_diff.py:261).
Unit tests: `test_all_not_run_cowfs_is_unmeasurable_not_diagnostic_zero`, `test_all_not_run_native_is_unmeasurable`.

Not run counted as pass or hidden.
`parse_console` decides NOT_RUN from the `[not run]` bracket plus the suite's `Not run: <case>` line, never from the "Passed all 1 tests" summary (g5_diff.py:81-87).
A pass needs rc 0 and a timed result line (`\d+s`) (g5_diff.py:88-94).
Native PASS with cowfs NOT_RUN is label `gap`, listed by class, not a pass and not hidden (g5_diff.py:188-190, receipt "Gap" lines).
In acceptance a gap blocks PASS.

Timeout counted as pass.
rc 124 or 137 maps to TIMEOUT before any text is read (g5_diff.py:59-61).
Cowfs TIMEOUT against native PASS is `worse`, which gives FAIL exit 1.
Native TIMEOUT is not a PASS, so it cannot make `both_pass`.

How "worse than native" is defined.
It is exactly native PASS with cowfs FAIL or TIMEOUT (g5_diff.py:188-190, 253).
Native PASS with cowfs NOT_RUN is a separate `gap` (42 in the wide run), not part of "worse".
So the builder's list of 8 "worse" ids is FAIL-only, and the 69 cowfs not-run cases are accounted for separately; the two statements do not conflict.
Two label combinations fall to `other` and never raise a flag: native NOT_RUN or FAIL with cowfs FAIL or TIMEOUT (g5_diff.py:197).
In the wide run that is generic/473 only (native FAIL, cowfs NOT_RUN), so no cowfs failure was hidden there.
Non-blocking: a cowfs FAIL where native did not run should at least be listed.

6-id acceptance requires the control.
`build_receipt` adds a problem, so verdict INVALID exit 3, unless the control record exists, is `FAIL` and has no identity problems (g5_diff.py:222-224).
The control status and problems are part of the receipt and appear in both sample-receipt.md and wide-receipt.md ("Control: {'status': 'FAIL', 'problems': []}").
Weakness (non-blocking): any `FAIL` satisfies the control, including a failure from a harness fault.
The control should also assert the failure reason (read-only filesystem, EROFS) so it proves the harness can see that specific failure.

Provenance holes in acceptance mode (the blocking item).
`build_receipt` requires `tree_head`, `check_sha256`, `cowfs_profile` and, in acceptance, `release` (g5_diff.py:202-221).
It does not require `cowfs_rev` to be recorded, it does not compare `cowfs_bin_sha256` to anything, and it does not bind `g5_root_sha256` to the reviewed script.
The sample and wide meta both carry `cowfs_rev=unrecorded`.
So the sample receipt `PASS (acceptance evidence)` is a PASS of a binary that nobody can map to source.
The box binary still has the recorded sha (bf6d2e11...bebc, built 2026-10-08 18:58, re-checked read-only), so it is identifiable, but the box copy is not a git checkout.
Required fix: reject `cowfs_rev` of `unrecorded` or empty in acceptance mode, add a unit test, and either pin the daemon sha or record the git revision at build time.
Until then the sample must be described as "6/6 on an unidentified release build", not "acceptance evidence".

Other validity notes.
`CHECK_CALLER_RE` classification of the shim log counts any unparsable line as a cycle, which is conservative and correct (g5_diff.py:146-161).
The 149 non-reviewed wide ids have no byte pin (only `pin.cases` ids are checked, g5_diff.py:212-215); acceptable for diagnostic mode, and the receipt labels the run "diagnostic".
The wide verdict is `FAIL` exit 1 with label "FAIL" (wide-receipt.md), not "DIAGNOSTIC"; the PR text calls it diagnostic, which is right by mode but the label could confuse a reader.

## 3. Safety on the box (password, cleanup, scope)

Password handling, g5_box.sh and g5_root.sh.
g5_box.sh:16-24: the caller's stdin carries the password; the first `ssh ... cat > launch.sh` takes its stdin from the heredoc (g5_box.sh:16, `<<'EOF'`), so the password does not enter the script file.
The second ssh (g5_box.sh:24) receives the caller's stdin, which the launcher reads with `read -r P` (g5_box.sh:18).
Password is sent to sudo via `printf '%s\n' "$P" | ... sudo -S -p ""` (g5_box.sh:21): printf is a bash builtin, so no argv exposure, and `-p ""` suppresses the prompt.
The ssh command line at g5_box.sh:24 carries only paths and run settings.
g5_root.sh has no password code at all (header comment at g5_root.sh:8 says so and the file confirms it).
The password is not written to the receipt, the log files, an exception message or a failure print.
`$OUT.sudo.log` captures sudo's stdout and stderr; sudo does not echo the password, and `poll` prints only its last 3 lines (g5_box.sh poll).
No `set -x` anywhere.
Empty password: refused before sudo (g5_box.sh:19, exit 9), so an empty string cannot reach sudo.
Caveat (non-blocking): `-S` with a wrong password lets sudo retry and consume further failed attempts on EOF, which can count toward pam_faillock; one wrong password could approach the lockout threshold.
Suggested hardening: `sudo -S -k -n` is not possible with a password, so instead run `sudo -S -v` once, check its exit, and only then launch.
Out of file scope: how the caller obtains the password from `.env` is not in this PR and was not reviewed.

Busy-box check.
Neither script checks `uptime`, `who` or running processes before starting.
The box showed load 0.02 and 2 logins when I looked, so nothing was harmed, but the PR claims no such guard and does not have one.
Non-blocking: add a refuse-if-loaded check (load average, existing `cowfs-daemon`, existing loops/mounts under the work dir) in g5_box.sh start.

Cleanup.
g5_root.sh:99-114 installs `trap teardown EXIT`: it shuts down the daemon through its socket, waits for the main mount to disappear, kills the pid, unmounts the native mount (lazy fallback), detaches the loop, and writes `teardown.txt` with `mounts_left`, `loops_left`, `daemons_left`.
Each cowfs case runs in `unshare -m --propagation private`, so a case's mount dies with its namespace.
Box check, read-only: `g5-wide2/teardown.txt` shows `mounts_left=0 loops_left=0 daemons_left=0`; no mounts under the work directory, no loop devices, no cowfs mount at review time.
SIGKILL of the script would skip the trap; there is no test for a kill mid-run.
The script is started with `setsid` and detached, so a dropped ssh session does not kill it.

Paths.
Work area defaults to `/mnt/docs/Projects/cowfs-g5` (g5_box.sh:9), outputs under `$W/out`, `TMPDIR=$OUT/tmp`.
g5_root.sh does not itself enforce a /mnt/docs prefix; it trusts `XFS`, `BIN` and `OUT` from the launcher.
It does a root `rm -rf` of stray `tmp.*` in `$XFS` (g5_root.sh around the cleanup loop) guarded by `${XFS:?}`; scope is the xfstests tree on the box.
Suggest an explicit prefix guard (`case $OUT in /mnt/docs/*`).

## 4. generic/127

Evidence read on the box (read-only), runs g5-wide1, g5-wide2 and g5-r127ns (shim disabled).
rc is 1 with `output mismatch`, so this is not a timeout (a timeout would be rc 124 and a TIMEOUT record).
The output lacks some `All 100000 operations completed A-OK!` lines: 2 missing in wide1 and wide2, 1 missing in the NOSHIM run.
Elapsed time is about 293 s in wide2 (progress 20:15:43 to 20:20:36) and about 305 s including setup in the NOSHIM run, so it sits at the 300 s `TMO` edge without crossing it.
`127.full` holds only `umount: bad usage`, in the NOSHIM run too, so that line is not the shim's.
The earlier isolated release run `iso-rel/127` passed in 290 s (check.time `generic/127 290`).
The full hand run `hand-cowfs-182401` also FAILED 127, so "the hand run passed" is true only for `iso-rel` (an isolated single-case run), not for the 155-id hand run.
Test design facts: generic/127 starts six fsx jobs in the background and every job writes to the shared `$tmp.output` (tests/generic/127 lines 33-69), which is a race the suite itself has; a missing completion line without an fsx failure text is consistent with that race but I could not confirm it.
Conclusion: undiagnosed.
It is not a timeout, it reproduces three times on the harness path and once on the hand path, and it passes only in the isolated run.
Do not classify it as a harness artefact or as a cowfs defect yet; file a diagnosis task that runs it alone in the harness and keeps `127.out.bad`, `127.full` and the fsx per-process output.
This is a hypothesis list, not a finding.

## 5. PR body, design doc, scope, provenance

Scope is right for the stated goal: bench/ files, one design doc, evidence, and a small `run` retirement in xfstests_gate.py (+17 -1).
The `run` retirement uses an env opt-in (`COWFS_G5_OLD_ARM_MODEL`) set with `os.environ.setdefault` at import time in test_xfstests_gate.py; it works but is global process state for the whole test run.
The design doc and PR body agree with the code and with the evidence on every point I checked (arm model, mount helper, identity, classification, worse and gap definitions, control, exit codes).
Doc inaccuracies to fix:
the doc lists "different fstype" as part of validity rule 8, but the code checks only that `TEST_DIR` differs (g5_diff.py:236-239); fstype separation is enforced per arm by rules 5 and 6, so behaviour is right and the doc wording is loose.
The doc says `NO_RESULT` makes the run INVALID; the code also makes a mismatched native/cowfs coverage INVALID, which is stronger and fine.
The PR body says "box is clean (no mounts, loops, daemons)": confirmed read-only (the only `cowfs-daemon` hit from `pgrep -f` was the ssh command itself; `pgrep -x` found none).
The "Remaining" list in the PR body and design doc is honest and complete as far as I can see, and the builder's admissions match what I found.

Provenance of the wide run as evidence.
It is a diagnostic list with a binary sha (recorded and still matching the box binary), a clean pinned xfstests tree head (3e1ee800...), the pinned `check` sha, kernel 7.2.8, and tool profile `release`.
It lacks the cowfs source revision and the `g5_root_sha256` and `noshim` meta lines (produced by an intermediate script version), and the repo holds only the receipt JSON and meta, not the per-case consoles.
So the 76/69/9 counts are reproducible only on the box, not auditable from the repo.
It is sufficient to call it diagnostic evidence about that exact binary on that day.
It is not sufficient for any claim about a cowfs revision, for the "worse" list to be treated as bugs, or for acceptance.
Recommend copying the per-case `console.txt` for the 8 "worse" cases and generic/127 into the evidence directory, and rerunning the wide list once on the final script to get a complete `meta.txt`.
