## 2. NFS semantics (nfsserve and cowfs-nfs)

Verified by reading crates/nfsserve/src/nfs_handlers.rs, rpcwire.rs, crates/cowfs-nfs/src/adapter.rs and convert.rs.

- Decoding: MKNOD3args reads dirops, ftype, then sattr3 (+ specdata3 for CHR/BLK), sattr3 only for SOCK/FIFO; REG, DIR and LNK set has_body=false and answer NFS3ERR_BADTYPE, which is what RFC 1813 asks for. An out-of-range ftype is an XDR error and gets GARBAGE_ARGS (proc 11 was added to the malformed-argument test).
- rdev: specdata1/specdata2 become `makedev(major, minor)` = (major<<32)|minor, and `fattr` reads them back with dev_major/dev_minor. The round trip is lossless for full u32 majors and minors. The NFS tests only use small values (1:3, 8:16); the wide-value round trip is covered by the Vfs/core layer and the FUSE unit test, not over the wire (note N3).
- Attributes: mode comes from sattr3 (Void defaults to 0o644), masked to 0o7777 by core. The server applies no umask, which is correct because the NFS client applies it. uid/gid in sattr3 are ignored; the node belongs to the mounter like everything else in cowfs. nlink 1 and size 0 are asserted by the new test.
- Device policy: `device && ctx.auth.uid != 0` gives NFS3ERR_PERM, with a wcc reply and nothing created (test asserts the name stays NOENT, then root succeeds). FIFO and SOCK are allowed for uid 1000.
- AUTH_NULL: `ctx.auth` starts as `auth_unix::default()` (uid 0, tcp.rs:265) per connection and is overwritten only when a call carries AUTH_UNIX (rpcwire.rs:50-53). So an AUTH_NULL client reads as root, and an AUTH_UNIX call with uid 1000 stays sticky for later AUTH_NULL calls on that connection. The PERM check is therefore bypassable by any client that sends AUTH_NULL; the builder states this and it is correct.
- Security assessment of that bypass: the server binds 127.0.0.1 only (cowfs-nfs/src/lib.rs:74), and MNT answers only for one per-mount random-looking export path that only `mount_nfs` is told (mount.rs:166). Anyone who can reach the port and learn the path can already read, write and delete the whole tree over raw RPC with no authentication, so unauthenticated device creation adds no new class of exposure.
- A device node is inert on the server: cowfs stores `kind` and `rdev` in its own redb store and never calls mknod on the host (core vfs_impl.rs:45-52, ns.rs:199-202).
- The real exposure is on the client. A device node on a mount lets a root user on the macOS client open the local device with that major/minor, unless the mount is nodev. The receipts show the mounts were `nfs, nodev, nosuid, mounted by zeeshanhaque` (identity.json), which macOS sets for non-root mounts. `nfs_option_string` (mount.rs:127-130) does not pass nodev or nosuid itself, so a daemon run as root is not guaranteed nodev. Recommendation (non-blocking): add `nodev,nosuid` to the mount_nfs option string.
- READDIR/READDIRPLUS/GETATTR/LOOKUP: all go through `ftype()` and `fattr()`, which now map Fifo, Socket, CharDevice and BlockDevice; the old SERVERFAULT wildcard remains only for unknown kinds. The new test checks type, mode, nlink, size and rdev through GETATTR after LOOKUP. READDIRPLUS for the four kinds is not asserted over the wire (the pjdfstest unlink/00.t and mkfifo runs exercise readdir implicitly).
- SETATTR, REMOVE, RENAME, LINK of special nodes use the generic paths; the semantics are pinned at the Vfs level by the special_* conformance checks (Core and MemVfs), and on the real macOS mount by unlink/00.t (77 ok / 35 not ok identical on both arms). There is no NFS wire test of LINK or RENAME on a special node.
- Replay cache: NON_IDEMPOTENT is now `[2, 8, 9, 10, 11, 12, 13, 14, 15]`. MKNOD (proc 11) was missing before; it was harmless while MKNOD always answered NOTSUPP but would have double-created on a retransmit once real. every_non_idempotent_procedure_replays now sends a MKNOD twice and passed on both OSes.
- Stale handles: mknod uses `ident(dir)` plus `not_side`, `new_name`, `not_a_view`, `with_names`, the same guards as symlink and mkdir; mknod_stale_parent runs at the Vfs level.
- Store flip: the first persisted special node bumps a version 2 store to 3 inside the same write transaction (slice A review, lines 36-48). An old build then refuses the store at open with `Format("format version 3, this build reads 2")`. For an NFS client that means the daemon of an old build fails to start and the mount never appears; there is no partial state visible. A store that never held a special node stays openable by old builds. Version 3 is permanent once a special node was committed (slice A note N1). This PR does not add an NFS-level test of the flip, and it need not.

## 3. FUSE (slice C)

- Type bits: `mknod_kind` maps 0 and S_IFREG to the existing create path, S_IFIFO, S_IFSOCK, S_IFCHR and S_IFBLK to `Vfs::mknod`, and anything else (directory, symlink) to EINVAL, as Linux does. The constants are the correct octal values.
- dev_t: `rdev_from_kernel` is exactly glibc/kernel `new_decode_dev` (major = (d & 0xfff00)>>8, minor = (d & 0xff) | ((d>>12) & 0xfff00)) and `rdev_to_kernel` is `new_encode_dev`. The kernel FUSE client uses the new encoding on the wire, and the unit test pins makedev(8,16) = 0x810 and round-trips (4095, 1048575) and (259, 70000). Majors above 12 bits or minors above 20 bits created through NFS are truncated when read through FUSE (the unit test pins this). It silently aliases a different device number; acceptable because nothing can open it, but note N4.
- Permission policy: a device from `req.uid() != 0` is EPERM, as a second line; the kernel already demands CAP_MKNOD before the request reaches FUSE. `allow_other` does not change this because the check is on the request uid. Mount options add no `dev`, and fusermount mounts nodev by default, so a device node on the mount cannot be opened as a real device; the kernel handles fifo and socket I/O locally (init_special_inode), so fifo and socket open never reaches the daemon. I did not verify fuser's mount path against libfuse; this is from the documented fusermount defaults.
- umask: ignored in the handler; the kernel applies it before the request unless FUSE_DONT_MASK is negotiated, which this adapter does not.
- attrs and readdir report the real type (`file_type`) and `rdev_to_kernel`; Probe forwards mknod.
- Test coverage: FUSE mknod has exactly one test, special_files_through_mknod, and it is weak in three places:
  - `assert!(!tool(["mkfifo", ...]), "a second mkfifo is EEXIST")` accepts any failure, not EEXIST (the log shows `File exists`, so it does hold today).
  - The non-root branch accepts any mknod failure as EPERM.
  - The root branch, the only code that proves the dev_t path through a real kernel, never ran in CI.
- Hazard N5: the new test calls `mkfifo -m 640` and `mknod` as external tools; a CI image without coreutils tools would fail loudly, which is fine.

## 4. The 16 skipped special checks

- The PR body says the harness "serves a host directory through PathVfs behind the mount, which has no mknod". That is wrong. The mount is served by MemVfs (tests/common/mod.rs: Probe over MemVfs, which has mknod). PathVfs is the conformance suite's client view of the mounted directory (conformance.rs lines 1-4 and 52-65), so the 16 checks fail on the client side because `PathVfs` lacks `mknod`, not because the mount cannot do it.
- The same wrong sentence is in docs/special-files-107.md and in the skip reason text.
- A better route exists and is cheap: `cowfs-vfs-path` already allows unsafe in sys.rs and depends on libc, so `PathVfs::mknod` (libc::mknodat, fifo and socket and, as root, devices) would turn the 16 SKIPs into real FUSE coverage, take the run from `128 run, 25 skipped` to 9 skipped, and cover setattr, link, unlink, rename, readdir kinds, open, io on special files through the mount. It would also let the same checks run against the macOS NFS mount.
- As it stands FUSE special files are covered by ONE test, which does not run as root in CI. The honest line in the PR is "FUSE mknod is covered only by special_files_through_mknod", and it says that. The `128 run,` count is correct as printed in the linux-fuse log (128 run, 1 failed, 25 skipped, 2 heavy not enabled), and ci.yml's hard-coded `^128 run,` stays valid.
- Not blocking, but I would file a follow-up issue for PathVfs::mknod; slice D is the natural home.

## 6. pjdfstest evidence (read-only, from the receipts)

- Identity: native arm is apfs (/dev/disk3s1s1, st_dev 16777234); cowfs arm is nfs `localhost:/cowfs-...` (st_dev 436210286 and 436210287) with `nodev, nosuid`. They are different filesystems, and each run had its own store and mount.
- Run 20261009T042113Z (harness state PASS): mkfifo/00.t and mknod/00.t. All four tap files give 25 ok / 11 not ok with the identical sequence `++++++++++++++++-------+----++++++++`. The 11 not-ok are the same on the native arm, so they are non-root artefacts and not cowfs behaviour. They also mean all root-only assertions (device creation, chown) never ran: the NFS device path, rdev through the macOS client and the PERM policy are untested on a real mount.
- Run 20261009T042425Z (harness state FAIL): open/17.t cowfs `+-+` against native `+++`; open/24.t 5/5 on both; unlink/00.t 77 ok / 35 not ok on both arms with identical sequences. The summary lists open/17.t #2 as an ESTABLISHED regression. The PR body reports it, which is honest. The harness verdict (PASS in run 1) was not used as acceptance; the per-case sequences were.
- Provenance gap: identity.json records cowfs_head 7332ff3 (run 1) and 24a1fb3 (run 2), never b4dc909, with the same daemon binary hash in both, built from an uncommitted tree. The NFS source is identical between 24a1fb3 and the head (`git diff 24a1fb3 b4dc909` over nfsserve, cowfs-nfs/src, cowfs-vfs and cowfs-core is empty), which makes the NFS result applicable to the head in practice, but the binary is not provable from the receipt.
- open/17.t #2 root cause: UNVERIFIED hypothesis only, I could not run a mount.
  - The test is `mkfifo f 0644; expect ENXIO open f O_WRONLY,O_NONBLOCK`, run as a non-root user who owns the node.
  - ENXIO for a write-open with no reader is produced by the client kernel's fifo layer after the vnode passes its access check; the server does not know about opens (no OPEN in NFSv3). So the EACCES came from the client's authorisation step before fifo_open, which on macOS for an NFS vnode consults cached attributes or an ACCESS RPC.
  - The server's ACCESS reply (`access_granted`, nfs_handlers.rs:274) is purely mode based and generic: for a 0644 node owned by the mounter it grants READ, MODIFY and EXTEND, so I see no server bug there. That points to the mode or owner attributes the client holds for the new node, or a client rule for special vnodes, rather than the ACCESS reply.
  - Checks that would decide it in minutes: tcpdump on lo0 for the open (does the client send any ACCESS or GETATTR, and what mode, uid, gid and rdev are in the fattr3 of the MKNOD reply), `stat` of the fifo on the mount immediately after mkfifo, and the same open as a plain `python3 -c 'os.open(p, os.O_RDWR|os.O_NONBLOCK)'`.
  - The urgent question is not the errno but whether a fifo can be opened for writing at all on the mount. That decides whether fifos are usable or only creatable, and nothing in the evidence shows a reader and writer exchanging data.
