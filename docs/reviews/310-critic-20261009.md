# Critic report: PR #310 (issue #302, power_core follow-ups)

Verdict: MERGE-AFTER-FIXES (small, test and doc only; nothing blocks correctness).

Scope checked: diff vs main, branch origin/test/power-core-followups-302.
No live mount touched. I did not re-run the sweep; CI is green (lint, ubuntu x2, macos, fault-seam, namespaces, fuse).

## Confirmed fine

No production code changes: the four files are Cargo.lock, tests/mutate_power.py, tests/power_core.rs, docs/crash-injection-173.md.
Cargo.lock +1 line is the existing self dev-dependency (`cowfs-core` with `fault-injection`, Cargo.toml line 28) that the lock was missing. Harmless, but unmentioned in the PR body.
Trace file lives under `CARGO_TARGET_TMPDIR/power_core` (inside gitignored `target/`), so it cannot be committed.
Trace size is bounded: one line per store op (about 280 to 410), plus about 14 root ops and a handful of acks, written only when a workload has failures. Roughly 20 to 40 KB per failing workload, at most 2 by default.
Trace `k` index is `run.ops` index, the same `k` as the tag, so the "k names a line" claim is true.
The new post-swap ops go through the model helpers (`put`, `rename_file`, `unlink`, `remove_snapshot`) which update `live` and `touched`, and the target snapshots exist with the needed files (`g` put into s1 before promote to base, `e` put into s3 before promote to fresh). They are scripted, not seeded, and `rand_phase` runs before them, so HashMap order changes only store-op order, not these `unwrap`s. Not a flake source for any workload seed.
`finish_swap` equivalence for I4 holds in the code read: `drop_intent` does remove then `sync_dir`; a resurrected intent with target present and no staging snapshot only drops the intent. Target removed by the user with staging gone goes to the "unreadable or absent" path (`kept` false), which only unregisters and removes the file. The 513/2400 and 386/1860 vs 5 and 6 numbers are consistent with the mechanism.
I3 and I4 patterns now hit `drop_intent` in swap.rs (`self.drop_intent(target);\n        entry.ok_or` at line 470 and `Ok(()) => sync_dir(&self.inner.root),` at line 483). Both strings are unique in the file.

## Findings

F1 (medium, harness): `mutate_power.py` does not fail loudly on a stale pattern.
It writes `PATTERN NOT FOUND` into `results.txt`, continues, and exits 0.
That is exactly how I3/I4 went stale unnoticed after the swap refactor. The PR re-anchors the patterns but leaves the failure mode.
Fix: at the end, exit non-zero (or print to stderr) if any mutant reported PATTERN NOT FOUND or COMPILE ERROR.

F2 (low, harness): the kill-detail regex is stale.
`re.findall(r"FAIL (k=\S+ seed=\d+ op=...)")` expects tags starting `k=`, but this PR changes tags to start `w=<seed> k=...`.
So "first image:" is silently dropped from every KILLED line. Change to `FAIL (w=\d+ k=\S+ ...)`.

F3 (medium, test strength): `resurrected` is a counter only. Nothing asserts it, and the I4 mutant still SURVIVES.
So the new post-swap ops have no regression guard: deleting them, or breaking `resurrected()`, leaves CI green.
The doc's core claim (resurrected intents meet user ops) rests on a number printed in a log nobody reads.
Cheap fix: `assert!(all.resurrected < all.images / 100)` is wrong direction for the clean run; better assert on a mutant-agnostic invariant such as "the post-swap ops exist in rops/ops" (like the `swaps` count assert), or assert `all.resurrected > 0` only in a dedicated negative-control style test with I4 emulated. At minimum say in the PR that it is observability only.

F4 (low, soundness of counter): `resurrected()` checks `dir.join(n).exists()` for any `Unlink(n)` before the cut, without checking that no later `Create`/`Rename` of the same name occurred before the cut.
Today each intent name is created once and unlinked once (same target swapped once per workload), so it is exact. A future second swap of the same target would be over-counted. Add a comment or a "no later Create of n at root_at < k" check.

F5 (medium, docs accuracy): the knob advice is wrong at the low end.
Doc says "keep at least 1 workload with 3 seeds" to satisfy `images > 1000`.
Images per workload are about (ops+1) x seeds. The doc itself says ops range 280 to 410, so 280 x 3 = 843 images, which fails the assert; only at 355+ ops does it pass. Recommend 1 workload with 5 seeds (about 1400 to 2050), or 2 workloads with 3 seeds.
Also `rand_phase` uses `COWFS_POWER_WORKLOADS` seeds 0..n, so workload seeds beyond 1 have never been exercised in CI; the scripted unwraps are safe, but the doc's "turn it down" path is the only supported direction.

F6 (low, docs honesty): the timings line "74 s on ubuntu, 212 s on macOS, negative control 94 s" is attributed to PR 299, not measured on this PR. This PR adds 5 post-swap ops and a root-op scan per image (`resurrected()` is an O(rops) loop with up to 14 `exists()` syscalls per image, about 4000 images), so the sweep is a little slower than the 299 numbers. The PR body claims about 70 s on cachyos (consistent with before), so expect macOS roughly 215 to 230 s. macOS check passed here; I did not read its duration. Please quote this PR's CI durations in the doc or label the figures as from 299.

F7 (low, CI log bounds): the trace is printed to stderr in full (up to about 40 KB per failing workload, two workloads). Bounded and acceptable, but it prints before the `FAIL` lines, so the summary lines are buried under it. Consider printing the `FAIL` lines first or capping the trace print (for example the last 120 lines around the first failing k, full file on disk).

F8 (low, hygiene): trace and kept-image dirs accumulate under `target/tmp/power_core` across runs and are never cleaned; `KEEP_MAX` limits images per run only. Acceptable for `target/`, but CI artifact upload of that path is not wired in this PR, so "a path CI can upload" is aspirational. Say so or add the upload step.

F9 (nit, PR body): lists no Cargo.lock change. It claims "all mutants killed except I2 and I4", which matches the doc table. I4 "equivalent" is argued, not proven; the doc wording "equivalent" is fair given recovery code read above.

## CI macOS time impact

Added work per image: one `resurrected()` scan (cheap) and slightly more store ops in the recording (5 ops). Estimated under 5 percent on top of the 212 s macOS figure. Not a risk for the timeout, but the sweep remains the longest job.

## Recommendation

Merge after F1, F2, F5 and F6 (doc and script fixes, no Rust logic). F3 is worth a follow-up issue if not fixed here, since it is the point of the PR's F2 item.
