## 2. The test fails on the old behavior

I extracted b23a311 with `git archive` into the scratchpad, replaced `adapter.rs` with the parent commit's version, and ran `cargo test -p cowfs-nfs --test protocol chown_to_another`.
It failed at `protocol.rs:246` with the message `other uid`, left 0 and right 1.
That is `NFS3ERR_OK` against `NFS3ERR_PERM`.
The old code path is `Adapter::setattr` doing `self.apply(i.ino, set_attr(s))`, with `convert::set_attr` documented "uid and gid are dropped" and building a `SetAttr` that has no uid or gid field.
`apply` then either returns a plain getattr (empty change set) or calls `vfs.setattr`, so a uid-only or gid-only request answered OK and changed nothing.
Result: the test is a real regression test, not a tautology.

## 3. Policy

Issue 110 offers two defensible shapes: answer EPERM for a change the filesystem will not make, or answer 0 and document that ownership is fixed.
The PR picks the first, and issue 110 says the lie ("a caller that chowns and then reads ownership back gets an answer it did not ask for") is the thing to avoid.
The pjdfstest run behind 110 was unprivileged (native answers EPERM), 713 assertions pass on the mount and fail natively, 226 `chown` and 487 `lchown`.
So for the measured population the new behavior moves cowfs toward native, which is the point of the issue.

Root.
pjdfstest `chown/00.t` style cases run as root natively succeed in changing ownership and then check it with lstat.
cowfs cannot store another owner, so it fails those cases either way.
Before the PR it failed late (success, then the uid assertion); after it fails at the chown call with EPERM.
Silent success for root would be the same lie as the original bug, and EPERM for every caller matches what an NFS server with root-squash gives root.
EPERM-for-root is the right call for a server that cannot store another owner.
The cost is that root-run tooling that preserves ownership (tar -p, rsync -a, cp -a, install -o as root) will now report an error where it used to report nothing.
I did not run those tools against the mount, so how each one reacts is unverified.
That is a visible behavior change and belongs in the release notes when it ships, but it is the honest direction.

The chgrp divergence.
An owner chgrp to a group the owner belongs to is success natively.
Before the PR cowfs answered success with the gid unchanged, so a later lstat gid assertion already failed.
After the PR it answers EPERM at the call.
I found no currently green case that this turns red.
Evidence: `git grep` over `crates/`, `bench/*.py` and `docs/` (excluding bench/out) finds no pjdfstest or conformance expectation list that names chown, chgrp, 714 or any ordinal count.
`bench/pjdfstest.py` is a native-versus-cowfs ordinal differential with no allowlist, so its numbers (the 714 chown/lchown looser rows in `docs/reviews/pjdfstest-g3-final.md`) will move, and are expected to shrink.
`bench/xfstests_gate.py:129` excludes tests that chown (needs a second user or root), so the xfstests gate is unaffected.
`crates/cowfs-fuse/tests/battery/test_cowfs_extra.py:44` chowns a symlink to its own uid and gid, which is FUSE and which is the no-op case anyway.
The only in-tree uid use in nfs unit tests is `convert.rs:187`, which tests `set_attr`, not the adapter.
The harness has not been rerun, so the actual movement of the pjdfstest numbers is unmeasured.

## 4. Siblings and ordering

Callers.
`Adapter::setattr` is the only place the new check is called, in `adapter.rs` after line 431.
`Adapter::create` (line 525 on) takes an `sattr3` but reads only mode and size from it, and `side_create` reads only size.
A create carrying a uid or gid is therefore still accepted and ignored.
That is a narrower gap than chown, matches the "SETATTR" scope of issue 110, and is not a regression.
It is worth a line in issue 160 or a new issue (see notes).

Mode in the same request.
`owner_unchanged` runs before `apply`, and on the plain path it is inside the same `and_then` chain, so a refused request applies nothing.
The test covers it: a request with uid+1 and mode 0o600 gets PERM and the mode is unchanged.
Size and timestamps ride in the same `SetAttr`, so they are covered by the same early return.

Durability barrier.
On the plain path `owner_unchanged(...).and_then(apply...).and_then(fa)` is assigned to `out`, and `durable_or(i.ino, &out)` runs unconditionally after it.
So a refusal still goes through the barrier, and a failed barrier outranks the refusal's status, exactly as the existing comment says.
The sidecar path returns from `side_setattr` with no barrier, as it did before the PR; the PR does not change that, and the commit message says only that the plain-path refusal flows through the barrier, which is accurate.

AppleDouble parity.
The PR's own test covers only a plain file.
I added a probe test in the scratch copy: create `doc` and `._doc` under `AppleDoubleMode::Hide`, then SETATTR on the sidecar handle.
Results: other uid gives PERM, other gid gives PERM, same uid and gid gives OK, a gid-only request naming the current gid gives OK, and a refused gid change combined with mode 0o600 on the plain file leaves the mode untouched.
All assertions passed, so sidecar parity is real; it is simply untested in the PR.
`side_attr` goes through `fa`, which applies the same `opts.owner` override, so the owner compared on the sidecar is the owner reported to the client.

Reported owner.
`owner_unchanged` compares against `self.getattr(id)`, which for plain files is `vfs.getattr` then `fa` (with the `opts.owner` override) and for sidecars is `side_getattr`.
That is the same value the client sees in attributes, so "naming the current owner is a no-op" holds under both `owner: None` and `owner: Some(..)`.
An unknown handle returns the getattr error (STALE or similar) before PERM, which matches the order the old code produced from `apply` or `side_file`.

Doc edits.
The `types.rs` comment now says the NFS adapter answers EPERM and the FUSE adapter still accepts and ignores.
That is accurate for this commit, and `docs/v1-architecture.md` says the same with the issue numbers.

## 5. Advisor audit marker

The hook is `~/.claude/hooks/advisor-commit-gate.sh`.
It blocks `git commit` unless `~/.claude/state/advisor-audit/<sha16>` exists, where sha16 is the first 16 hex characters of the sha256 of `git diff --cached` (or `git diff HEAD` when the command has `-a`/`--all`).
It exits 0 when that diff is empty, when `ADVISOR_AUDIT_OFF=1` is set, or when the command does not match its `git commit` regex.
The state directory holds exactly two empty marker files: `3b2f3b321660dbda` (Oct 8 13:00:01) and `dbe50423b15c42a2` (Oct 8 13:49:32).
The commit b23a311 is dated 14:25:50, after both markers.
`git diff b23a311~1 b23a311` hashes to `75ab192f4c71304a`, and the crates-only diff hashes to `5b96096dcc4de2ba`.
Neither matches a marker.
So there is no audit marker for this exact diff.
The hook either did not fire (for example the commit ran with `git -C <worktree>` while the hook's cwd had an empty staged diff, which exits 0 by design, or `ADVISOR_AUDIT_OFF=1` was set), or it was satisfied some other way I cannot see.
I cannot tell which from the artifacts, so I report it as: the gate did not reject, and no matching marker exists.
This is a process gap against the standing rule "advisor diff contract audit before staging a commit", not a code defect.
The audit can still be run on the PR diff before it leaves draft, and its marker will be keyed to the diff then staged.
