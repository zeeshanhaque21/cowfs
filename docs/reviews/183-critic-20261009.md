## 2. Issue 88 constraint (release builds, feature unification)

The workspace uses `resolver = "2"` (`Cargo.toml` line 2). Resolver 2 does not unify dev-dependency features into a non-test build.
The `fault-injection` feature is declared once (`crates/cowfs-store/Cargo.toml:12`, `fault-injection = []`, not in `default`).
It is enabled in exactly two places, both under `[dev-dependencies]`: the store's own self edge (line 31) and the new `cowfs-gc` line (`crates/cowfs-gc/Cargo.toml:20`).
`cargo tree --workspace -e normal,build -i cowfs-store -f '{p} {f}'` shows 0 lines with `fault`.
I ran `cargo build --release -p cowfs-daemon -j2` in the scratch clone (finished, 5m53s). `grep -ac C7D_EXIT target/release/cowfs-daemon` returned 0.
So a normal release daemon build does not get the seam from the new dev-dependency, and the control surface, daemon and CLI gain no new public API (the diff touches none).
The remaining caveat is the one the doc already states: `cargo build --workspace --all-targets` or `cargo test` unifies the feature onto the lib. That is pre-existing and not a shipping build.

## 3. Soundness of the test

Is the sweep vacuous? I probed it directly.
Probe A, receipts: `want` holds 12 blocks, 36000 bytes. The set is non-empty and every block is compared byte for byte, so the readback is real.
Probe B, are the crashes inside `collect`? I made the child return after opening the store and gc but before `collect`. The sweep then failed with `the sweep crashed only 0 times`. So `Store::open` and `Gc::open` contain zero boundaries and all 72 crashes are inside `collect`.
Probe C, does a status 77 mean the seam? The test asserts the exact code 77 for every non-zero exit. A panic or other failure exits 101 and fails the test. The control run asserts exit 0, `freed > 0` and `unlinked >= 2`.
Probe D, my own mutation: after the live set is built, drop one live block from `live` in `Gc::collect` (`live.remove(...)` before `r.live_blocks = live.len()`). The test FAILED at the control receipts: `uncrashed control: live block lost: block 3469ae... not found`. The readback is sensitive to the loss of a live block.
Reads in the parent come from a freshly opened `Store` in a different process from the child, so no in-process cache can mask a missing block. The OS page cache is not a concern for process-exit semantics.
Rerun result in the scratch clone (macos): `crash_inject: 72 crashes over 73 boundaries, 26 after an unlink, control freed 118856 bytes in 4 packs`. 72, 73, 118856 and 4 match the PR. The "after an unlink" count was 26, not the 28 in the PR body. The test only asserts it is greater than 0, so this is a platform or timing variation of the figure, not a defect. See note N1.

## 4. Mutation 2 and scope wording

Claim: a boundary fires after its operation, and an unsynced write survives a process exit, so moving the unlink before the watermark raise cannot be caught.
Agreed. In `crates/cowfs-store/src/fsio.rs`, every `fault_boundary` call sits after the operation (`write_all_at` then boundary at line 149-150; `sync_data` then boundary; `rename` then boundary). `fs::remove_file` in `compact.rs` (line 484) calls no boundary at all.
If the unlink were moved before the watermark write, there is no boundary between them, so no crash image can show "unlinked, watermark not raised". The first image after the pair already contains the watermark write, which a process exit keeps in the page cache. Mutation 2 is not catchable by this seam.
The doc and the test header both say so plainly, and name the follow-up (a `fault_boundary` after `remove_file`, deferred because it shifts hard-coded n in store tests).
The scope wording is honest. It states: no daemon-level claim; no power-loss claim; the metadata-commit edge and the collector's `gcstate` writes are outside `Io`; the freeze `meta.sync` window is not crash-tested; the daemon `gc_crash` case still frees 0 bytes; g6 stays open.
One small precision gap, see N3: the freeze-time metadata sync is mentioned in the test header and doc but not in the PR body's "Not covered" list by that name.

## 5. check-fault-seam-absent.sh

Robustness points that hold:
- It uses a private `CARGO_TARGET_DIR` (`target/seam-check`), so it cannot be fooled by stale artifacts in the shared target.
- `set -euo pipefail`; the count helper uses `grep -ac` with `|| true`, so a missing rlib gives a failing `[ "$off" = 0 ]` only if the file is absent, which `cargo build` would have errored on first.
- The positive control is real: it touches `lib.rs`, rebuilds `cowfs-store --features fault-injection`, and requires more than 0 hits. Both CI logs show 1 hit with the feature on and 0 off, so the pattern demonstrably matches the string when present.
- A wrong grep pattern cannot pass vacuously, because the positive control would then find 0 and fail with "the check is blind".
- Works on both OSes: the step passed on ubuntu and macos in CI. `grep -a` and `cargo tree` are portable.
Weaknesses, all non-blocking:
- The `cargo tree ... -p cowfs-daemon` check covers only the daemon's graph. `cowfs-cli`, `cowfs-fuse`, `cowfs-nfs` and `cowfs-ctl` are not covered by the graph check, and the rlib build of `-p cowfs-store -p cowfs-gc` would not see a feature enabled by one of those crates (see N2).
- It checks a debug rlib, not a release binary. The PR body and doc say so. My release-binary grep (section 2) closes that gap for this head, but the script does not repeat it.
- `cargo tree -e features` output matching `fault-injection` is a text grep. It is guarded by a positive control for the tree check too (the `--features fault-injection` line), which is good.

## Non-blocking notes

N1. The "28 after an unlink" figure did not reproduce here (26 on macos). Suggest wording it as "N after an unlink (platform dependent)", or print it from CI with `--nocapture` so the PR figure is the CI figure.
N2. Extend the graph check to `cargo tree --workspace -e normal,build -i cowfs-store -f '{p} {f}'` and fail on `fault-injection`. That covers cli, fuse, nfs and ctl as well as the daemon. I ran exactly this and it returns 0 lines.
N3. Consider adding one CI line that greps a built `cowfs-daemon` for `C7D_EXIT`. It is cheap once a release or debug daemon is built, and checks the shipping artifact rather than an rlib. The doc already admits CI has no release build.
N4. The `mid_reclaim` assertion only requires greater than 0. A floor (for example at least half of the unlink-bearing boundaries) would stop a future change that quietly removes most unlink crashes from still passing.
N5. `copy_tree` and `pack_files` helpers are test-local; fine, but `COWFS_GC_INJECT_DIR` child gating relies on the env var being absent for the parent run. It is, and the child returns at once otherwise (`child_collects_once ... ok` appears in every run).
N6. The future `fault_boundary` after `remove_file` is the only way to close mutation 2 at process-exit level. Worth filing as its own issue once slice 1 merges.
