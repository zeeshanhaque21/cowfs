## 2. Mode mapping

Read: kernel `fs/fuse/file.c` `fuse_file_fallocate` and `fs/open.c` `vfs_fallocate`, both at tag v6.8 (fetched). The runner's actual kernel is UNVERIFIED.

Correction to the premise in the task: v6.8 `fuse_file_fallocate` returns EOPNOTSUPP for `mode & ~(KEEP_SIZE | PUNCH_HOLE | ZERO_RANGE)`.
So collapse and insert are NOT forwarded to FUSE on v6.8. Only 0, KEEP_SIZE, PUNCH_HOLE, ZERO_RANGE reach the daemon.
The PR doc statement ("kernel forwards only the keep-size, punch-hole and zero-range bits") is correct for v6.8.

`convert::falloc_mode` (convert.rs, new) by case:

| mode | adapter result | what the kernel does first |
|---|---|---|
| 0 | Allocate | forwards |
| KEEP_SIZE | KeepSize | forwards |
| PUNCH_HOLE\|KEEP_SIZE | PunchHole | forwards |
| ZERO_RANGE | ZeroRange | forwards |
| ZERO_RANGE\|KEEP_SIZE | ZeroRangeKeepSize | forwards |
| PUNCH_HOLE alone | ENOTSUP | `vfs_fallocate` EOPNOTSUPP, never reaches FUSE |
| PUNCH_HOLE\|ZERO_RANGE | ENOTSUP | `vfs_fallocate` EOPNOTSUPP |
| COLLAPSE, INSERT | ENOTSUP | fuse EOPNOTSUPP (v6.8) |
| UNSHARE_RANGE (0x40) | ENOTSUP | passes `vfs_fallocate`, fuse EOPNOTSUPP |
| NO_HIDE_STALE, unknown bits | ENOTSUP | EOPNOTSUPP |

- All the adapter's ENOTSUP arms are defensive for the kernel path, and correct for any other FUSE client. `libc::ENOTSUP == EOPNOTSUPP` (95) on Linux, so the mount test comparing against `libc::EOPNOTSUPP` is consistent.
- Mask values are right: KEEP 0x01, PUNCH 0x02, NO_HIDE_STALE 0x04, COLLAPSE 0x08, ZERO 0x10, INSERT 0x20, UNSHARE 0x40.
- Offsets and lengths: fuser signature order `(ino, fh, offset, length, mode)` matches `Fs::fallocate`. `offset()` is `u64::try_from(i64)`, so negatives are EINVAL. The kernel already rejects `offset < 0 || len <= 0` with EINVAL in `vfs_fallocate`, so the adapter check is unreachable through the kernel and still correct.
- Overflow: `vfs_fallocate` returns EFBIG for `offset + len` over s_maxbytes or negative. Past MAX_FILE (but under s_maxbytes) the Vfs returns FileTooBig, mapped to EFBIG by `Error::errno` (cowfs-vfs `error.rs:68`, also tested in `lib.rs:57`). The `1 << 42` case in the mount test takes this adapter path.
- Handle versus inode: `_fh` is ignored and the call uses `ino`, same as other inode-keyed lanes. A read-only descriptor gets EBADF from `vfs_fallocate` (`!(f_mode & FMODE_WRITE)`) before FUSE. A read-only mount is enforced by the kernel `MountOption::RO`; fs.rs has no separate `read_only` check on the write paths, so this is consistent with the others.
- Special files: `vfs_fallocate` returns ESPIPE (fifo), EISDIR, ENODEV (non-regular, non-block) before `f_op->fallocate`. This now VERIFIED from source for v6.8, upgrading the PR's "from memory" caveat. Core and MemVfs return InvalidArgument for non-regular kinds, unreachable through the kernel.
- Kernel post-success handling (v6.8): it updates size via `fuse_write_update_attr` when no KEEP_SIZE, truncates the page cache for punch and zero-range, and calls `fuse_invalidate_attr_mask(MODSIZE)`. So returning `()` with no attributes is correct, and mtime/ctime and blocks are refetched. The comment on `Core::fallocate` is accurate.
- Kernel never gets ENOSYS from this adapter (no_fallocate latch not triggered).
- Wrappers that forward `Vfs`: the PR covers the daemon test-only `GuardedView` (`crates/cowfs-daemon/tests/separate_adapter_namespace.rs`) and the fuse test `Probe`. The PR body is right that the real daemon path hands `Core` and `SnapshotView` directly (both forward, `view.rs:188`, `vfs_impl.rs:136`). `conformance.rs` `Keep` forwards through a macro (line 78). 
- Wrappers that do NOT forward and silently answer NotSupported (the trait doc at vfs.rs:204 says forwarders must forward): cowfs-nfs tests (`ns_durability.rs`, `contract.rs`, `separate_adapter_namespace.rs`, `namespace_race.rs`, `common/reuse.rs`, `common/counting.rs`), `cowfs-vfs-test/tests/runner.rs` `Bad`, and `cowfs-vfs-path` PathVfs (slice D by design). No NFS code path calls fallocate (`rg fallocate crates/cowfs-nfs` hits nothing in src), so there is no behaviour impact today. Non-blocking.

## 4. Mount test strength

Real kernel path: yes. `libc::fallocate` on an fd of a mounted FUSE file, with `fs::metadata` size and blocks and `fs::read` against a byte model. It ran and passed on the Linux runner.

Mutation reasoning against the mapping (fixture is MemVfs behind Probe):

- KeepSize mapped as Allocate: caught (`KEEP` at 65536+4096 asserts size stays 65536).
- ZeroRangeKeepSize mapped as ZeroRange: caught (65000+5000 asserts size 65536).
- ZeroRange mapped as ZeroRangeKeepSize or KeepSize: caught (66000+1000 asserts 67000).
- Allocate mapped as KeepSize: caught (offset 70000 len 1 asserts length 70001).
- PunchHole to Allocate or KeepSize: caught (zeros plus blocks drop).
- Swap PunchHole with ZeroRangeKeepSize: NOT caught by the mount test. MemVfs treats them identically (`(true, false)` vs `(true, punch_grows)`), and the Vfs contract says they are the same. Only the unit test catches it: it asserts each mask maps to the exact variant. Fine.
- The "refusals" block (modes 0x08, 0x20, 0x40, 0x04, length 0) is answered by the kernel on v6.8 and never exercised the adapter. Only the `1 << 42` EFBIG assertion exercises an adapter plus Vfs error path. The refusals still guard against an adapter that wrongly accepts something, and they document observable behaviour. Non-blocking.
- `unsupported_operations_report_enotsup` now asserts collapse and insert are EOPNOTSUPP, again a kernel answer. It replaces the old `fallocate -l 4096` CLI check, which would now succeed, so the change is necessary.
- Not asserted: mtime and ctime after a punch (that is Core conformance, slice D).
- `#[allow(unsafe_code)]` is on the single helper `falloc` only (mount.rs:164), with a `SAFETY:` comment. Workspace `Cargo.toml:20` sets `unsafe_code = "deny"`. Not module-wide. Correct.
