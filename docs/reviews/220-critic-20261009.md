# Critic report: PR #220 (swap recovery, issues #176 and #177)

## Verdict: BLOCK (one narrow data-loss regression, small fix)

The design is sound and the tests are real, but the new orphan sweep destroys the only copy of a pending swap's tree when the swap target name ends in ".tmp".
This is a new loss path that main does not have.
Everything else checked holds.
CI at review time: lint, fault-seam, linux-fuse, linux-namespaces and both ubuntu test shards pass; macos test (1,1) still pending.

## Blocking finding

The sweep decides which staging snapshots are protected from `intents()`, which skips every file ending in ".tmp" (crates/cowfs-core/src/swap.rs:94-107, filter at the `!n.ends_with(".tmp")` line; `sweep_orphans` at swap.rs:~165-182 builds `named` from it).
A target named `X.tmp` writes its intent to `swap-X.tmp` (intent_path, swap.rs:~44), which `intents()` treats as a leftover temp file and ignores.
So after a crash or failed `finish_swap` past the point of no return, `Core::open` finds the staging snapshot `X.tmp.cowfs-swap0` "named by no intent" and unregisters it.
The old target is already gone, so the new tree is lost entirely.
Reproduced in a scratch clone with a probe test: `ingest_replacing` into "base.tmp" with `set_swap_fault(4)`, drop the Core, reopen, snapshot list has no "base.tmp" (probe fails with "base.tmp lost").
On main the same state kept the staging snapshot (not served, but recoverable), because main never swept.
Names ending ".tmp" are valid snapshot names (validate_snapshot_name only rejects leading dot, "/", control chars, the reserved marker).
Fix options: make the sweep protect any `swap-*` file by also reading intents whose name ends in ".tmp" (a valid 2-line intent with a staging name is an intent, whatever its name), or give the temp file a suffix a snapshot name cannot carry (for example a reserved marker) so the two cannot collide.
Add a regression test with a ".tmp" target.

## Crash-point walk (replacing ingest and promote)

| Point | Open / retry behaviour | Result |
|---|---|---|
| staging written, no intent | open sweeps orphan (swap.rs sweep_orphans) | correct, old target untouched |
| intent written, old target present | open: `finish_swap` sees target exists, skips fork, drops staged, removes intent | swap abandoned, old kept (same as main) |
| old target removed, no new target | open or retry: `recover_intent` forks staged into target, drops staged, clears intent | rolled forward once |
| new target published, staged and intent still there | `finish_swap` sees target, only drops staged and intent | no second fork, idempotent |
| intent cleared | nothing to do | clean |

Exception: the ".tmp" target above.
No ordering found that rolls forward onto a different tree than the intent names (`finish_swap` takes both names from the intent).
Torn intent: staging name is derived from the file name; `trim_start_matches("swap-")` strips repeated prefixes, so a target like "swap-x" derives "x.cowfs-swap0" (pre-existing, now also reachable through `recover_target`); the sweep then removes the real orphan anyway, and a torn intent has no readable owner, so low risk.

## Idempotency and concurrency

Second open after recovery: no-op, covered by `open_recovers_a_pending_swap_and_a_second_open_changes_nothing`.
A partial recovery (error in `finish_swap`) leaves the intent and the sweep keeps its staged snapshot because `named` reads the intent file (swap.rs sweep_orphans), which is correct for non-".tmp" names.
Sweep vs live ingest: `Store::open` takes flock on `store/LOCK` for the Core's life (crates/cowfs-store/src/store.rs:353-374), so a second Core or process cannot be staging during open; the claim holds.
Same-name concurrent ingest on two clones of one Core is still racy, as the PR body says: thread B's new `recover_target` can see thread A's fresh intent while A has not yet removed the old target, finish and delete A's staged tree, and A then loses it.
This is not worse than main, which unregistered A's staged leftover unconditionally, but the new call widens the set of interleavings; note it, do not block on it.

## Sweep pattern

Match is `is_staging`, which is `name.contains(".cowfs-swap")`, not `*.cowfs-swap0` (swap.rs:~38, cowfs_snapname::is_reserved).
User names cannot contain the marker (rejected at create, rename and ingest), so no user snapshot can be swept.
Staging names truncate the target to 200 chars (`staging_name`), so two targets sharing a 200-char prefix collide on one staging name (pre-existing).
Unusual bytes: names are `&str`, UTF-8, control chars rejected; no byte-pattern risk found.
A target of 255 bytes makes the intent file name 260 bytes and `write_intent` fails on most filesystems (pre-existing, error path rolls back).

## Durability and format

Intent fsync, rename, directory fsync order is untouched (write_intent unchanged).
`replace_with_staged` gains fault seams 2, 3, 4 only; no write order change.
No on-disk format change: confirmed, no struct, key, file name or record layout altered.

## Failing-first claims

Ran the branch tests on the branch: 9 of 9 pass.
Ran the branch's tests/swap.rs against main's crates/cowfs-core/src in a second scratch clone: 6 of 9 fail (the 6 new tests), the 3 older ones pass.
The orphan test fails on main with `["fresh.cowfs-swap0"]` surviving open, as claimed.
Honest limit: the tests use the `set_swap_fault` seam and an in-process copy of the store dir taken in a synchronous progress hook, not kill -9; the PR body says so for #176 and says the #173 seam is not a kill-at-point mechanism.
No real process-kill test exists for either issue.
