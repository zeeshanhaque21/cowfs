## What matches the claims
Importer sets atime and mtime per node with `Vfs::setattr(SetTime::At)`.
Directories are set after their children, so adding children does not move them. The root is set too.
Hardlinks use `Vfs::link`, keyed by (dev, ino), and only names inside the tree are counted.
The read-back compares mtime, link identity both ways (same source file, same inode; different source files, never one inode), and the final nlink per linked file.
No on-disk format change. `hash_tree` and `hash_view` still cover the same fields, so the hash verification is unchanged in what it covers.
Ordering is sound. `set_times` runs after content and after children. A hardlink name added to the directory currently being walked happens before that directory's own `set_times`.
The two core tests (mtime nanoseconds, hardlinks with the outside-name case and the equal-content-not-same-file case) would fail on the old importer. It never called setattr or link, so the mtime and nlink asserts fail.
The edit to `a_source_that_changes_under_the_import...` is honest. It keys on `total > 0 && done == total`, which still fires after the write and before the read-back compare, so the intent is kept.
Cancel paths are correct. `plan` now returns `Cancelled`, hash ticks return `Interrupted`, and the daemon maps that back to the cancel via `ctx.check()`.
`fsck_with` reports per record and during the live-set walk, and cancels with Interrupted.

## Findings
1. Docs not updated (MEDIUM). `docs/v1-daemon.md` section "import on the core backend" (lines 126-150) is the contract for what import keeps, and it says nothing about mtime, atime or hardlink preservation. It also says the import verifies "byte for byte" but now also verifies mtime and link identity. Add two sentences: times and in-tree hardlinks are kept, ctime is the import time, outside names are not counted. The same section says a fifo, socket or device is refused with invalid_params, while the code (pre-existing, `mknod`) accepts them. That staleness is not this PR's fault, but this PR edits the paragraph's subject, so fix it.
2. Hash-phase progress is a constant (LOW-MEDIUM). In `verified_report` the tick sends `done: 0, total: Some(hashed), Unit::Items` on every event. A client that renders a bar shows 0 of N for the whole hash, and any consumer that checks progress monotonicity or "done increases" learns nothing. It does reset the idle timer, which is the stated goal. Either count entries and send a real `done`, or send `total: None`. The PR body does not say progress is only a liveness pulse there.
3. Throttle skips the cancel check (LOW). When `throttle.due()` is false the ingest and fsck closures return true without calling `ctx.progress`, so cancel is observed at most every 50 ms plus one entry. Fine in practice. The `due()` first call always fires, so the first event is always sent. No bug.
4. Hardlinks of symlinks and special files are code-reachable but untested (LOW). The guard is `!md.is_dir() && nlink > 1`, so a symlink or fifo with two names goes through `view.link`. The PR Limits section admits only regular files are asserted. I did not confirm that `link` accepts a symlink or fifo inode in the core. If it refuses, the import fails with an opaque core error rather than falling back to a copy. Add one test for a hardlinked symlink and one for a hardlinked fifo, or make `link` failure on those kinds fall back to a separate inode.
5. Mismatch coverage gap (LOW). The new verify checks (`a hard link of the source is a separate file`, `two different source files are one file`, nlink count) have no negative test. Only the positive path is covered. A source that gains a hardlink during the import is the realistic trigger. This is a hand-run claim only; do not trust the PR's "verify now covers link identity" without one failing-case test.
6. Source changing during import (LOW). A file changed between write and read-back now fails on mtime as well as content. That is stricter and correct, but an in-use source (a build dir being written, atime aside) now reports a Mismatch on mtime-only touches that do not change content. It is a behavior change not called out in the PR body. The old `touch`-during-import was a success.
7. Unverified numbers in the PR body (INFO). The table (19 of 34 before, 0 of 34 after, n=3 and n=5, cachyos box) and "118 test binaries ok" come from a harness that is "kept out of the repo". I could not reproduce them here. They are plausible and consistent with issue 290 (19 of 34), but they are the author's claims. Ask for the harness log or a commit of the script under tools/ or docs/verification/.
8. Progress count semantics (INFO). `plan` reports `(0,0)` once per entry. The daemon turns `total == 0` into `None`, so a real client sees a phase with no total during the count. This is intended and tested by `reports_progress_while_it_counts...` (calls >= 30 is a weak lower bound, but it fails on the old code, which reported 10 or fewer).

## Safety
No data-loss risk found. The import writes to a reserved staging snapshot and renames only after verify, unchanged. Hardlinks and mtime failures abort the staging snapshot via the same outcome path.
Concurrency: the new maps live in per-call `Counters` and `Check`, with no shared state.
Memory: one HashMap entry per hardlinked source file (and one `owners` entry per non-directory node in the verify), which is O(files) at 1M files, roughly tens of MB. Acceptable but note it for the 1,000,000-file case that issue 290 names.
