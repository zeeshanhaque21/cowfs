## (a) core cfg(test) hook and the commit-error tests

The hook does not change production behaviour in any build.
`after_commit_fault` in `swap.rs` and its call site in `Core::move_name` in `lib.rs` are both `#[cfg(test)]`.
The thread-local `FAIL_AFTER_COMMIT` and `FAIL_BEFORE_COMMIT` sit in a `#[cfg(test)] thread_local!` block.
Release and `fault-injection` builds compile without them.
Integration tests under `tests/` never see them, since they link the non-test lib.
Nothing outside `swap.rs` references the new names.

The hook has one fidelity gap that does not matter here.
The test hook returns `Err` after `replace_snapshot` succeeded, so it does not reset `victim.removed`.
A real failing `replace_snapshot` does reset it.
The landed test only reopens the store afterwards, so this is harmless.

The "landed but Err" test genuinely exercises the data-loss guard.
I mutated `replace_did_not_land` to always return true, meaning the re-read always says "did not land".
`a_commit_that_landed_but_returned_an_error_keeps_the_intent_and_rolls_forward` FAILED, at the "intent kept" assertion.
The reason is that `unwind` sees the live registry still mapping the target to the old id and calls `rollback`, which drops the intent and the staging snapshot.
That staging snapshot is the only name holder of the new tree.

The mutation to always return false makes `a_commit_error_that_did_not_land_is_rolled_back_not_left_pending` FAIL.
Both directions are therefore pinned.

The test's own `durable_snapshots().any(name == staging || name == "abc")` check is vacuous, because "abc" always exists.
The real proof is the reopen assertion `has_f(&c, b"abc")`.
Tighten it to assert the staging row or the new id specifically (low).

The `Before` fault is a real `before_sync` hook failure through `Core::open_with_meta`.
This is the same mechanism production uses, so the "commit never writes" premise is genuine, not simulated.
The flag stays set while `rollback` runs.
The test still passes, so rollback does not depend on a further meta commit succeeding.
This is worth knowing but is not a defect.

## (b) daemon test expectation change

The new expectation is correct.
With the hook failing before the second commit writes, the re-read shows the old target and the staging snapshot intact, so the core rolls back.
The old tree (`AAAA-from-srcA`) stays, the intent file is gone, and the record reads unknown.
That matches `docs/v1-core.md` lines 168 to 173.
Those lines describe rollback when the re-read proves "did not land", and keep-intent when it is unknown or landed.

No doc promises the old premise.
The old premise was "intent pending after a failed second commit, reopen rolls forward".
`docs/v1-daemon.md` has no statement about it; line 94 only says one fork plus one replace-by-name commit.
The "intent pending after a commit error" statement survives in `docs/v1-core.md`, correctly scoped to the unknown and landed cases.
