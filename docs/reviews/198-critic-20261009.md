## 2. Semantics versus Linux fallocate(2) and MemVfs

I read `op_fallocate` in crates/cowfs-core/src/io.rs and `FileData::punch` in crates/cowfs-core/src/file.rs.
Mode mapping is Allocate = extend, KeepSize = nothing, PunchHole and ZeroRangeKeepSize = zero without extend, ZeroRange = zero and extend.
Any other mode is NotSupported, so collapse and insert are refused.
len 0 is InvalidArgument.
offset+len overflow and end past 1<<42 are FileTooBig, and the conformance check pins the exact boundary (max-1 plus 1 works, one more fails).
MemVfs now returns FileTooBig too, so Core and MemVfs agree; slice A's NoSpace note is closed.
The size decision and the chunk rewrite both happen under `node.st.wr()`, so there is no check-then-act window.
The punch flushes dirty extents first, builds the new chunk list as a value, and only then publishes it, so an error leaves the list unchanged.
On a punch error after the flush, the flushed list is queued, so a later sync cannot commit stale content.
Edge chunks are read, length-verified and re-chunked.
Chunk-aligned edges read nothing, and a unit test proves the surviving refs are byte-identical.
A punch inside an existing hole ref and a punch across a ref longer than HOLE_MAX are both unit tested, and refs stay valid (no zero length, no hole over HOLE_MAX).
Ranges past the chunk-covered total are clamped, so the implicit hole needs no work.
A punch or zero range past EOF with KEEP_SIZE keeps the size.
ZeroRange past EOF extends the size.
Directories give IsDir, and non-regular files give InvalidArgument (Linux gives ENODEV; the FUSE mapping in slice C should decide this).
mtime and ctime: zeroing modes and growth set both, KeepSize and Allocate-inside set ctime only.
This matches MemVfs, and the times check passes on Core.
Dirty-byte accounting subtracts the pre-flush dirty bytes after a successful flush, the same pattern as truncate.
Lock order: the gate is entered before the node lock, as in op_setattr's truncate, and docs/v1-core.md puts the gate outermost.
`scripts/lock_audit.py --check` passes ("lock-audit table is current (113 rows)").

## 3. Snapshot safety (own test)

I wrote crates/cowfs-core/tests/critic_snap.rs in a scratch clone only; it is not in the PR.
It writes a 6 MiB file in snapshot a, forks b, then punches a with an unaligned 5000-byte range, a 3 MB span, and a zero-range over the tail.
It then syncs and runs three GC collector cycles with reclaim on.
Result: b reads byte-identical to the original (also after a cache drop), a reads the model, b's live block set is unchanged, every b block is still in the store, and fsck has no damage.
After removing b and running GC again, a still reads the model and fsck is clean.
Limit: the GC report shows the only pack is `Active`, so no pack was rewritten or unlinked.
The test therefore proves the collector's input (the walk) is right, not that a reclaim cycle ran.
The builder's PR body states the same limit ("No GC cycle runs in these tests").
Chunk lists are Arc values and blocks are immutable, so the code has no in-place path that could touch a shared list.
I could not construct a meaningful copy-on-write-skipping mutation, because there is no separate copy-on-write step to skip.

## Non-blocking notes

1. `op_fallocate` takes `Timestamp::now()` before the node write lock, while `op_write` deliberately reads the clock inside the lock via `clock_read` (see its comment). A fallocate that waits behind a write can set mtime/ctime earlier than that write's. `op_setattr` has the same shape. Use `clock_read(&st)` after the lock, or file a follow-up.
2. The concurrency test covers Allocate against growing writes only. There is no concurrent write-versus-punch test. The lock makes it atomic by construction, but a test would pin it.
3. A comment in tests/fallocate.rs ("when FileTooBig lands") is stale. Its test does not pin the variant; the conformance check does.
4. Special files return InvalidArgument where Linux returns ENODEV. Slice C should map this deliberately.
5. Punch edge re-chunking adds store blocks and has no quota check; the doc says NoSpace on store refusal, which is fine, but this is untested.
6. The punch error-after-flush path has no fault-injection test (the PR says so).
7. No GC reclamation was exercised (the pack stays Active in small tests). Slice C or D, or a dedicated GC test, should cover a rewrite after a punch.
8. The daemon GuardedView and other wrappers still need fallocate forwarded in slice C, as the PR says.
