## What the diff does

## Attack (a): pre-serve to make the legit socket the least served
Handles are blake3-keyed MACs over (generation, ino, inode generation, kind) with a 32 byte urandom key (handle.rs).
Generation is checked first: older gives STALE, newer gives BADHANDLE, neither bumps `served`.
So an attacker without a handle cannot raise `served`.
Exploit run on the cachyos box (test x1, load 11 at start, cargo -j 4): cap 4, three attacker connections each sent forged, zero-MAC, empty and wrong-generation handles on GETATTR, FSINFO, FSSTAT and PATHCONF, plus MNT of a wrong path, EXPORT, DUMP and NULL.
Then the kernel-like socket pinged, MNT connection arrived.
Result: the pinged socket survived and GETATTR with the real root worked.
The only way to get `served` above zero is a valid handle, which only a won MNT yields (the documented racer case).

## Attack (b): starvation and thrash of new connections
Measured (test x2, cap 4): the pinged socket dies exactly on the 4th later connection, survives 3.
So eviction needs `max_connections` arrivals, as claimed (3 survived at cap 4, 63 at cap 64).
Timing: 64 raw loopback connects took 18.8 ms in a debug build.
An attacker therefore needs the gap between the kernel's ping and its first handle call to exceed roughly 20 ms, or a sustained flood above roughly 3000 connections per second.
The PR says "a few ms"; that gap was not measured and I did not measure it either (macOS only).
This is a rate bar, not a one-shot, which is a real improvement over one NULL ping.
N1: residual is real but honestly stated.
Thrash (test x3, cap 4): if every other slot is served, a newcomer that has not yet sent a handle call is evicted by the very next arrival.
There is no grace period for a brand-new connection.
Reachable only when all other slots hold served connections, which needs 64 valid-handle connections.
An attacker without a handle cannot build that; the racer who won the first MNT could, but the mount is already lost then.
N2 (low): optional hardening is to never pick a victim younger than a few hundred ms.
Not needed for this PR.

## (c) Fairness, ties, overflow, in-flight
Ties: (served, id) is a total order, ids are monotonic u64 from `next_conn`, so "oldest first" is deterministic and correct.
Overflow: `served` is u64 incremented by 1 per call, unreachable.
`active + 3_600_000` cannot overflow in practice.
Eviction under lock: victim is removed and `kick.send(true)` is non-blocking inside the mutex, fine.
Kick makes `serve_connection` break and `writer.abort()` drop queued replies.
A victim with an in-flight request loses its reply.
Victims are served-0 connections in every attacker-reachable state, so this costs the client one reconnect and a retransmit (reply cache replays non-idempotent calls, tests exist for that).
Not tested for a hard mount against a real kernel client.

## (d) First-MNT analysis
Verified in code: `MountGate::claim` is a one-shot atomic swap, later MNTs get MNT3ERR_ACCES and set `refused`, UMNT does not rearm, only `rearm_mount` (explicit) does.
`Mount::new` maps a refused MNT after mount_nfs failure to `RootHandleTaken`.
The comment's claims hold against the code: export path is the per-mount random token, the check_peer_uid path only applies to MNT and only helps against other users.
The "5 s" figure is NOT from code.
The only 5 s constant in mount.rs is `shutdown_timeout(5s)` in `Server::drop`, unrelated to mount_nfs.
The code-derived bound on how long a winning racer keeps access is `command_timeout`, default 20 s, plus unmount.
N3: the comment and PR body should say "at most command_timeout (20 s default); mount_nfs retry delay of 5 s is from Apple source, not measured".
The code path itself is marked `ponytail: reasoned, not tested end to end`.
