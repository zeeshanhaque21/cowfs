# Critic report: PR #241 (pjdfstest.py Linux mount table)

Verdict: PASS WITH NOTES.
No blocking counterexample was found.
Reviewed at head db7b961 in a fresh clone, read-only.

## Scope correction

The PR does not parse /proc/self/mountinfo.
It parses the text output of `/sbin/mount` in both shapes.
So the mountinfo questions (field positions, optional fields, octal escapes in mountinfo, bind mounts) do not apply to this diff.
The 11-line change is in `mount_entries`: if the text before the final ` (` contains ` type `, split it off and prepend the fstype to the options.

## 1. Parsers

macOS format is unchanged.
I fed this Mac's real `/sbin/mount` output (16 lines) to the old and new `mount_entries`.
The results are identical.

Linux format is correct for the shape in the PR.
`src on /mp type fuse.cowfs (rw,...)` gives mountpoint `/mp`, first option `fuse.cowfs`, and `fs_identity` takes the first option as `fstype`.
`mount` prints entries in mountinfo order.
`fs_identity` keeps the longest mount point and uses `>=` on ties, so for several mounts at one path the last (topmost) wins.
`mount_state` returns MOUNTED for any exact match, which is correct for stacked mounts.

Note 1 (low, real regression on macOS only for odd paths): the docstring says both OSes escape a space in a path.
I could not confirm that for `mount` on either OS.
Without escaping, a mount point containing a literal ` type ` parses wrongly now.
Example: `x on /Volumes/a type b (apfs, local)` used to give mount point `/Volumes/a type b`, and now gives `/Volumes/a` with fstype `b`.
So the "byte-identical" claim holds for the real table, not for every possible line.
Hardening option: only split when the tail after ` type ` has no further space, or key off the Linux-only form.
Unconfirmed: whether Linux util-linux `mount` prints spaces as `\040` or raw.
Spaces in other positions are harmless on both OSes.

Note 2 (pre-existing, unchanged): `mount_state` compares `str(path)` to the table without `realpath`.
A mount requested through a symlinked path reads NOT_MOUNTED.
`fs_identity` does call `resolve()`.
Linux callers should pass resolved paths.
The cachyos end-to-end run in the PR body used paths that matched, so this did not bite.

Fail-open check:
- An empty or non-newline-terminated table returns (None, reason), so `mount_state` gives UNKNOWN, and `start_daemon` raises "cannot confirm the mount".
  `fs_identity` sets `problem`, and `validate_runtime_identity` refuses to score.
  This fails closed.
- Garbage lines are skipped, so a table with no parsable line gives NOT_MOUNTED (pre-existing).
  That cannot make `start_daemon` accept a mount, since it needs MOUNTED.
  It could make `stop_daemon` think a mount is gone if the format ever drifted.
  Linux lines that previously mis-parsed now parse, so this risk shrank.
- A bogus MOUNTED needs an exact mount point string match, so the new split cannot create one by accident.

## 3. identity.json and arm distinction

`identity.json` writes `native_fs` and `cowfs_fs` from `fs_identity`; the fields are unchanged and `fstype` now fills correctly on Linux (`fuse.cowfs`, `btrfs`).
`validate_runtime_identity` separates the arms by `st_dev` only, plus a non-empty fstype, a mount point, and the expected cowfs mount path.
It does not compare fstypes, and this PR does not change that.
I checked: native `btrfs` dev 1 and cowfs `btrfs` dev 2 are accepted.
Native and cowfs reporting the same `st_dev` is still rejected.
If the requirement is "same fs type must be rejected" or "cowfs must be fuse.cowfs", that is not enforced before or after this PR.
Suggest a follow-up issue for a `fstype.startswith("fuse")` check on the cowfs arm.
