# Critic review: PR #255 (Fixes #243), FUSE mknod allows the 0:0 whiteout for non-root

Head reviewed: `e3f6e34ce127cb7e27ea8741956f9b216ec28f49` (branch `fix/fuse-whiteout-243`).
Reviewer: fresh-context security critic, read-only (no edits, merges or pushes).

## Verdict

PASS WITH NOTES.

No counterexample found: on a real mount the adapter now matches native Linux exactly, for every mknod form I tried as uid 1000.
The notes are test-strength and cross-adapter policy gaps, none of them a reason to block.

## 1. The predicate

`mknod_kind` matches `mode & S_IFMT` exactly, so only `S_IFCHR` gives `CharDevice`.
`S_IFCHR|S_IFBLK` is numerically `S_IFBLK` (0o060000), so it is a block device and stays root only.
Any other `S_IFMT` value is EINVAL.
`rdev_from_kernel` maps all 32 bits of the kernel `rdev` (bits 0-7 and 20-31 to the minor, bits 8-19 to the major), so the decoded value is 0 exactly when the raw value is 0.
No masking loss lets a nonzero device decode to 0.
`whiteout = special == Some(CharDevice) && rdev == 0` is therefore exact.

Runtime matrix on cachyos (kernel 7.2.8-2-cachyos, uid 1000), `mounthost` example built from the PR head (MemVfs behind the same `fs.rs` mknod path), mount `fuse.cowfs rw,nosuid,nodev,default_permissions`, compared with a native ext4 directory:

| mknod | native | cowfs mount (PR head) |
| --- | --- | --- |
| c 0 0, 0644 | ok, 0:0, 020644 | ok, 0:0, 020644 |
| b 0 0 | EPERM | EPERM |
| c 0 1 | EPERM | EPERM |
| c 1 0 | EPERM | EPERM |
| c 4095:0 | EPERM | EPERM |
| c 0:(1<<19) | EPERM | EPERM |
| S_IFCHR\|S_IFBLK 0:0 | EPERM | EPERM |
| S_IFMT 0o170000 | EINVAL | EINVAL |
| c 0 0, 06777 | ok, 026755 | ok, 026755 |

Parity is exact, including the setuid and setgid bits on the whiteout (native keeps them too; umask 022 applied).

Note N1 (test strength, low): for a non-root caller the kernel's `vfs_mknod` returns EPERM for every device except c 0:0 before the request reaches the daemon.
So the `b 0 0` and `c 0 1` assertions in `special_files_through_mknod` exercise the kernel, not the cowfs predicate (the CI log shows them as kernel EPERM).
A mutation such as `let whiteout = rdev == 0;` (dropping the kind test) would pass every test in this PR.
The only callers that reach the daemon's reject arm are a non-root uid holding `CAP_MKNOD` (setcap binary) and similar, which no test covers.
Suggested follow-up: lift the predicate into a pure function in `convert.rs` (kind, rdev, uid) and unit test b 0:0, c 0:1, c 1:0 and c 0:0 there.

## 2. What a stored whiteout means

On Linux, c 0:0 is inert: native open gives ENXIO, and on the nodev cowfs mount open gives EACCES.
On macOS, 0:0 is a real device: `/dev/console` on this Mac is `crw------- 0,0` (verified with `stat -f %Z`).
On FreeBSD, device nodes outside devfs do not work, so it is inert there.

The risk needs a privileged process to copy a cowfs tree onto a macOS filesystem that allows devices, keeping device nodes (for example `cp -a` or `rsync -D` as root).
The copy would then hold a console node with a mode the user picked.
I found no in-tree path that does this.
`cowfs-core::import` goes host to cowfs only.
The treehouse `CowfsMaterialiser` is an explicit `Unsupported` stub.
The macOS NFS mount options are `nodev,nosuid` (`crates/cowfs-nfs/src/mount.rs:130`), so a node served to a macOS client is inert.
Most importantly, this PR adds no new ability: any non-root Linux user can already make c 0:0 with native `mknod` on ext4 or tmpfs (row 1 above), and that out-of-tree copy hazard applies to native trees just the same.
Assessed risk: negligible, and inherent to Linux semantics rather than to cowfs.

## 3. Cross-adapter policy

Note N2 (pre-existing, medium, not introduced here): `crates/cowfs-nfs/src/adapter.rs` `mknod` (around line 701) has no privilege check at all.
Any NFS client caller can store any char or block device, for example b 8:0.
The NFS adapter maps every file to the mounter, and the macOS mount is `nodev,nosuid`, so the stored node is inert through that mount.
But the policy differs from FUSE (root only, plus the whiteout) and the stored node survives into snapshots, where another adapter or a later copy-out could expose it.
Recommend a GitHub issue to align NFS with the FUSE rule, or to document why the NFS adapter trusts its loopback client.
`PathVfs` and Core have no uid policy of their own.
PathVfs defers to the host kernel, which applies the same rule, and Core trusts its adapters.
So after this PR, FUSE and PathVfs agree on Linux, and NFS is the outlier, as before.

## 4. Conformance check

`mknod_whiteout_char_device` tolerates `PermissionDenied` only when `!cfg!(target_os = "linux")`; on Linux every error propagates, so a regression fails.
It does not look at `no_device_privilege`, which is right, because the whiteout needs no privilege on Linux 5.8 and later.
Running as root changes nothing: root also succeeds.
Note N3 (low): on Linux older than 5.8, or with a native PathVfs base directory on a filesystem that refuses unprivileged whiteouts (for example an NFS-backed base), the native run would fail.
That is arguably the intended parity assertion, but the kernel floor is worth one line in the doc comment.
The check also asserts `lookup` equality, `readdir_attrs` kind and rdev, and cleans up with `unlink`; I saw no ordering or timing source of flakiness.
