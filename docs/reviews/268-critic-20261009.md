## N2 (torn intent roll-forward)

The round-2 stray-snapshot risk is not reintroduced.
Reason: the roll-forward name is the intent FILE name, and the staging name is `staging_name(name)`, which hashes the full name.
A file name cut to `ab` yields `staging_name("ab")`, which is a different hidden name than `staging_name("abc")`.
So abc's staged tree is never published under `ab`; it is swept as an orphan, which is the pre-PR behaviour.
I checked this on the cachyos box with a corrupted file name (renamed `swap-abc` to `swap-ab`, content still readable): the result was snapshot list `["abc"]` only, no `ab`.
The intent writer is temp, fsync, rename, dirsync, so a file named `swap-<x>` cannot have a truncated name except by directory corruption.
Staged tree completeness: an intent only exists after the staging tree is fully built and verified (`stage_and_intent`, and import writes the intent after `verify`), so a roll-forward publishes a complete tree.
Unrelated user snapshot `ab` with a torn `swap-abc` and `abc` gone: test run on the box, `ab` content untouched, abc rolled forward, no leftovers.
Target still exists: staging removed, old target kept (the PR's new test, and my reading).
Roll-forward only runs when `snap_by_name(name)` fails, so it can never overwrite an existing snapshot.

### Note 1 (should fix): a failed roll-forward deletes the only copy

In `recover_intent` the torn branch computes `kept = ... && core.finish_swap(&staged, &name).is_ok()`.
If `finish_swap` returns Err (flush, fork or register I/O error), `kept` is false and the code then unregisters the staging snapshot and deletes the intent file.
That is exactly the loss the PR claims to prevent, in the one case where the target is gone.
The readable-intent path does the opposite: on a real error it returns Err and leaves the intent in place.
It needs two faults (media corruption of the intent plus an I/O failure during recovery), and main already deleted the tree in the first fault alone, so this is not a regression.
Not reproduced as a test: I found no deterministic injection point for a `finish_swap` failure at open (the swap fault seam does not cover it).
Suggested fix: on Err, return the error and keep both the staging tree and the file, the same as the readable path.

## N1 (staging-hash collision)

`clear_leftover` is called after `recover_target` in `ingest_with` and `swap_snapshot`, so a same-target retry is handled by recovery and never refused by its own intent (`t != target`).
Error text is clear and nothing is changed before the refusal.
The hash override is `#[cfg(test)]` and a thread_local, so it is absent from release builds, has no env or user API, and is not reachable from integration tests of the lib.
The test resets the override only at the end, but libtest runs each test on its own thread, so a panic cannot leak it.
Cost is one `read_dir` plus a read of each intent file per call, O(pending intents), small and rare.
The scan is not under a lock of its own.
A race needs two concurrent calls whose names already collide on a 64-bit hash plus a 200-byte prefix, and the old code had the same shared-staging-name race, so this adds no new exposure.

### Note 2 (minor)

Torn (unreadable) intents are skipped by the collision scan, so a colliding call can still delete the staging tree a torn intent would roll forward.
This again needs media corruption plus a hash collision.

## N3 (name length)

The check is `9 + len > 255` in bytes, applied to the temp file name `tmp-swap-<name>`, which is the longer of the two intent-related names, so `swap-<name>` also fits.
Box results: replacing import of 246 bytes ok, 247 refused, 255 refused; multibyte 123 x e-acute (246 bytes) ok, 124 (248 bytes) refused.
Consistent with the 240-byte base-name limit: names of 241 to 246 bytes are valid plain snapshots and valid replace targets, but not bases; that is fine.
Staging name is capped at 200 plus hash plus suffix, so it is not the limiting length.

### Note 3 (behaviour change)

`ingest_with` applies `check_target_len` whenever `replace` is true, even when no victim exists and no intent file will be written.
On origin/main a replacing import of a fresh 247 to 255 byte name worked (no intent needed); now it is refused.
This matches the PR text ("fails on the first call") but is a small regression for that input, and the PR body should say so.
Narrowing the check to `victim.is_some()` would keep the first-call guarantee for real swaps without it.

## Race: same-name promote vs base_refresh

The builder's reasoning holds from the code.
`promote` (core and path backends) runs inside `bases.exclusive`, requires the name to exist, and writes the "unknown" record only if no record exists.
`base_refresh` replaces the tree, calls promote, then `set_base_meta`, which overwrites unconditionally.
Any promote interleaving either sees no name (NotFound), sees an existing record (no write), or writes "unknown" that the refresh then overwrites, so the final record always comes from the last refresh.
The test (2 threads, 16 refreshes, both backends) checks the final state and each report's commit, so it would catch a stale final record.
It cannot see the transient between tree install and record write, where an old commit is paired with a new tree; that window exists independent of promote and was not claimed.
The test is adequate for the stated claim; weak but not misleading.
