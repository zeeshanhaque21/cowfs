# Critic report: PR #314 (per-target lock for swap and ingest, issue #300)

Verdict: MERGE-AFTER-FIXES.
The core fix is sound and the repro is real.
The fixes asked for are small (docs accuracy, one test hardening); the rest are follow-up issues.

## Evidence run

I checked out 437cc30 (test-only commit 1) and ran `cargo test -p cowfs-core --test swap_concurrent`.
All 3 tests FAIL there, so they fail without the fix (finished in 1.84s).
`python3 scripts/lock_audit.py --check` on the PR head: "lock-audit table is current (118 rows)".
CI on the PR: lint, ubuntu x2, macos, fault-seam, namespaces x2, fuse all SUCCESS.
I did not run the PR head tests locally and did not touch any NFS mount.

## Findings

1. Repro was done first and honestly (PASS). Commit 1 is test-only, commit 2 is the fix. PR body claims match what I observed.
2. Coverage of entry points (PASS with a gap). `swap_snapshot` (so `promote_base`) and `ingest_with` (so `ingest` and `ingest_replacing`) take the lock before `recover_target`, `clear_leftover`, staging, `replace_with_staged`, `finish_swap` and `rollback`. Those inner functions are only reached from those two entry points, so they are covered. `Core::open` recovery runs before any other caller exists (store flock), so it needs no lock.
3. Gap (MEDIUM, follow-up): `remove_snapshot`, `rename_snapshot` and `fork_snapshot` (lib.rs:333-353) do not take the target lock. A rename of the target name, or a remove of it, during a parked replacing import or promote still races on the same name. The lock is keyed by name, so a rename of the target to another name and then a promote of the new name takes a different key while the staging snapshot is the same id. Not part of #300's repro, but the PR doc says the lock "serialises every call that stages, replaces or recovers", which is true only for stage and replace. File an issue.
4. Gap (LOW, pre-existing): the staging name is a 64-bit FNV hash. Two different targets that collide get different lock keys but one staging snapshot. `clear_leftover` only guards the intent-file case, not a live in-flight collision. Needs a 2^32 search, so negligible, but the docs should not claim full per-staging-name isolation.
5. Lock order and deadlock (PASS). The lock is taken first, never nested, never twice in one call, never while holding a core lock. The set mutex is a leaf. The daemon's `ingest_replacing` takes `bases.exclusive` in a closure that returns BEFORE `ingest_with` runs (backend.rs:622-641), so the daemon lock is not held across the core lock. The core never takes daemon locks. No opposite-order path found. The per-snapshot `guard.lock` is taken above core calls in the daemon, same direction.
6. Blocking behaviour (MEDIUM, follow-up). The waiter blocks in `Condvar::wait` with no cancel check and no timeout. A daemon import of a name queued behind a long ingest of the same name cannot be cancelled or report progress while waiting. The lock is held across the whole ingest (minutes for big trees), by design. Other targets are not blocked (correct). `notify_all` wakes all waiters of all names (thundering herd, harmless at this scale) and there is no FIFO fairness, so a waiter can starve under constant contention on one name. Acceptable now; file an issue to poll a cancel hook while waiting.
7. Leak and poison (PASS). The guard removes the key on Drop, so the set never grows. Drop runs on unwind, so a panic inside an ingest releases the target. The set mutex uses `lk()` (poison-tolerant) and the wait uses `unwrap_or_else(into_inner)`. A panic in Drop-time `remove` is not possible.
8. Name vs id (see 3). Name key is right for the staging name and intent file, which are name-derived. It does not protect against rename.
9. Docs (FIX before merge). docs/v1-core.md now has two items numbered "0." in the lock list (the new one and the reference gate). Renumber. The lock-audit table row `swap::lock_target | leaf | 1` is misleading: the function takes the outermost lock, not a leaf. Mark it as root (or whatever the audit script's vocabulary allows) so the table matches the prose "above the gate". The table passes the script only because the script checks names.
10. Tests (FIX, small). Two tests assert the second call "waits" using a fixed `sleep(300ms)` and `recv_timeout(10s)`. They would pass if the lock did nothing and the second call simply ran after the first by luck, but they fail on main in practice because the second call runs during the park. On slow macOS CI the 300ms is still adequate as the intent is to let the second call start, so no flake risk was found (macOS job passed). Suggest asserting ordering explicitly (e.g. a channel that records completion order) rather than sleeping. The third test (4 promotes x 20 loops) is fast and deterministic enough.
11. PR body (PASS). Honest, lists the repro, the fix, the doc change and the stray `swap.rs-E` removal.
12. Scope creep (LOW). Deleting the tracked `swap.rs-E` sed backup is unrelated but correct and called out in the body. Fine.
13. CI macOS timing (PASS). macOS job green; tests finish in about 2s locally.

## Required before merge

- Fix the duplicate "0." numbering and the `swap::lock_target` audit row in docs/v1-core.md.
- Narrow the doc claim in `lock_target` so it does not imply rename/remove/fork are covered (or cover them).

## Follow-up issues to file

- Take the target lock in `rename_snapshot` and `remove_snapshot` for names that can be a swap target, or document why not.
- Make the lock wait cancellable and observable by the daemon import job.
- Replace sleep-based ordering in `swap_concurrent.rs` with explicit completion ordering.
