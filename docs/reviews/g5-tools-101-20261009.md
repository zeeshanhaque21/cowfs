# g5 tools (issue 101): building ltp/fsstress and ltp/fsx without root

Issue: 101.
Date: 2026-10-09.
Host: the cachyos box (`zeeshan@100.122.64.51`), kernel 7.2.8-2-cachyos, gcc 16.2.1 20260810.
Recipe: `bench/xfstests_build.sh`, tests in `bench/test_xfstests_build.py`.
Evidence: `docs/verification/evidence/g5-tools-101-20261009/`.

## Verdict

Building the helpers is no longer what blocks g5.
The recipe fetches the pinned xfstests commit, verifies it, and builds `ltp/fsstress`, `ltp/fsx` and `tests/generic/group.list` with no root, in about 20 seconds.
Both helpers pass a native smoke (fsx 200 ops A-OK, fsstress 50 ops with `-v`, 45 distinct op lines logged, rc 0).
What still blocks a g5 receipt is root for the suite's `check`, which this run did not have.
The one-case native vs cowfs sample was therefore not run.

## Exactly what blocked the build, per host

- `moonscapenas` (the Pi, where issue 101 was measured): autoconf, automake, libtool and m4 are not installed, and installing them needs root.
  The suite's build always goes through autoconf-generated `include/builddefs` and `include/config.h`, so nothing builds there unprivileged.
- This Mac: not viable.
  `ltp/fsx.c` and `ltp/fsstress.c` need Linux headers and syscalls (`linux/fs.h`, `sys/vfs.h`, statx, io_uring, libaio), and the suite runs only on Linux.
- The cachyos box: nothing is missing.
  autoconf, automake, libtoolize, m4, gcc and make are installed.
  The headers for libaio, liburing, acl, uuid and xfs are present (`attr/xattr.h` is absent and is not needed).
  The configure step detects AIO, io_uring, libcap, fallocate, open_by_handle_at, fiemap, copy_file_range, SEEK_DATA and FICLONE.
- A CI runner was not needed, so no artifact download path was built.
- The g4 `fsx` (`bench/fsx-gate/build-fsx.sh`) is not reusable for g5.
  It is a single-file build of a different xfstests commit (`22348afe`) with a hand-written `config.h`, which issue 101 declined for g5, and g5 also needs `fsstress` and `group.list` in-tree.

## The recipe

`bench/xfstests_build.sh XFS_DIR`:

1. Reads the commit pin from `bench/xfstests-allowlist.txt` (`tree_sha 3e1ee800e52a0f53d7d9a7809be1ffc80ec1788f`), so the build and the reviewed cases cannot drift apart.
2. If `XFS_DIR` is absent, `git init` plus `git fetch --depth 1 origin <commit>` from kernel.org, so only the pinned commit is ever fetched.
3. Refuses unless `HEAD` is that commit, the git tree object is `3683cb11c7dde850a567042e89b4e35e5d082b8e`, and the tree is clean.
   A present tree at another commit is refused before `make` runs.
4. Runs the suite's own top-level `make -k`, with unmodified flags.
5. Fails unless `ltp/fsstress`, `ltp/fsx`, `include/builddefs` and `tests/generic/group.list` exist, and the tree is still clean.
6. Records failed make targets instead of hiding them.
   Only `src/locktest` fails, against kernel 7.2 headers (`struct delegation` has no member `d_type`), as in the earlier status run.
7. Runs the smokes and refuses a helper that does not report work.
8. Writes `XFS_DIR.identity.txt` with the pins, compiler, kernel, make result and the helper sha256s.

No download other than the pinned git fetch happens, and git verifies the fetched objects against the commit and tree ids.

## Digests, and why they are per host and per path

The suite builds with `-g -O2`, so each binary embeds its build directory in `DW_AT_comp_dir`.
Measured: a clean rebuild at the same path gives byte-identical helpers.
Measured: the same gcc and identical `builddefs` and `config.h` at a different path give different helpers.
So the expected digest is a property of one build at one path on one host, as in g4's `rebuild_note`.
The recipe does not add `-ffile-prefix-map`, because that would change the suite's own flags.

Digests from the final recipe run at `/mnt/docs/Projects/cowfs-g5-build/final/xfstests`:

- `fsstress_sha256=37b4976f33f9f95e96a72045e5ff568de9a82008b3b713e08fdb49c8324370e7`
- `fsx_sha256=a3c50f07fd7297dabf9c9b4dca9ab4621a80d820c15902068bdf55119cc1fbae`
- `group_list_sha256=66cf56d81f41f7a485edbc3a57cd7d793384f6b9c365391cfe8853af313a96b4` (path independent)

These are not the digests a harness run will see, because `bench/g5_box.sh` builds nothing and uses `$G5_W/ref/xfstests`.
The harness workspace tree `/mnt/docs/Projects/cowfs-g5/ref/xfstests` currently holds an Oct 8 build with `fsstress` `9bfa06b0...` and `fsx` `d1ab6fa4...`, same gcc, differing only in `comp_dir`.

## How the g5 harness handled helper digests

Before this change it did not.
`bench/g5_root.sh` recorded `check_sha256`, every case sha and the daemon sha in `meta.txt`, but nothing about `ltp/fsstress` or `ltp/fsx`.
This change adds `fsstress_sha256` and `fsx_sha256` to that meta block, under the same keys the recipe writes.
So `grep -Fx -f <(grep _sha256 XFS_DIR.identity.txt | grep -v group_list) meta.txt` shows that a run used the recorded build.
Enforcing them in `bench/g5_diff.py` acceptance, as `--daemon-sha256` does for the daemon, is a follow-up.

## What still blocks g5

1. Root for `check`.
   `check` refuses non-root with `QA must be run as root`, and the arm model (loop device, ext4, private namespaces, root daemon) needs root by design.
   `bench/g5_box.sh` gets it from a sudo password on stdin, and no password source was available to this run (`CACHY_OS_PASS` unset).
   No sudo was attempted, which also avoids the faillock seen on the earlier run.
2. `bench/g5_box.sh` hardcodes `XFS=$W/ref/xfstests`, so to use a recipe build, run the recipe at `$G5_W/ref/xfstests` or point `G5_W` at a workspace whose `ref/xfstests` is the recipe build.
3. `src/locktest` still does not build on kernel 7.2 headers, so generic/131, 786 and 787 stay harness skips or both-arm failures.
